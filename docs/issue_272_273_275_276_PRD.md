One PR, four issues, two clusters:

- **Index cluster** — #272 (IndexRegistry silently rebinds a collection type) and #273
  (`[GenerateIndex]` maps complex properties with default indexing, which Corax faults on every
  document). Shared file: `GenerateIndexDiagnostics.cs`.
- **Synchronizer cluster** — #275 (hand-set `query` wiped on non-`[Reference]` attributes) and

The framework is in preview: breaking changes to public surface are acceptable now
(absorb-API-churn rule), and Fleet/HR are demo apps — changing them (including adopting
`[GenerateIndex]` on HR's `Person` as a live reproducer) is in scope, not a compat constraint.

## Issue #272 — IndexRegistry: one dictionary slot per collection type

### Problem

`IndexRegistry.RegisterIndex` (`libs/spark/MintPlayer.Spark/Services/IndexRegistry.cs:72-91`)
guards on `_byIndexName` but writes `_byCollectionType[collectionType] = registration`
unconditionally. Two differently-named indexes over the same entity silently rebind the collection
to whichever registered last — decided by `Assembly.GetTypes()` metadata order within an assembly
and `AddIndexesFrom(...)` order across assemblies. Direction from the issue owner: the defect is
the **data model**, not the missing guard — `Dictionary<Type, IndexRegistration>` structurally
cannot represent two indexes per collection, and RavenDB treats multiple indexes per collection as
routine. The registry must retain *all* registrations.

### Findings

- **F272.1 — Blast radius of the binding.** `GetRegistrationForCollectionType` feeds
  `QueryExecutor.cs:142-165` and `DatabaseAccess.cs:153-164` (the whole generic query surface),
  `ModelSynchronizer.cs:103-105` (projection/index merged into model JSON), and
  `ModelShapeDiscovery.cs:41-53` → `ModelHashVerifier` — so a nondeterministic winner makes the
  **model hash itself** flap between builds, tripping the `modelHashes.json` startup gate with no
  code change.
- **F272.2 — `IsProjectionType` scans only `_byCollectionType.Values`** (`IndexRegistry.cs:136-142`),
  so the overwritten registration's projection stops being recognized as a projection and
  `ModelSynchronizer`/`ModelShapeDiscovery` would emit the losing `V*` type as its **own entity
  model file** — the exact silent-wrong-output failure the doc comment at
  `SparkMiddleware.cs:372-385` warns about.
- **F272.3 — `RegisterProjection` already supports coexistence**: it resolves by index name via
  `_byIndexName` (`:94-110`), so with all registrations retained, each projection attaches to the
  right registration with zero changes.
- **F272.4 — SPARK_INDEX_004 is a dead descriptor.** `GenerateIndexDiagnostics.EntityAlreadyHasHandWrittenIndex`
  (`GenerateIndexDiagnostics.cs:107-118`) is declared but **never reported anywhere** — nothing
  prevents the collision today, not even within one compilation. Its doc comment is also wrong
  twice: the registry does not "silently skip duplicates" (it overwrites, unspecified winner), and
  it is not "the second index" that is never used (it is one of the two, unspecified which).
- **F272.5 — Population order is consistent within one build** (runtime, `--spark-synchronize-model`
  and `--spark-verify-model` all consume `SparkModuleRegistry.ResolveIndexAssemblies()` +
  `Assembly.GetTypes()` through the same `PopulateIndexTypes`), but **flips across recompiles** when
  source declaration order or `AddIndexesFrom` order changes — an invisible trigger for a visible
  hash change.
- **F272.6 — Offline paths construct the registry bare** (`new IndexRegistry()` in
  `SparkDevelopmentExtensions.cs:128,216` and in tests) — the fix must not require constructor
  arguments. In-class logging idiom is `Console.WriteLine` (startup-time activity).
- **F272.7 — Throwing on a duplicate is not an option**: coexistence is a legitimate pattern the
  issue explicitly wants (the CodeCoverage consumer needs a hand-written `Commits_ByRepository`
  *plus* `[GenerateIndex]` on the same entity), and re-registration of the same index is normal
  (multiple population paths per process).

### Requirements

- **R272.1** — The registry retains every registration; no registration is ever silently dropped or
  rebound. Two indexes over one collection type coexist, both addressable by name, both carrying
  their own projection.
- **R272.2** — The generic query path (singular lookup) resolves exactly one **default**
  registration per collection type, deterministically across builds, machines, scan orders and
  source reorderings. Chosen rule: **ordinal-min index name** (smallest `IndexName` under
  `StringComparer.Ordinal`) — insertion order was rejected because moving a class within a file
  silently flips the winner (F272.5).
- **R272.3** — A second index binding an already-bound collection produces a registration-time
  warning naming both indexes and the chosen default (`Console.WriteLine`, matching the class
  idiom). Never throw.
- **R272.4** — `IIndexRegistry` gains `GetRegistrationsForCollectionType(Type)` (plural,
  default-first order); the singular member's contract is documented as "the default registration"
  (not "the first"), so a future explicit-default marker changes only the selection rule, not the
  contract. Breaking interface change is acceptable (preview).
- **R272.5** — `IsProjectionType` recognizes projections of **all** registrations, including
  non-default ones (fixes F272.2).
- **R272.6** — Model-hash determinism: registering the same duplicate pair in opposite orders
  yields identical model hashes.
- **R272.7** — SPARK_INDEX_004: remove the dead descriptor (never reported, and its premise —
  one-index-per-entity hard ceiling — is now false). Update analyzer release tracking accordingly.
- **R272.8** — Minor: `TryGetValue(indexName, out var existing)` with unused `existing` →
  `ContainsKey`.

### Design

`_byCollectionType` becomes `Dictionary<Type, List<IndexRegistration>>`, append-only under the
existing `_lock`, kept default-first (sorted insert by ordinal index name). `_byIndexName` stays as
the dedupe/name-lookup structure — both are written once in the same lock, so no divergence hazard.
Plural lookup returns a copy, like `GetAllRegistrations`. Singular = element 0.

Non-default semantics, stated explicitly: a non-default index's projection type is recognized by
`IsProjectionType` (so it never becomes a phantom entity model file) but appears in **no** model
JSON — it is a hand-query-only surface reached via `session.Query<TProjection, TIndex>()`, which
never consults the registry. The stale-model-file cleanup (`ModelSynchronizer.cs:219-230`) deletes
any previously-emitted file for it.

**Deferred (follow-up issue):** an explicit `IsDefault` marker on `[GenerateIndex]` / hand-written
indexes. The restructure makes the registry side of it ~5 lines (selection prefers the marked
registration, else ordinal-min), but the attribute/generator plumbing collides with #273's edits to
the same generator files. File it after this PR merges.

## Issue #273 — `[GenerateIndex]` complex properties fault Corax

### Problem

`GenerateIndexGenerator.Describe()` maps every indexable property verbatim
(`GenerateIndexGenerator.cs:298-309`); a complex-typed property (nested object, or collection of
non-scalars) gets no `Index()` declaration → RavenDB default indexing → Corax throws
`NotSupportedInCoraxException` **per document** at runtime, with no compile-time signal. The index
ends up with zero entries and the generic grid for that entity returns nothing. Reproduced in
MintPlayer/CodeCoverage (`Build.Sessions`, `Build.Coverage`, `Repository.LatestCoverage`).

Dropping the field (`[IgnoreForIndex]`) is not an acceptable default: `EntityMapper` builds
AsDetail attributes from the full complex object on the projection (`EntityMapper.cs:228-234`) and
silently skips attributes with no matching projection property (`:224`) — the column would blank.
RavenDB's own exception names the sanctioned combination: **store it, don't index it**.

### Findings

- **F273.1 — `FieldIndexing = "No"` flows through with zero shape change.** `IndexPropertyInfo.FieldIndexing`
  is a string where `null` means "declare nothing" (load-bearing for sort companions,
  `GeneratedIndexInfo.cs:104-111`); the producer's emission loop (`Producer.cs:251-255`) renders any
  non-null value. Setting `"No"` in `Describe()` emits
  `Index(nameof(VX.Field), global::Raven.Client.Documents.Indexes.FieldIndexing.No);` and
  `StoreAllFields(FieldStorage.Yes)` (`:260`) keeps the field projectable — grids keep rendering.
- **F273.2 — `DescribeReferenced()` calls the same `Describe()`** over metadata symbols
  (`GenerateIndexGenerator.cs:375-396`), so a classifier inside `Describe()` covers
  referenced-assembly entities for free. Metadata symbols have no source location — SPARK_INDEX_010
  anchors at `Location.None` there, same as existing diagnostics.
- **F273.3 — Runtime twin.** `SparkModelShape.IsComplexType` (`SparkModelShape.cs:261-270`) +
  `GetDataType` (`:182-207`, which special-cases `System.Drawing.Color → "color"` and
  `TranslatedString` *before* the complex fallback) are the rules to mirror, per the keep-in-step
  mandate in the `SparkModelSymbols.cs` header. But the classifier must key on the **serialized
  JSON shape**, not `IsValueType`: a user-defined struct persists as a JSON object and faults;
  runtime's `IsComplexType` would wrongly call it scalar. Dictionaries
  (`KeyValuePair<,>` elements) likewise persist as objects — classify complex (deliberately
  stricter than runtime; flag the runtime divergence, don't change runtime in this PR).
- **F273.4 — Spike answered statically: duplicate `Index()` throws.** RavenDB.Client 7.2.5's
  `Index(string, FieldIndexing)` is `IndexesStrings.Add(...)` — a second call for the same field
  throws `ArgumentException` at index construction. Generated `Index()` calls run **before** the
  `OnInitialize()` partial (`Producer.cs:232-266`), so consumers carrying the manual workaround
  partial (Coverage's `GeneratedIndexes.ComplexFields.cs`) will **throw loudly at startup** once
  the generator emits the same call. Release note required: delete the workaround partial.
- **F273.5 — Spike answered statically: Fleet is NOT latently broken.** `Car.Color`/`InteriorColor`
  persist as `"#rrggbb"` strings via `ColorNewtonsoftJsonConverter`
  (`Converters/ColorNewtonsoftJsonConverter.cs:21-30`, registered in `SparkMiddleware.cs:88-93`);
  the index map runs against stored JSON, so no fault. The classifier must whitelist
  `System.Drawing.Color` as scalar or the fix regresses Fleet.
- **F273.6 — `[Search]` on complex already errors via SPARK_INDEX_005** (`SearchKindOf`,
  `GenerateIndexGenerator.cs:539-556`), but `Describe()` still emits `FieldIndexing = "Search"` for
  it (tolerable only because 005 is an Error). The classifier must make complex win: `"No"`, no
  companion, regardless of `[Search]` — 005 keeps reporting.
- **F273.7 — SPARK_INDEX_010 is free.** House severity convention: Error = generated output broken;
  Warning = something silently does nothing. No Info diagnostic exists, and Info renders as an
  easily-missed build message — **Warning** chosen for stored-not-indexed.
- **F273.8 — HR `Person` is the natural demo reproducer**: `Address?` (nested complex) and
  `[Sortable] CarreerJob[]` (array of complex) would fault immediately; `Professions`
  (`List<string>`) must stay indexed. Fleet/HR are demos — adopting `[GenerateIndex]` on `Person`
  as a live acceptance case is in scope.
- **F273.9 — Measured (spike, live 7.2.5): the fault is engine-dependent.** On a Lucene-defaulted
  server the verbatim complex map indexes without error; forcing `SearchEngineType = Corax`
  reproduces the per-document `NotSupportedInCoraxException` exactly (2 of 3 docs faulted; the doc
  with `Address = null` + `Jobs = []` indexed fine — confirming the "clean in an empty dev DB"
  profile). **Regression tests must pin Corax explicitly** or they silently pass on
  Lucene-defaulted servers.
- **F273.10 — Measured: nested-path map expressions are null-safe on Corax.**
  `item.Address.City` with null `Address` and the two-hop `item.Address.Description.Label` through
  a mid-path null both index as null with zero index errors — RavenDB evaluates maps server-side
  over stored JSON, where a missing path yields null, never an NRE (consistent with the S6
  measurement in `docs/issue_210_plan.md:105-135`). Sorting on the nested-path scalar works (nulls
  first) and equality filtering works. **The generator does not need to emit null guards.**
  Collection fan-out `item.Jobs.Select(j => j.Title)` also indexes cleanly (multi-valued field;
  null `Jobs` degrades to empty) — usable for filter/search, meaningless for sort.
- **F273.11 — Measured: sort/filter against a `FieldIndexing.No` field degrades silently** —
  filter returns 0 rows, sort returns rows in meaningless order, no error either way. No
  `QueryExecutor` guard is required; a doc note suffices. Byte-identical redeploy is a no-op
  (`CreatedTimestamp` unchanged).
- **F273.12 — `BreadcrumbAttribute` today is class-level-template-only**
  (`libs/spark/MintPlayer.Spark.Abstractions/BreadcrumbAttribute.cs:15-24`:
  `AttributeUsage(AttributeTargets.Class)`, single `Template` ctor arg; consumed by the runtime
  `BreadcrumbResolver` via template parsing, `BreadcrumbTemplate.cs:24-89`). **No property-level
  marker exists** — the breadcrumb-companion design requires widening it to `Class | Property`
  with a parameterless ctor for the marker form. No back-compat constraint (preview).
- **F273.13 — REPLACE-the-field is structurally dead; COMPANION rides existing machinery.**
  Mapping the nested path *into* the complex field's own name puts a string where the projection
  declares the complex type: `ModelSynchronizer.cs:477-488` throws on the collection-vs-projection
  type mismatch, and `EntityMapper.cs:222-234` needs the full complex object to scaffold the
  AsDetail column (a string blanks it). The companion shape (`{Name}Sort`, `FieldIndexing = null`,
  `IsSortCompanion = true` → `[IgnoreProperty]`) is byte-for-byte the existing
  TranslatedString-companion pattern (`Producer.cs:91-98`, `GenerateIndexGenerator.cs:516-525`):
  emission, index-entity property, `[IgnoreProperty]`, storage and the
  `QueryExecutor.ResolveSortProperty` redirect (`QueryExecutor.cs:796-803`) are all automatic —
  **sorting works with zero runtime change**. The name must be exactly `{Name}Sort` (the redirect
  matches only that suffix + `[IgnoreProperty]`). The synchronizer vetoes `[IgnoreProperty]`
  members (`ModelSynchronizer.cs:448-462`), so no model JSON churn and no hash change.
- **F273.14 — Per-column filtering does not exist in the generic query surface** (`Execute.cs`
  accepts `sortColumns`/`skip`/`take`/`search`/`parent*` only), so no filter redirect is needed.
  Caveat: `ResolveSearchableProperties` (`QueryExecutor.cs:716-725`) deliberately excludes
  `[IgnoreProperty]`, so the breadcrumb companion is invisible to `?search=` pushdown — the complex
  column sorts but its text is not searchable. Documented limitation; widening search is a
  deliberate follow-up, not a silent side effect.
- **F273.15 — Referenced-assembly walk works**: all symbol attribute checks match by
  fully-qualified name (`SparkModelSymbols.cs:157-158`), valid for metadata symbols; `[Breadcrumb]`
  lives in Abstractions, which the entity's assembly must already reference. Edge: an unresolvable
  complex type degrades to an error symbol with no members — the walk must fail soft to
  `FieldIndexing.No`, never crash.

### Design — two layers

**Layer 1 (foundation, always active):** complex properties are mapped verbatim, stored, and
declared `FieldIndexing.No`. This is the unconditional fallback: it is what collections of complex
elements get, what breadcrumb-less complex types get, and what an unresolvable metadata type
degrades to. The classifier is one internal symbol-level predicate,
`IsComplexForIndex(this ITypeSymbol)`, in `SparkModelSymbols` — an allow-list forced by how types
persist (not negotiable by framing): unwrap `Nullable<T>`; unwrap collection elements (arrays, the
six generic wrappers, any `IEnumerable<T>` except `char`; dictionaries/`KeyValuePair<,>` →
complex) and recurse; scalar iff `SpecialType` primitive/string/bool/char/numeric, enum, `Guid`,
`DateTime`, `DateTimeOffset`, `TimeSpan`, `DateOnly`, `TimeOnly`, `decimal`,
`System.Drawing.Color` (persists as `"#rrggbb"` — recursing into R/G/B would be wrong and regress
Fleet), `TranslatedString` (keeps its fan-out). Everything else — unknown classes, user structs —
is complex. Doc-linked to `SparkModelShape.IsComplexType`/`GetDataType` per the keep-in-step rule,
with the deliberate divergences (user structs, dictionaries) stated.

**Layer 2 (breadcrumb surface rework + sort companion — v3, three-agent design pass +
live measurements, 2026-08-19).** The breadcrumb configuration surface is redesigned for full
Vidyano parity; nothing of today's breadcrumb system needs preserving (owner direction). Two
surfaces, each where its consumers live:

**Display surface — the model JSON template, authoritative (Vidyano parity):**

- The class-level `[Breadcrumb("template")]` attribute is **deleted** (breaking, allowed). The
  `"breadcrumb"` template in the entity's model JSON becomes the sole display authority — exactly
  Vidyano's shape (`"Breadcrumb": "{Key} - {Value}"` in the po-json, hand-authored, reference
  tokens recursing). The synchronizer's existing preserve → synthesize → validate pipeline
  (`ModelSynchronizer.cs:702-760`) survives minus the attribute-authoritative branch; its
  shape-hash lines (`SparkModelShape.cs:64-68`) are deleted with it. `breadcrumb` stays
  presentational and hash-invisible (`ModelFileShape.cs:33-35`), same regime as post-#274
  `showedOn`.
- **New resolver arm — embedded-complex tokens.** Today a template token naming an embedded
  complex property (`{Customer}` where `Customer` is a nested object) falls into the scalar arm
  and renders `ToString()` — i.e. the CLR type name, silently
  (`BreadcrumbResolver.cs:144-206`). Fix: `attr.DataType == "AsDetail" && !attr.IsArray` → resolve
  the embedded type's own breadcrumb (its JSON template, or its marked property — below) against
  the in-memory embedded value. No extra loads (the data is in the document; AsDetail-nested
  reference targets are already preloaded, `BreadcrumbResolver.cs:223-238`); template-cycle guard
  by CLR type; mirrored in `EmbeddedBreadcrumbRenderer`. This closes the owner's
  `[Breadcrumb("{Customer}")] class Order { Person Customer }` case for display.
- Reference tokens keep the BFS resolver unchanged (cross-document, RLS-checked).

**Index surface — the property-level `[Breadcrumb]` marker in C#:**

- `BreadcrumbAttribute` becomes `AttributeTargets.Property`, parameterless (the template ctor
  dies with the class form). The marker means "**this type renders as this property**". It may
  sit on a stored scalar property (`[Breadcrumb] string LastName`) or on a **computed get-only
  property** that combines fields in real C#
  (`[Breadcrumb] string FullName => $"{FirstName} {LastName}"`). Both are equivalent to every
  consumer because **the value persists into the document JSON** (measured — Newtonsoft
  serializes get-only properties; nothing in Spark suppresses them; `IgnorePropertyAttribute.cs`
  documents persistence explicitly). Multi-level composition is ordinary C#
  (`Order.Customer` of type `Person` whose `FullName` references `Address.Crumb`, etc.) — the
  compiler enforces reachability, so the previously-planned recursive symbol walk
  (`FindBreadcrumbPath`, cycle set, depth limit, explicit-at-every-level machinery) collapses to a
  **one-hop lookup**: `GetBreadcrumbProperty(this INamedTypeSymbol)` over `GetSparkProperties`
  (raw member scan — deliberately not `IsIndexableProperty`, see next point).
- The marked property carries `[IgnoreProperty]` when it should stay out of the visible model —
  the **sanctioned** combination (it is exactly the generator's own sort-companion pattern,
  `GenerateIndexProducer.cs:275-282`); persistence and index reachability are unaffected. Without
  `[IgnoreProperty]` it becomes a read-only model column (per #253) — the author's choice.
- **Generator emission**: for a *singular* complex property `Customer` whose type has a marked
  property `X`: one extra `IndexPropertyInfo` — `Name = {Name}Sort` (**must** be the `Sort`
  suffix; `ResolveSortProperty` redirects only to it), `MapExpression = item.Customer.X` (reads
  the persisted value; nested member access is measured null-safe, F273.10), `FieldIndexing =
  null` (undeclared = one lower-cased un-tokenized term = case-insensitively sortable),
  `IsSortCompanion = true` (→ `[IgnoreProperty]`). Rides the TranslatedString-companion pattern
  end-to-end; sorting works with zero runtime change; no model JSON or hash churn (F273.13).
- **Consistency by default, drift warned**: for a type with a marked property, the synchronizer's
  *synthesized default* template becomes `"{MarkedProperty}"` — display and sort agree unless the
  author edits the JSON template away, which triggers a sync-time warning (heuristic: the marked
  property does not appear in the authored template). This is the accepted cost of two
  half-surfaces; a single surface cannot serve both the hand-editable JSON display contract and
  the source generator (see rejected alternatives).

**Rejected alternatives (design-twice, all evidence-based):**

- *Template-compiled concat map expressions* (generator renders `"{FirstName} {LastName}"` into
  `item.Customer.FirstName + " " + item.Customer.LastName`): measured viable but carries a real
  transpiler hazard — RavenDB's LINQ-to-string conversion **silently re-bound `.Trim()` to the
  last operand** of a concat chain (verified via `GetIndexOperation` map dump), so only bare `+`
  chains are safe; null tokens render as empty strings producing leading-space artifacts that
  cluster in sorts; and it requires two renderers of one template (generator + runtime) agreeing
  forever. The persisted marked property needs none of that machinery.
- *JSON-only config consumed by the generator via `AdditionalFiles`*: structurally possible (the
  generator runs in the app project where App_Data lives) but one build behind the synchronizer,
  per-app csproj ceremony that fails silent when forgotten, and diagnostics that cannot anchor to
  symbols. Decisive: once breadcrumb config drives an index map it is no longer presentational —
  a hash-invisible JSON edit would silently change the deployed index, inverting the
  `modelHashes.json` gate's purpose. The index-relevant bit must live in C#.
- *Materializing the rendered breadcrumb as an index field for display* (owner note): display
  would need a DB roundtrip against the index per resolution + staleness. Display stays
  resolver-based. (Note the persisted marked property is different: it lives on the *document*
  the resolver already loaded — no roundtrip.)
- *Imperative breadcrumbs (actions-hook `GetBreadcrumb(entity)`)*: arbitrary code cannot be
  compiled into a map — display and sort would diverge silently. A Vidyano-style PO-shaped
  `OnLoad` hook (Spark has none today; `po.Breadcrumb` is stamped by `EntityMapper.cs:212` and
  nothing runs after it) is a display-only follow-up; the index companion never mirrors it.

**Out of scope for the companion**: collections of complex (no single path; measured `Select`
fan-out indexes but cannot sort — stays Layer 1); a marker on a `[Reference]` id property (the
crumb cannot cross documents — and `LoadDocument` in a map is rejected outright: it would leak
RLS-redacted values into sortable terms and reindex on every referenced-document change;
diagnostic, degrade to Layer 1); TranslatedString-marked properties (language decision — defer).

**Known costs, measured:** a null-unsafe computed getter throws `JsonSerializationException` at
save time — and the getter also runs during session dirty-check re-serialization, so it can fail
an unrelated `SaveChanges` that merely loaded the entity. Loud but wide; authors must write
null-safe getters (document prominently; an analyzer can only heuristically warn). Documents
saved before the marked property existed lack the field until re-saved (index reads null; re-save
heals; demos are fresh). A formula change after deploy leaves stored crumbs stale until the next
save (self-healing, byte-stable recompute otherwise — deterministic getters cause no phantom
dirty flags).

### Requirements

- **R273.1** — A complex-typed property on a `[GenerateIndex]` entity is mapped, stored, and
  declared `FieldIndexing.No`: the generated index deploys and populates **on Corax** (tests pin
  `SearchEngineType.Corax` explicitly — F273.9), and the field round-trips through `ProjectInto`
  and `QueryExecutor` fully populated.
- **R273.2** — The `IsComplexForIndex` classifier per Layer 1, in `SparkModelSymbols`.
- **R273.3** — Complex wins over `[Search]`: no `Search` indexing, no *search* companion;
  SPARK_INDEX_005 still reported. The breadcrumb sort companion is independent of `[Search]`.
- **R273.4** — Diagnostics, all reported via per-property lists on `GeneratedIndexInfo`
  (`InvalidSearchProperties` pattern):
  **SPARK_INDEX_010 (Warning)** — complex property with no reachable breadcrumb: stored for
  projection, not indexed; add `[Breadcrumb]` to a property of `{ComplexType}` to make the column
  sortable, or `[IgnoreForIndex]` to drop it from the index.
  **SPARK_INDEX_011 (Warning)** — multiple `[Breadcrumb]`-marked properties on one type: names
  all candidates and the ordinal-min winner.
  **SPARK_INDEX_012 (Warning)** — unusable `[Breadcrumb]` placement (on a `[Reference]` id
  property, on a collection-typed property, or on a complex-typed property whose own type also
  marks nothing): named reason, companion skipped, field degrades to Layer 1. Note
  `[Breadcrumb]` + `[IgnoreProperty]` is the **sanctioned** combination (hidden from the model,
  persisted, index-reachable) — never diagnosed.
- **R273.5** — Entities with no complex fields produce byte-identical generator output (no index
  reset for the unaffected).
- **R273.6** — Works for referenced-assembly entities (metadata symbols) for both layers,
  covered by `ReferencedAssemblyEntityTests` cases; unresolvable types fail soft to Layer 1
  (F273.15).
- **R273.7** — Release notes: consumers with the `OnInitialize()` workaround partial must delete
  it (duplicate `Index()` throws at startup, F273.4); class-level `[Breadcrumb("template")]` is
  removed — move templates into the model JSON (the synchronizer preserves what is already
  persisted there, so most apps need no action); marked computed getters must be null-safe
  (save-time throw otherwise); pre-existing documents grow the marked field on next save.
- **R273.8** — HR `Person` adopts `[GenerateIndex]` as the in-repo acceptance case:
  `Address` gains `[Breadcrumb] public string Crumb => $"{Street}, {City}"` (computed, null-safe,
  `[IgnoreProperty]`) → sortable AsDetail column via the companion; `Jobs` (collection of
  complex) lands on Layer 1; `Professions` (`List<string>`) stays indexed. HR's existing
  class-level `[Breadcrumb]` templates on `Person`/`Company`/`Profession` migrate into the model
  JSON (they are already persisted there by today's sync — deleting the attribute is a no-op for
  the files).
- **R273.10** — Display: the resolver (and `EmbeddedBreadcrumbRenderer`) renders an
  embedded-complex template token via the embedded type's own breadcrumb (JSON template, else
  marked property) instead of `ToString()`; template-cycle guarded; reference tokens unchanged.
- **R273.11** — Synchronizer: attribute-authoritative branch deleted; JSON templates preserved
  and validated as today; synthesized default for a marker-carrying type is `"{MarkedProperty}"`;
  sync-time drift warning when a type's marked property does not appear in its authored template.
- **R273.12** — A persisted-shape pin test (modeled on `TranslatedStringPersistedShapeTests`)
  asserts the marked get-only property serializes into the stored document JSON at both entity
  and embedded level — the design's load-bearing fact.
- **R273.13** — **Standalone placement analyzer** (in scope; next free SPARK00x id — SPARK003 is
  the template-placeholder analyzer, SPARK004 the middleware-order analyzer; verify at
  implementation), so entity-library authors get squiggles locally, before any app compiles:
  (a) `[Breadcrumb]` on a property **inside a `[FromIndex]` projection class** → Warning
  "no effect — projections are derived; mark the source type's property instead";
  (b) `[Breadcrumb]` on an invalid property kind (collection-typed, `[Reference]` id,
  `TranslatedString`) → Warning — the local, symbol-anchored mirror of SPARK_INDEX_012 (the
  generator-side 012 still fires for referenced-assembly entities the analyzer never saw).
  No code fix (a `CodeFixProvider` in the analyzer assembly breaks the generator suite —
  measured, see `reference_codefix_needs_own_assembly`). Deliberately **not** included: a
  "marker declared but never used by any index" rule — an entity library compiles without
  knowing its consumers, so it would false-positive on any library indexed by only some of its
  apps.
  Fate of SPARK003 (`IgnoredBreadcrumbFieldAnalyzer`, validates class-level template
  placeholders): its subject is deleted in this PR — retire it; the new placement analyzer is
  its successor.
- **R273.9** — Companion-name collision (an entity already declaring a real `{Name}Sort`
  property): skip + diagnose, reusing the hand-written-companion dedupe
  (`GenerateIndexGenerator.cs:461-464`).

### Spike results (executed 2026-08-19 against live RavenDB 7.2.5, Corax forced)

Round 1 (F273.9–F273.11): fault reproduced (per-doc, non-null complex only), `FieldIndexing.No` +
`StoreAllFields` repair pinned through `ProjectInto`, nested single- and two-hop path maps
null-propagate (no guards needed), sort/filter on a `No` field degrades silently (no guard
needed), collection `Select` fan-out indexes but can't sort, byte-identical redeploy is a no-op.

Round 2 (breadcrumb design pass):

- **Computed get-only properties persist** into the stored JSON at every nesting level
  (`{"Address":{...,"Crumb":"Main, Ghent"},"Crumb":"Alice @ Main, Ghent"}`); the index reads them
  with a plain member access and sorts them (nulls first).
- **Null-unsafe getter throws at save**: `JsonSerializationException` from the getter during
  serialization — the entity is unsavable until the getter is null-safe.
- **Concat-through-null in server maps**: `null + " | " + null` renders `" | "` (nulls become
  empty strings, junk separators survive) — one of the reasons template-compiled concat maps were
  rejected. The other: RavenDB's LINQ transpiler **re-bound `.Trim()` to the last operand** of a
  concat chain (measured via `GetIndexOperation`) — only bare `+` chains transpile faithfully.
- **Sort semantics**: an undeclared companion field stores one lower-cased whole-value term —
  case-insensitive sorting; never declare `Exact` (case-sensitive regression) or `Search`
  (multi-term, arbitrary order).

Remaining to verify in-repo (cheap, part of M2's tests, not blocking design): the same behaviors
under `SparkTestDriver` with the *generated* index shape, and the end-to-end `QueryExecutor` sort
redirect through the breadcrumb companion.

## Issue #275 — Synchronize wipes a hand-set `query` on non-`[Reference]` attributes

### Problem

`ModelSynchronizer.cs:575` (existing-attribute update branch):
`existingAttr.Query = referenceAttr != null ? resolvedQuery : null;` — a hand-set `"query"` on an
attribute **without** `[Reference]` but **with** a matching CLR property is nulled on every run.
Same defect class as #274 (silent re-derivation over an authored value). Unlike `showedOn`,
`query` **is** part of the structural hash (`ModelFileShape.StructuralAttributeFields`,
`ModelFileShape.cs:114-119`), so the fix must distinguish "derived value went stale" (clear) from
"no derived value exists" (preserve).

### Findings

- **F275.1 — The derivation source only exists when `referenceAttr != null`**
  (`ModelSynchronizer.cs:531-536`: explicit `[Reference].Query`, else `Get{ContextProperty}` for
  the target type). For a non-reference property there is nothing to derive — any stored value is
  authored.
- **F275.2 — The stale-derived case is real**: removing `[Reference]` from a property leaves a
  machine-derived `query` behind; naively preserving it keeps a dead value that the hash then
  confirms — the exact failure the `:569-573` comment warns about.
- **F275.3 — Provenance signal exists**: an attribute that *was* a Reference stores
  `dataType: "Reference"` and non-null `referenceType`, both readable **before** the update branch
  overwrites them (`DataType` reassigned at `:563-566`, `ReferenceType` at `:574`).
- **F275.4 — Hash/gate implications: none.** Synchronize writes the preserved value and then
  re-hashes its own output (`WriteModelHashes`, `:232,239-247`) — self-consistent. Hand-editing a
  deployed App_Data without re-syncing trips the gate, as for any structural field; synchronize is
  what blesses the edit. Unchanged semantics.
- **F275.5 — Runtime caveat**: `EntityMapper.cs:446` sends
  `Query = def.DataType == "Reference" ? def.Query : null` on the wire — a preserved `query` on a
  non-Reference attribute is currently invisible to the client. The fix's value is not destroying
  authored JSON and unblocking future consumers; passing it through EntityMapper is **out of
  scope** (flagged, not changed).
- **F275.6 — Composes with merged #277**: the showedOn fix sits at `:592-595`, same method,
  disjoint lines.

### Requirements

- **R275.1** — A hand-set `query` on a non-`[Reference]` attribute with a matching CLR property
  survives synchronize, run any number of times (fixed point).
- **R275.2** — A `[Reference]` attribute's `query` is still re-derived on every run (tampering it
  is corrected back).
- **R275.3** — Removing `[Reference]` from a property clears the stale derived `query` (and
  `referenceType`), with a console line explaining the clear — the `queryType`-clearing precedent
  at `:398-419`.

### Design — provenance-gated re-derive (chosen)

Capture `wasReference = existingAttr.DataType == "Reference" || existingAttr.ReferenceType != null`
**before** the overwrites at `:563`, then:

```csharp
existingAttr.Query = referenceAttr != null ? resolvedQuery   // still a reference: re-derive
                   : wasReference          ? null            // reference removed: stale derived — clear (+ console line)
                   : existingAttr.Query;                     // never a reference: authored — preserve
```

**Rejected:** name-convention sniffing (`Get{X}` is also the most natural hand-authored name —
ambiguous both ways); pure preserve (leaves the stale derived value hashed as gospel — the same
reason #274 rejected delete-the-line).

## Issue #276 — SparkQuery `source` goes stale after a context property rename

### Problem

`CollectQueriesFor` (`ModelSynchronizer.cs:323-338`) copies existing queries through verbatim
(dedup by `Id` only); minting (`:111-136`) only creates a query when none of that **name** exists.
After renaming a `SparkContext` property, the old query keeps `"source": "Database.OldName"`
(pointing at nothing — `QueryExecutor.ExecuteDatabaseQueryAsync:111-116` silently returns `[]`,
an eternally-empty grid) and a second query is minted for the new name — both left in the file.

### Findings

- **F276.1 — `IndexName`/`UseProjection` are never written by the synchronizer at all** — the mint
  sets only `Id`, `Name`, `EntityType`, `Source`, `SortColumns`. Every stored
  `indexName`/`useProjection` value is hand-authored. "Re-derive them" would wipe authored
  overrides — precisely the #274 defect class. They must be left alone (at most an advisory
  warning when `IndexName` names an index unknown to the registry — advisory only, because
  registry discovery is entry-assembly-scoped, `:407-415`, and #272 is changing its semantics).
- **F276.2 — Rename is detectable with high confidence**: within one entity's query group,
  exactly one dead `Database.X` source (resolves to no context property of that entity's type) +
  exactly one unclaimed property (no query sources it) = rename. Multiple simultaneous same-typed
  renames are ambiguous — refuse to pair, fall back to warn + mint.
- **F276.3 — Query identity is `Id`**: program units reference queries by `QueryId`
  (`Endpoints/ProgramUnits/Get.cs:128-131`) — retargeting in place (same `Id`) keeps them working;
  delete + re-mint would orphan them.
- **F276.4 — `Custom.*` queries are a separate feature** (#37; `StreamingQueryExecutor.cs:31` also
  keys on the prefix) and must never be touched.
- **F276.5 — SparkQuery is not hashed** (`ModelFileShape.Describe` reads only the
  `persistentObject` element) — no gate implications; only the fixed point must hold.
- **F276.6 — "Re-derive `Source` keyed by name/id" was rejected**: `Name` is authored/renamable
  (breaks deliberately-renamed queries); `Id` encodes nothing to derive from. Rename-pairing is
  the only derivation that exists.

### Requirements

- **R276.1** — Scope guard: everything below applies only to queries whose `Source` starts with
  `Database.` (ordinal-ignore-case) and whose `EntityType` matches the file being written.
  `Custom.*` queries pass through byte-identical.
- **R276.2** — Rename ⇒ **retarget in place**: pair one-dead-with-one-unclaimed (same entity),
  set `Source = "Database.{NewProp}"` on the existing query, preserving `Id`, sort columns, render
  mode, description, alias and all other authoring; skip minting the duplicate. If `Name` matches
  the minted convention `Get{OldProp}`, rename to `Get{NewProp}` (and clear a matching auto-alias);
  an unconventional `Name` is authored and stays. Console line either way. The retarget pre-pass
  runs **before** the mint loop (the convention rename must not collide with a same-name mint).
- **R276.3** — Unpairable dead `Database.*` source ⇒ **warn and keep** (message names the query,
  the dead property, the empty-grid consequence, and the fix options). Never delete — "synchronize
  adds and modifies; it does not delete" (`:643`), and a transient state (property temporarily
  removed, module assembly missing) must not destroy authoring.
- **R276.4** — Ambiguous pairing (≥2 dead or ≥2 unclaimed for one entity) ⇒ refuse to guess:
  warn + mint, exactly today's behavior plus the warning.
- **R276.5** — `IndexName`/`UseProjection` are never cleared or re-derived (F276.1).
- **R276.6** — Fixed point: after any of the above, a second synchronize run is byte-identical.

## Cross-cutting acceptance criteria

1. Every new behavioral test is **red on `master`** before its fix milestone and green after
   (test-first; the PR squashes, so red commits never reach `master`).
