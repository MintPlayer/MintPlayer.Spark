# Issues #385, #387, #389 — AsDetail row affordances, and proving branch deletion

**Status:** Implemented in PR #391 — see [issue_385_387_389_plan.md](issue_385_387_389_plan.md) for
what landed, what did not, and why
**Issues:** [#385](https://github.com/MintPlayer/MintPlayer.Spark/issues/385) ·
[#387](https://github.com/MintPlayer/MintPlayer.Spark/issues/387) ·
[#389](https://github.com/MintPlayer/MintPlayer.Spark/issues/389)
(#385 and #389 have been retitled and carry these corrections at the top of their bodies)

## Why these three

Two of them are one defect seen from opposite ends. #385 is about the **supply** of
`asDetailPermissions()` — the record the client builds per AsDetail attribute. #387 adds a third
**consumer** of that same record. Shipping #387 alone would leave its new pipe failing closed for
exactly the types #385 is about, so the fix would read as a new bug.

#389 is unrelated in subject but shares the shape that produced all of them: **something shipped
without a path that exercises it.** It is included because it is the third such finding from #382 in
two days, it touches only `apps/CodeCoverage`, and it costs nothing in package surface.

`#386` (server-side row lifecycle) and `#388` (entity-library dependency split) are **out of scope** —
see the closing section. That is not a split of this unit of work; they are different units.

## What the issues get wrong

Every claim below was verified against the code. Recording them here because two of the three issues
would send an implementer at the wrong thing, and one of them sent *this PRD* at the wrong thing.

### #385 — right mechanism, unreachable user, understated symptom

- **The described caller does not exist.** #385 is written around a user with `New/{RowType}` but not
  `Query/{RowType}`. Across all four apps' `security.json` there are exactly three `New`-without-`Query`
  grants (`ReadEditNew/Car` ×2, `ReadEditNew/Person`), all on **root** persistent objects, all held by
  machine/module integration groups that never render a form. As written, #385 is latent.
- **The real trigger is broader and live now.** The catalogue miss needs only *no `Query` on the row
  type* — not the `New`-without-`Query` combination. Three of the six array-AsDetail row types in the
  workspace qualify: `OidcApplication.Claims` and `.Secrets` (apps/HR — administrators hold
  `QueryReadEditNewDelete/OidcApplication` and **nothing at all** on the row types) and
  `Build.Sessions` (apps/CodeCoverage).
- **The symptom is much larger than the headline.** The same catalogue miss also skips
  `asDetailTypes[attr.name]` (`spark-po-form.component.ts:289`), so `as-detail-columns.pipe.ts:8`
  returns `[]`. **The entire table renders with no columns** — no headers, rows reduced to a bare
  action cell. A missing Add button is a footnote on that. This is the same
  understated-symptom pattern as #384, in the same component.
- **Its suggested shortcut does not work.** The issue proposes calling `getPermissions` with
  `attr.asDetailType`. `ResolveEntityType` (`ModelLoader.cs:117-122`) handles Guid and Alias only,
  never `ClrType`, so that call returns the all-false payload. It is fixable in two lines, but it is
  not the fix the issue thinks it is.

### #387 — every claim true, one word wrong

All nine cited line numbers are exact, and the load-bearing claim holds: `canEdit` is already
computed (`GetPermissions.cs:39`), already on the wire (`entity-permissions.ts:11`), and already
fetched per AsDetail attribute (`spark-po-form.component.ts:292-293`). It is simply never read for
the row path. **No server change is required.**

The correction is terminological but changes the argument in the issue's favour: the title says the
server *"will refuse"* the edit. It does not — `EntityMapper.cs:714-725` **silently restores** the
stored row and `:750-757` raises a warning toast. The save succeeds and the user's edits vanish.
That is worse than a refusal, and a stronger reason to gate the affordance.

### #389 — the blocker is not the one named

- **"The feature itself is complete" is false.** `DeleteBranchOnPrClose` moved to `Repository` in
  #382, and `Repository` has never had an `Edit` right (`git log -S "Edit/Repository"` → zero
  commits). No controller, custom action or client code writes it. The feature is a complete
  *reader of a value nothing can produce*.
- **The permission rollout is probably moot.** `contents: write` exists only as prose in
  `docs/code-coverage/product-overview.md:288,292` — no manifest, no terraform, nothing
  machine-readable. The operator checked the installation page and found nothing pending, which is
  consistent with the App having had `contents: write` since it was created for source display and
  `push` events. Nothing in-repo can settle it; only the App's settings page can.
- **There is a worse defect than the one the issue names.** GitHub returns **404, not 403**, for
  refs a token may not write in some cases — so a permission failure lands in the `NotFoundException`
  arm and logs at *Information* as `"Branch ... was already gone"`. **A permission failure recorded
  as a success.** The repo already knows Octokit is unreliable here:
  `PullRequestCommentPublisher.cs:86-88` catches `ApiException when StatusCode == Forbidden` with the
  comment *"ForbiddenException for most 403s but a bare ApiException on some"*.
- The issue is otherwise accurate: all six arms exist, plus an unlisted **seventh** (null
  installation → warn and return), and the method is genuinely untested.

### A correction to this PRD's own first draft

This document initially claimed a fourth defect: that `Get.cs:26`'s comment ("Read implies Query at
rights-expansion time") was false and `List.cs:24-27`'s documented escape hatch therefore did not
exist. **That was wrong.** The implication is implemented in
`SparkRightImplications.cs:35-38`, composed into the grant index at
`ISecurityConfigurationLoader.cs:207-219`, and tested at `QueryWithoutReadTests.cs:126`
(`Read_implies_Query_so_a_bare_Read_grant_lists_and_reads`).

The error came from searching `SparkCombinedActions` and concluding from its absence there. That
type's own doc comment distinguishes the two: it expands one written name into the actions it **is**;
`SparkRightImplications` expands an action into what it **entails**. Recorded because the reasoning
failure — "not in the table I looked at, therefore not implemented" — is the same one that produced
#384's wrong repro, and because a PRD that silently dropped a claim it had made would leave the next
reader wondering whether it was checked.

## Requirements

**#385 — the supply**
- **FR1** — an AsDetail array whose row type the caller lacks `Query` on renders its **columns**. This
  is the headline, not the Add button.
- **FR2** — `getPermissions` resolves a type by `ClrType`, so the client can ask about a row type it
  cannot find in the catalogue.
- **FR3** — no widening of the `Query`-scoped catalogue in `List.cs`. Its scoping is deliberate and
  `spark-po-detail` depends on it for sub-query pruning.
- **FR4** — no new disclosure beyond what the parent's own `Read` already ships (see Design).

**#387 — the affordance**
- **FR5** — a `canEditDetailRow` pipe, **failing closed** like its two siblings.
- **FR6** — applied **read-only, never hidden**. A row the caller may not edit stays fully readable;
  hiding the inputs would hide the data.

**#389 — the proof**
- **FR7** — every arm of `DeleteHeadBranchIfEnabled` is tested: merged-only, flag respected, forks
  skipped, 404 → success, 422 → warn, catch-all never throws, **and** the seventh arm (null
  installation).
- **FR8** — a permission failure is diagnosable. A 403 (in either of Octokit's shapes) logs
  distinctly, and must not be reported as "already gone".
- **FR9** — the tests do not depend on the flag being settable. They seed the document directly.

**Release**
- **FR10** — every changed package is bumped, and #390's unpublished breadcrumb fix ships with it.
- **FR11** — CI fails when `libs/**` changes without a version bump.

## Design

### #385 — embed the row type's definition, pruned

The decisive finding is that **the server already ships the row type's full attribute schema under
the parent's right.** `EntityMapper.ScaffoldFrom` (`:388-404`) stamps `Name` and `ObjectTypeId` and
copies fourteen fields per attribute (`FromDefinition`, `:420-437`) — including validation `Rules` —
onto every row in `attr.Objects`, **with no permission check on the row type**. The gate was the
parent's `Read`.

So embedding the definition is not a new disclosure channel; it is the same channel, made
addressable when the collection happens to be empty. Add to `EntityTypeDefinition`:

```csharp
[JsonIgnore(Condition = JsonIgnoreCondition.WhenWritingNull)]
public EntityTypeDefinition[]? DetailTypes { get; set; }
```

⚠️ **Per-caller, never persisted** — modelled on `CanRead` (`:39-40`), whose remarks already document
this contract. `ModelSynchronizer` writes definitions back to disk, so a property that serialized by
default would round-trip nested copies into every model file.

Populated in `SubQueryPruner.PruneAsync` — per that file's own instruction at `:25-26`, *"If you add
a second pruner, extend this helper rather than writing another one"* — and chained from
`EntityTypes/Get.cs` and `List.cs`, which both already inject `IModelLoader`.

**Pruned, deliberately.** The embedded copy nulls `QueryType`, `IndexName`, `Queries` and `Alias`.
Those four are precisely what `docs/prd/PRD-SecurityAudit.md:66` names as the harvest surface —
*"query sources (`Database.*` / `Custom.*`), and projection structure"* — and the client needs none of
them for a detail table (`spark-po-form.component.html:204,241,270,394` read `attributes` and `id`).
With them gone the delta over what `attr.Objects` already carries is empty-collection schema plus
presentation metadata: **strictly less than the row data on the same response.** `CanRead` is set
honestly on the embedded copy so the client never guesses.

Needs a cycle guard and a depth bound — AsDetail-in-AsDetail is real (`EntityMapper.cs:439`
recurses), and a self-referential row type would loop.

**And fold in the two-line `ClrType` fallback** (FR2) in `GetPermissions.cs`, not in
`ResolveEntityType`. The latter has twelve call sites; widening it would make
`POST /spark/po/{ClrType}/…` route and creates a collision class where a CLR name equal to another
type's alias silently wins. `GetPermissions` answers unknown-type and fully-denied identically
(`:22-27`, deliberately, per audit M-1), so widening its key space opens no existence oracle.

⚠️ **The fallback must never ship alone.** By itself it replaces missing permissions with honest
all-false, which flips the Add button from *present and working* to *present and inert*, while the
table still has no columns. It is an adjunct to the embedding, not an alternative.

### #387 — a third pipe, applied read-only

`can-edit-detail-row.pipe.ts` mirroring its two siblings, fail-closed. Applied to the per-row pencil
(`spark-po-form.component.html:294`) and to the inline cell chain by extending its existing
`col.isReadOnly` test at `:110`, so a non-editable row falls through to the read-only span that is
already there. Client-only.

### #389 — tests, and an honest 403

The harness exists: `GitHubEventsRecipientTests.cs:85-110` already contains a purpose-built
`RecordingInstallationService` with `Deleted` and `DeleteThrows` — **read by nothing**. Its own
registration comment says it exists because otherwise "every test in this class fails at
construction — which is how the feature originally shipped, having no tests of its own."

Four preparatory changes, then the facts: add an `installation` node to the shared PR payload (it has
none, so every test would otherwise die on the seventh arm and prove nothing), parameterize
`action`/`merged`/`merged_at`/`state`, add a second repository JSON for the fork arm, and return the
recording service from `CreateRecipient` so a test can read it.

For FR8, add a `catch (ApiException ex) when (ex.StatusCode == Forbidden)` arm **above** the
`NotFoundException` arm, copying `PullRequestCommentPublisher.cs:86-88`. The 404-means-forbidden case
cannot be distinguished from a genuine 404 by status alone, so the `NotFoundException` message
changes from asserting "already gone" to naming both possibilities.

### Release

Pack is solution-wide and every version is written literally in each `.csproj`, so all **24** NuGet
projects move together. `--skip-duplicate` means an unbumped version is a **silent green no-op** on
both registries — which is exactly how #390 merged and published nothing.

| What | From | To |
|---|---|---|
| `<Version>` in all 24 `libs/**/*.csproj` | `10.0.0-preview.76` | `10.0.0-preview.77` |
| `libs/node_packages/ng-spark/package.json` | `22.14.0` | `22.15.0` |
| `libs/node_packages/ng-spark-auth/package.json` | `22.9.0` | unchanged |

Majors stay: still `net10.0`, still Angular 22. ng-spark-auth's `^22.8.0` peer range already admits
`22.15.0` and its own sources are untouched.

**FR11 — a CI guard.** `pull-request.yml` has no pack step and nothing compares the in-repo version
against the registry, so no signal existed. The guard added there fails a PR that touches `libs/**`
without a version change — a **diff** check rather than a registry query, so it needs no network or
credentials and answers the actionable question ("you changed a package and did not bump it") rather
than "master happens to equal what is published right now". It would have caught #390, where the sole
control was a review step that did not fire.

### Found while implementing: a per-caller value written into the shared model graph

Not in any issue, and worth recording as a defect class rather than an incident.
`EntityTypes/List.cs` assigned the per-caller `CanRead` onto the definition returned by
`PruneAsync`, under a comment asserting *"PruneAsync already copied the definition"*.

**It had not.** `PruneAsync` returns the **same singleton reference** whenever it prunes nothing —
both of its early returns — which is its documented contract and precisely the reason it is safe.
So for every entity type with no sub-queries, a per-caller boolean was written into `ModelLoader`'s
process-wide graph, and two concurrent callers with different rights could each serialize the
other's answer.

Fixed by copying explicitly when neither step did. The shape is what matters: the comment was not
describing the code, it was describing an *intention*, and it had been true of an earlier version.
That is the third defect in this cluster whose disguise was a confident comment — the first being
`EntityMapper`'s "embedded objects have no id" (#384), the second `ApiTokenActions` ignoring three
separate comments saying `In()` rather than `Contains` is load-bearing.

## Out of scope

- **#386 — server-side row lifecycle.** The three cherry-pickable commits are the easy 30%: ~577
  lines land cleanly, but the delete round-trip was never written, `ServerSideRowLifecycle` gates
  nothing yet, no client posts to the new endpoint, and the three commits contain **zero tests**.
  Realistically 20–30 files and 1200–2000 lines, and it changes `PersistentObject.SetValue` to mark
  `IsValueChanged` — an unaudited behaviour change feeding the save path.
- **#388 — entity-library dependency split.** Smaller in lines, far larger in blast radius: merging
  it **publishes a new package id to nuget.org**, permanently, from a pipeline whose PR check has no
  pack step. It also needs a coordinated bump across all 14 packages where getting it wrong makes
  `GetTypeByMetadataName` return null and silently switches off the index and translation generators.
- **Granting `Edit/Repository`** to make #389's flag settable. That belongs to the Account-PO work,
  and the naive grant is dangerous: `RepositoryActions.GetRowFilterAsync` returns the anonymous-tier
  filter for non-`Query` actions, so it would let every signed-in user edit every public repository.

## Risks — as they stand after implementation

- **R1 — the embedded definition discloses more than intended.** *Mitigated, partly by assertion.*
  The four type-level fields are pruned in code and pinned by
  `The_embedded_copy_carries_no_projection_or_query_surface`, which fails if anyone widens the copy.
  ⚠️ **The other half of the argument is still unmeasured:** that the residual is only
  empty-collection schema comes from reading `ScaffoldFrom`/`FromDefinition`, not from diffing a real
  payload (see the plan's S1). If the disclosure question reopens, that diff is the missing evidence,
  and the fallback remains per-app `Query.../{RowType}` grants rather than a framework change.
- **R2 — fail-closed pipes make #385's broken state look worse before it looks better.** *Measured
  and small.* S2 enumerated every array-AsDetail attribute: the fail-closed `canEdit` changes exactly
  **one** shipped screen — HR `Person.Jobs` becomes read-only for Viewers, who hold `Query`+`Read`
  and no `Edit`, which is the intended effect. For the three row types with no rights at all the
  table was already broken, so nothing regresses. Landing both in one PR was still right, but the
  risk was smaller than feared.
- **R3 — #389's tests pin only the reader half.** *Unchanged, and accepted.* They cannot
  regress-guard the missing write path; if someone later adds `Edit/Repository`, no test here would
  have caught its absence. Stated rather than solved.
- **R4 — the version bump is mechanical and silent when wrong.** *Mitigated but unproven.* All 24
  csproj moved together and `ng-spark` went to `22.15.0`; FR11's guard now fails a PR that touches
  `libs/**` without a bump. ⚠️ **The guard has never gone red**, and a check that has never failed is
  indistinguishable from one that cannot. Proving it needs a deliberate red commit and a CI round.
- **R5 — restoring the columns does not restore the buttons.** *New, discovered by S2.* A row type
  with no grants now yields an honest `canCreate`/`canEdit: false`, so HR's `OidcApplication.Claims`
  and `.Secrets` become readable but **not manageable**. That is correct per the rule that a type
  used only as an `asDetailType` still needs a type-level grant — but it means the framework fix
  alone does not give an administrator back the ability to edit them. Tracked as **M2b**, and
  deliberately not bundled: it is a security-configuration decision, not a framework one.
