# PRD — Issues #286–#290: local-credential auth is unconditional, server and client

**Status:** Planned — not yet started · targets `10.0.0-preview.58`
**Issues:** #286 · #287 · #288 · #289 · #290 — *to be filed; #285 is the highest existing number, issues and PRs share one sequence*
**PR:** one combined PR (owner's direction, 2026-08-20) — precedent: [issue_272_273_275_276_PRD.md](issue_272_273_275_276_PRD.md) → PR #278
**Branch:** `feat/issue-286-local-credential-opt-out`
**Plan:** [issue_286_287_288_289_290_plan.md](issue_286_287_288_289_290_plan.md) · **Guide:** [guide-authentication-schemes.md](guide-authentication-schemes.md) (updated in place)

Breaking changes allowed — no backward compatibility required (owner's standing direction). The default

Investigated by a four-agent census against this tree (`preview.57`, master @ `5464aa6`), 2026-08-20.

## Problem

A Spark application that authenticates **only** through an external identity provider — the motivating
case is Coverage, which allows GitHub sign-in and nothing else — still ships the complete
local-credential surface, on both tiers, with no way to turn it off.

The intended model is that **local credentials are a feature an application opts into, not a fixture of
the framework.** Today they are a fixture: calling `spark.AddAuthentication<TUser>()` at all — which an
external-only app must do, because that is where external login, `/me` and `/logout` come from —
unconditionally mounts password registration, password sign-in, and the full password-recovery family.

The abuse surface is not limited to `register`. `forgotPassword`, `resetPassword`, `confirmEmail` and
`resendConfirmationEmail` stay live and, taken together, remain an account-enumeration oracle and a
mail-bomb surface even in an application where no user can ever hold a password. Closing `register`
alone is not enough — the family is the unit.

## Origin

Reported by the owner, 2026-08-20, from first-hand consumer pain. It is independently corroborated by
the consumer's own security review: `C:\Repos\Coverage\docs\authorization-hardening.md` finding **C1**
(line 386) records that `POST /spark/auth/register` is mounted and anonymous with no email confirmation
configured, so a self-registered local account satisfies every `[Authorize]`, and that it *"stops short
of impersonating an owner only because Identity forces `UserName == email` and a GitHub login cannot
contain `@` — a string-format coincidence, not a control."* Its planned mitigation **M5.1** (line 588)
is a terminal 404-shadowing middleware, adopted explicitly because *"Spark has no opt-out — confirmed by
the owner."* This PRD exists to make that workaround unnecessary.

## Investigation findings (four-agent census, 2026-08-20)

### F1 — The entire ASP.NET Identity API is mounted whenever any authentication is configured

`libs/authorization/MintPlayer.Spark.Authorization/Extensions/SparkAuthenticationExtensions.cs:71-83`:

```csharp
var authGroup = endpoints.MapGroup("/spark/auth");           // :71
var identityConvention = authGroup.MapIdentityApi<TUser>();   // :83  <-- Microsoft's, all-or-nothing
```

`MapIdentityApi<TUser>()` is Microsoft's monolithic mapper. It contributes, verified against the shipped
runtime string table (`Microsoft.AspNetCore.App/10.0.11/Microsoft.AspNetCore.Identity.dll`):
`POST /register`, `POST /login`, `POST /refresh`, `GET /confirmEmail`, `POST /resendConfirmationEmail`,
`POST /forgotPassword`, `POST /resetPassword`, `POST /manage/2fa`, `GET|POST /manage/info`.

It is reached from `SparkBuilderExtensions.cs:47-70` (`AddAuthentication<TUser>`), which registers
`MapSparkIdentityApi<TUser>` unconditionally at `:66`. **There is no flag anywhere that skips it.** Grep
across `libs/` for `disableLocal|allowRegistration|localLogin|externalOnly|passwordless` returns nothing.
`AuthorizationOptions` (`SecurityFilePath`, `DefaultBehavior`, `CacheRights`, `CacheExpirationMinutes`,
`EnableHotReload`) has no endpoint toggle; `SparkIdentityProviderOptions` has none either.

**The only way to not mount them today is to not call `AddAuthentication<TUser>()` — which also gives up
`/me`, `/logout`, `/csrf-refresh`, external login, and the credential schemes.** That is not an option.

### F2 — `register` is a live enumeration oracle; the other four are uniform but not inert

Handlers are Microsoft's; Spark adds no override anywhere (verified by grep — Spark contributes only
antiforgery metadata). Measured behaviour of ASP.NET Core 10's `MapIdentityApi`:

| Endpoint | Known vs unknown email | Verdict |
|---|---|---|
| `POST /register` | **400** carrying `DuplicateUserName`/`DuplicateEmail` vs **200** empty | **Live, explicit oracle** |
| `POST /login` | 401 whose body is `SignInResult.ToString()` — `LockedOut` and `NotAllowed` are reachable **only for an existing user** | **Secondary oracle** |
| `POST /forgotPassword` | Uniform `Ok()`; sends only when `user is not null && IsEmailConfirmedAsync(user)` | Mitigated by design; **timing channel** + mail-bomb surface |
| `POST /resendConfirmationEmail` | `if (user is null) return Ok();` | Same |
| `POST /resetPassword` | Unknown user / unconfirmed email returns the *same* `InvalidToken` problem as a bad code | Mitigated; timing residue |
| `GET /confirmEmail` | Keyed on `userId` + signed code; unknown → `Unauthorized` | Weak — not an *email* enumeration path |

So the framing is correct and the census sharpens it: **closing `register` fixes the loud oracle but
leaves a timing side-channel and an unauthenticated mail-send trigger on four more endpoints.** Removing
the family closes all of it at once, and is the only mitigation that does.

### F3 — Nothing in the external-login flow depends on the local endpoints

`SparkAuthenticationExtensions.cs:181-193` — the external callback provisions inline against
`UserManager`/`SignInManager`: `new TUser()` → `SetUserNameAsync` → `SetEmailAsync` →
`user.EmailConfirmed = true` → `CreateAsync(user)` (no password) → `AddLoginAsync` → `SignInAsync`.
It does **not** call `/register` or `/confirmEmail`. Auto-provisioning is gated on an issuer-attested
`email_verified` / `urn:github:email_verified` claim (`:44+`, `:134-213`).

**Removing the local-credential routes cannot break GitHub login.** This was the largest design risk
going in, and it is retired.

### F4 — Service registration and route registration must not be conflated

`SparkAuthenticationExtensions.cs:45` calls `AddIdentityApiEndpoints<TUser>()`. Despite the name, that is
the **service** registration — it is what makes `UserManager`, `SignInManager` and the Bearer handler
resolvable, all of which the external callback at F3 uses. `MapIdentityApi` at `:83` is the **route**
registration. An opt-out must skip `:83` and keep `:45`.

Corollary: `MapSparkIdentityApi` (`:67-219`) is one indivisible callback registered at
`SparkBuilderExtensions.cs:66` — `MapIdentityApi`, the generated Spark endpoints (`/me`, `/logout`,
`/csrf-refresh`), and external login all ride it. **The method has to be split.**

### F5 — Client-side: five routes, always emitted, no way to omit one

`libs/node_packages/ng-spark-auth/routes/src/spark-auth-routes.ts:27-62` — `sparkAuthRoutes(config?)`
returns one wrapper route with five lazy children: `login`, `login/two-factor`, `register`,
`forgot-password`, `reset-password`. None carries a guard.

`SparkAuthRouteEntry = string | { path, component? }` (`models/src/auth-route-config.ts:3-11`) lets you
**rename a path or swap a component, but not omit one** — `resolveEntry` (`:8-25`) reads `undefined` as
"use the default". Every demo spreads `...sparkAuthRoutes()` verbatim, including WebhooksDemo
(`Demo/WebhooksDemo/.../app.routes.ts:11`), which is already effectively an external-only app and
therefore ships five unused local-credential pages today.

**There is no confirm-email and no resend-confirmation page** — exhaustive grep for
`confirmEmail|resendConfirmation|confirm-email|resend` across `libs/node_packages` + `Demo` returns
nothing. Those two are server-only (emailed links). So the client half of the family is: `login`,
`register`, `forgot-password`, `reset-password`, plus `two-factor`, which is reachable *only* from
`SparkLoginComponent`'s `RequiresTwoFactor` branch (`login/src/spark-login.component.ts:59-67`) and posts
to the same `/login` endpoint — it is local-credential-coupled, not universal.

### F6 — The real client-side blocker is three redirect targets, not the pages

`SparkAuthConfig` (`models/src/auth-config.ts:1-15`) is exactly three fields: `apiBasePath`,
`defaultRedirectUrl`, `loginUrl`. `loginUrl` is a **separate string** from the route-config `login` path —
two independent sources of truth for "where is the login page", both hardcoded to `/login`.

Three consumers navigate to `config.loginUrl` and would dead-end at a non-existent route, **with no type
error and no build failure**:

| Consumer | Location |
|---|---|
| `sparkAuthGuard` | `guards/src/spark-auth.guard.ts:15` |
| `sparkAuthInterceptor` (on 401) | `interceptors/src/spark-auth.interceptor.ts:26` |
| `SparkAuthBarComponent` unauthenticated branch | `auth-bar/src/spark-auth-bar.component.html:5` |

Conversely, the intra-family links are a **star centred on login** — every other page links back to
`login`, and `login` is the only page linking out to `register`/`forgot-password`/`two-factor`
(`login/...html:51,54`, `register/...html:64`, `forgot-password/...html:47`,
`reset-password/...html:11,60`, `two-factor/...html:61`). Because `SparkAuthRoutePaths` is
`Required<Record<keyof SparkAuthRouteConfig, string>>` (`models/src/auth-route-config.ts:13`) and the
templates dereference every key unguarded, dropping any *proper subset* dangles a `routerLink`.

**Dropping the whole family together dangles nothing, and needs no change to the `Required<...>` type.**
That is the decisive argument for making the family the unit rather than offering per-endpoint switches.

### F7 — There is no library UI for external sign-in, and no provider discovery

`login/src/spark-login.component.html:1-58` contains only the email/password form and the two sibling
links — **no provider buttons at all.** The only external-login code in the library is the service method
`SparkAuthService.loginWithProvider(provider, options)` (`core/src/spark-auth.service.ts:84-131`).

The one GitHub button in the repo is app-level: `Demo/WebhooksDemo/.../shell/shell.component.ts:54-57`
and `shell.component.html:20-24`. Coverage does the same, and its *only* current mitigation is cosmetic —
`shell.component.html` renders a GitHub button and no link to `/login` or `/register`, while both pages
stay reachable by typing the URL.

This inverts a risk we expected: removing the login route does **not** remove the GitHub button, because
the button was never there. But it means **an external-only app has no library-provided landing
experience** — every consumer hand-rolls it, and hardcodes the scheme name as a string literal
(`'GitHub'`). Turning off local credentials without shipping a replacement entry point leaves a hole.

### F8 — No server→client capability channel exists

There is no `/spark/auth/config`, no capabilities document, and no endpoint that enumerates registered
external schemes. The only startup fetches are `GET /spark/auth/me` (`core/src/spark-auth.service.ts:62`)
and `GET /spark/program-units`; neither carries feature flags. There is no `APP_INITIALIZER` /
`provideAppInitializer` / `ENVIRONMENT_INITIALIZER` anywhere in `libs` or `Demo`.

`provideSparkAuth` and `sparkAuthRoutes` are also **completely decoupled** — the routes function cannot
read `SPARK_AUTH_CONFIG` (it runs before injection exists). So a flag would have to be passed to both
call sites independently, and could silently drift from the server's actual configuration: server-side
removal alone leaves the Angular login page POSTing into 404s.

### F9 — `MintPlayer.Spark.IdentityProvider` is a second, independent local-credential surface

`libs/identity_provider/.../Extensions/SparkIdentityProviderExtensions.cs:112-113` maps
`GET|POST /connect/login` (handler `Endpoints/Login.cs`, resolving `SignInManager<>` reflectively at
`:81-92`), plus `/connect/two-factor`, `/connect/consent`, `/connect/applications` and the OIDC protocol
endpoints. **An opt-out on `AddAuthentication` would not touch any of it.** Shipping the flag without
covering `/connect/*` would produce a Spark app that reports local credentials disabled while still
serving a password form on another path.

### F10 — Rate limiting does not substitute for removal

`SparkBuilderRateLimiterExtensions.cs` — the limiter is **opt-in and off by default**; the framework
imposes no policy (its own audit finding L-3). None of the four demo apps calls `AddRateLimiter`, so
these endpoints are entirely unmetered there. When enabled, the default scope `["/spark", "/connect"]`
does cover the whole family via whole-segment `StartsWithSegments`, with no exemptions
(no `[DisableRateLimiting]` on any framework endpoint) — but it is **150 requests / 10 s per client IP in
one bucket shared across every metered prefix**, i.e. a generic browsing budget, not an auth-abuse
budget. At 900 req/min per IP, credential stuffing and enumeration fit comfortably; lockout is per-account
so it does not help against spraying. Coverage additionally clears `KnownNetworks`/`KnownProxies` (its own
finding C5), making `RemoteIpAddress` spoofable via `X-Forwarded-For` — which defeats the IP partition
outright. **An endpoint that cannot be reached is the only robust control.**

### F11 — Three live traps for anyone approaching this area

- `Configuration/ExternalLoginOptions.cs` (`Google`/`Microsoft`/`Facebook`/`Twitter`/`GitHub` →
  `{ClientId, ClientSecret}`) is **dead configuration** — nothing reads it. Providers are wired through
  the `configureProviders` callback instead. An obvious false lead for "how do I gate providers".
- `SPARK_OIDC_PROVIDERS`, `provideSparkOidcLogin` and `AddOidcLogin` **do not exist on master** (grep:
  zero hits in `libs/`). They are Identity-Provider-branch artifacts. Earlier notes referencing them as
  shipped API are wrong; external login today is `identity.AddGitHub(...)` →
  `/spark/auth/external-login` → `/spark/auth/external-login-callback`.
- The doc comment at `SparkAuthenticationExtensions.cs:62-65` misattributes `/logout` and `/me` to
  `MapIdentityApi`; they are Spark's own, source-generated via `MapSparkAuthEndpoints` (`:104`).

## Requirements

| | Requirement |
|---|---|
| **R1** | `spark.AddAuthentication<TUser>()` accepts a Spark-owned options object carrying a `LocalCredentials` mode. The default is today's behaviour, so an app that does not opt in is unaffected. |
| **R2** | `LocalCredentials` is a three-value enum — `Full`, `SignInOnly`, `Disabled` — **not** a set of per-endpoint booleans. Per-endpoint switches are an **error of design**, not a missing feature: F6 shows any proper subset dangles a client `routerLink`, and F2 shows any proper subset leaves an oracle. |
| **R3** | `Disabled` removes `register`, `login`, `refresh`, `confirmEmail`, `resendConfirmationEmail`, `forgotPassword`, `resetPassword` and `POST /manage/info` from the route table. They must be **absent** — a 404 produced by shadowing middleware is **not** acceptable, because the endpoints would still exist in the route table and in OpenAPI. |
| **R4** | `SignInOnly` removes `register` and `resendConfirmationEmail`, and keeps `login`, `refresh`, `forgotPassword`, `resetPassword`, `confirmEmail`. This serves admin-provisioned-accounts apps, which still need password recovery. |
| **R5** | `POST /manage/info` is treated as part of the local-credential family, not as universal account management: it changes the email an external binding was provisioned against (`SparkAuthenticationExtensions.cs:183-186`), desynchronizing the attested claim. `GET /manage/info` is retained in all modes. |
| **R6** | `/spark/auth/me`, `/spark/auth/logout`, `/spark/auth/csrf-refresh`, `/spark/auth/external-login` and `/spark/auth/external-login-callback` are mapped in **every** mode. `csrf-refresh` in particular is load-bearing — without it the XSRF cookie is not rotated after sign-in and every subsequent mutating call fails antiforgery (`core/src/spark-auth.service.ts:33,52,57`). |
| **R7** | `AddIdentityApiEndpoints<TUser>()` continues to run in every mode (F4) — the mode gates routes, never services. |
| **R8** | `MapSparkIdentityApi<TUser>` is split so that the `MapIdentityApi` call is separately gated from the generated Spark endpoints and external login (F4). |
| **R9** | A new anonymous `GET /spark/auth/capabilities` returns the local-credential mode and the list of registered external schemes (`{ scheme, displayName }`). It is the single source of truth the client reads; it leaks nothing, since it describes exactly what a sign-in page renders. |
| **R10** | `sparkAuthRoutes(config?)` accepts the same mode and omits the local-credential routes — **by not evaluating their `import()` call sites**, so the lazy chunks are not emitted, not merely unreachable. |
| **R11** | `SparkAuthRoutePaths` stays `Required<...>` and no secondary entry point is removed. Dropping the family as a unit makes this possible (F6); it keeps the change additive for the npm package. |
| **R12** | The guard, the interceptor and `SparkAuthBarComponent` must not dead-end when the login route is absent (F6). `loginUrl` becomes the single source of truth for "where does an unauthenticated user go", and an external-only app points it at its own or the library's sign-in landing route. |
| **R13** | The library ships a sign-in landing component that renders a button per external provider, driven by `/spark/auth/capabilities` (R9) rather than a hardcoded scheme string, so `Disabled` mode has a working entry point out of the box (F7). |
| **R14** | `MintPlayer.Spark.IdentityProvider` honours the same mode for `/connect/login` and `/connect/two-factor` (F9). A Spark app must not report local credentials disabled while serving a password form on another path. |
| **R15** | An unsatisfiable configuration **throws at startup**, matching `AddRateLimiter`'s philosophy: `LocalCredentials = Disabled` with **no** external provider registered leaves an application nobody can sign into, and is a configuration error, not a silent dead end. |
| **R16** | `Configuration/ExternalLoginOptions.cs` is deleted (F11) — dead configuration that reads as a provider gate. |
| **R17** | `docs/guide-authentication-schemes.md` documents the modes, the abuse surface each closes, and the external-only recipe; the README guide table row is updated. |

## Design

```
spark.AddAuthentication<SparkUser>(
    auth => auth.LocalCredentials = SparkLocalCredentials.Disabled,   // R1, R2
    configureProviders: identity => identity.AddGitHub(...))
        |
        +-- services: AddIdentityApiEndpoints<TUser>()  ---- always (R7)
        |
        +-- routes: MapSparkIdentityApi<TUser>()  ---- split (R8)
              +-- MapLocalCredentialApi<TUser>(mode)   <- gated (R3, R4, R5)
              +-- MapSparkAuthEndpoints()              <- always: /me /logout /csrf-refresh (R6)
              +-- external-login + callback            <- always (R6)
              +-- GET /spark/auth/capabilities         <- new, anonymous (R9)
                        |
                        v
   +-----------------------------------------------------------+
   |  { localCredentials: "Disabled",                           |
   |    externalProviders: [{ scheme: "GitHub", ... }] }         |
   +-----------------------------------------------------------+
                        |
   sparkAuthRoutes({ localCredentials: 'disabled' })  <- build-time (R10)
   SparkSignInComponent  <- runtime, renders provider buttons (R13)
```

The split is deliberate about **which tier owns which decision**. Route emission is a *build-time* choice
(R10) because omitting an `import()` is the only way to keep the chunk out of the output. Provider button
rendering is a *runtime* choice (R13) because the scheme list is server state. The capabilities endpoint
(R9) exists so the two cannot silently disagree — a mismatch between the build-time flag and the server
mode is detectable and reportable, where today it would be invisible (F8).

- **`SparkAuthenticationOptions`** — new, in `MintPlayer.Spark.Authorization/Configuration/`. One property
  for now (`LocalCredentials`). Named for the module, not the feature, so later auth-surface decisions have
  a home rather than accreting parameters on `AddAuthentication`.
- **`MapLocalCredentialApi<TUser>(mode)`** — wraps the `MapIdentityApi<TUser>()` call and publishes only
  the endpoints the mode allows. *How* it filters is the subject of spike S1.
- **`SparkSignInComponent`** — new secondary entry point `@mintplayer/ng-spark-auth/sign-in`, additive.

## Decisions

**D1 — A three-value enum, not per-endpoint booleans.** Rejected because both tiers punish proper
subsets: any subset leaves a dangling `routerLink` (F6) or a surviving oracle (F2). The enum encodes the
three configurations that are actually coherent. This is not a compromise on flexibility — it is the
removal of configurations that do not work.

**D2 — Absence, not shadowing.** Coverage's planned terminal-404 middleware (M5.1) is the right call for
a consumer that cannot change the framework, and the wrong one for the framework itself: the endpoints
would remain in the route table and in OpenAPI, so the surface would still be discoverable and still be
reachable by anything that bypasses the middleware ordering. A second `MapPost` on the same template is
not an alternative — it throws `AmbiguousMatchException` (500), it does not override.

**D3 — `refresh` goes with `Disabled`.** The external callback signs in on the **cookie**
(`ApplicationScheme`) via `SignInAsync` and never mints a bearer pair, so `/refresh` is only reachable
after `POST /login?useCookies=false`. With `login` gone it is dead weight. The Bearer credential scheme
stays registered (`SparkBuilderExtensions.cs:63`) — harmless, and unregistering it would be a wider
change than this PRD warrants; the guide will note it has no issuer in `Disabled` mode.

**D4 — Startup throw on `Disabled` with no external provider (R15).** The alternative — booting an
application nobody can sign into — is the exact class of silent misconfiguration `AddRateLimiter`
already refuses (empty `PathPrefixes`, bare `"/"`), and `SparkModuleRegistry.AddMiddleware` refuses for
an applied stage. Consistency here is free.

**D5 — Ship the sign-in landing component (R13) rather than documenting a recipe.** F7 shows every
consumer currently hand-rolls the button and hardcodes the scheme string. Turning off local credentials
without an entry point would convert a security problem into a usability problem. Pulling this complexity
downward is what makes `Disabled` a one-line change for the consumer rather than a small project.

**D6 — `/connect/*` is in scope (R14).** Tempting to defer, but a flag that claims to disable local
credentials while another package serves a password form is worse than no flag: it would be believed.

## Spikes

Two unknowns are load-bearing enough to settle before M1. Both are specified in the
[plan](issue_286_287_288_289_290_plan.md) with method, evidence and negative branch.

- **S1 — can the endpoints `MapIdentityApi<TUser>()` produces be selectively suppressed?** This is the
  premise of R3/R4 and the only genuine technical unknown in the PRD. Microsoft's mapper is all-or-nothing
  and exposes no removal API. Negative result → hand-write the retained endpoints against
  `SignInManager`/`UserManager` (a real cost: tracking upstream), which changes M1's shape but not the
  requirements.
- **S2 — does GitHub sign-in still work end to end with the family removed?** F3 says the coupling is
  absent by inspection; S2 pins it by execution, because "no HTTP coupling" and "works" are different
  claims and this is the one regression that would matter most.

## Migration (consumers)

- No action for existing apps. `LocalCredentials` defaults to `Full`, which is today's route set exactly.
- An external-only app adds the mode to `AddAuthentication`, passes the matching flag to
  `sparkAuthRoutes(...)`, and points `loginUrl` at a sign-in route (the library's `SparkSignInComponent`
  or its own).
- Coverage additionally **drops its planned M5.1 shadowing middleware** and can close finding C1 outright.
- Anyone referencing `ExternalLoginOptions` must remove the reference (R16) — it never did anything.

## Out of scope / follow-ups

- **A dedicated auth rate-limit policy.** F10 shows the shipped default is a browsing budget, not an
  auth-abuse budget, and that it is per-IP in a bucket shared with every other metered prefix. Real, and
  a separate concern from *whether the endpoint exists* — file separately. This PRD deliberately does not
  make removal depend on it, nor rate limiting a substitute for it.
- **Email confirmation enforcement.** There is no `IEmailSender` and no `SignIn.RequireConfirmedAccount`
  anywhere in `libs/`, so in `Full` mode `register` still yields an immediately usable account. Orthogonal
  to this change and unchanged by it, but worth its own issue — it is the other half of Coverage's C1.
- **Trust-boundary hardening of `X-Forwarded-For` handling.** Coverage's C5; a consumer configuration
  issue, though the framework could offer guidance.
- **Step-up 2FA for external identities.** `SparkTwoFactorComponent` is local-login-coupled today
  (F5); making it reachable from an external flow is new capability, not a fix.
- **Removing the Bearer credential scheme in `Disabled` mode** (D3) — deliberately left registered.
- **Collapsing `loginUrl` and the route-config `login` path into one source of truth** (F6). Tempting to
  fold in, but it is a breaking change to `SparkAuthConfig` that this PRD does not need: R12 is satisfied
  by making `loginUrl` authoritative for redirects.
