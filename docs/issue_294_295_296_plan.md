## Spikes

### S1 — runtime inference and the declared-weaker-than-actual case — **PASSED**

**Question.** The whole of decision D1 rests on a claim: that a method declared `IQueryable<T>` but returning `session.Query<T>()` yields an object for which `typeof(IRavenQueryable<T>).IsInstanceOfType(result)` is `true`. If RavenDB's LINQ provider returns something that does not implement `IRavenQueryable<T>` directly — a wrapper, or an internal type implementing only the non-generic interface — then runtime inference buys nothing over the signature and D1 collapses into the rejected fix.

**Method.** A throwaway xUnit test against the embedded store: declare an actions method returning `IQueryable<Employee>` whose body is `session.Query<Employee>()`, and one returning `Task<IQueryable<Employee>>` doing the same. Assert `IsInstanceOfType` for both, and assert the same for a genuinely in-memory `new[]{...}.AsQueryable()` (which must be `false`).

**Evidence.** `Passed! - Failed: 0, Passed: 1`. Runtime types, from the test's own output:

```
[S1] sync=Raven.Client.Documents.Linq.RavenQueryInspector`1[[...Thing, ...]]
[S1] async=Raven.Client.Documents.Linq.RavenQueryInspector`1[[...Thing, ...]]
[S1] inMemory=System.Linq.EnumerableQuery`1[[...Thing, ...]]
```

`RavenQueryInspector<T>` satisfies `typeof(IRavenQueryable<>).MakeGenericType(T).IsInstanceOfType(...)` for both the sync and the awaited shape, and `EnumerableQuery<T>` does not — so the boundary holds in both directions. Awaiting does not change what the object is.

**Negative result →** not taken. Had it failed, the fallback was non-generic `IRavenQueryable`, then the signature-based fix with F6's gap recorded as a follow-up.

**Disposition.** Promoted to a permanent pinning test, `tests/.../Services/RuntimeQueryableInferenceTests.cs`. It pins a fact about **RavenDB**, not about Spark: if a future upgrade returns a wrapper that no longer implements the generic interface, every async custom query silently loses its pushdown and nothing else in the suite would notice. Modelled on `SortCompanionRedirectTests`, which exists for the same reason.

### S2 — sort companions under a model gate — **PASSED (by construction)**

**Question.** `ResolveSortProperty` redirects a complex field to its `{Name}Sort` companion (#272/#276). The companion is a *computed persisted property*, not a model attribute — so if the `ShowedOn` check ran after redirection it would reject every companion-backed sort. D-B asserts the check must run on the **declared** name, before redirection. This needs confirming against a real companion, not reasoning.

**Answered by reading, and unambiguously.** `ResolveSortProperty` (`QueryExecutor.cs:828-835`):

```csharp
var companion = sortType.GetCachedProperty(requested + "Sort");
if (companion is null) return requested;
if (!companion.IsIgnoredForSparkModel()) return requested;
return companion.Name;
```

The companion is used **only when it is ignored for the Spark model** — so a sort companion is by construction *never* a model attribute. Confirmed by the existing fixture `SortCompanionRedirectTests.cs:65-66`, where `VCar.ModelSort` carries `[IgnoreProperty]`.

**Therefore D-B's ordering is not merely preferable, it is required:** a `ShowedOn` check placed after redirection would reject every companion-backed sort, because the companion it redirects to is not in the model at all. The check goes on the **declared** name.

A useful corollary falls out for free: because the companion is invisible to the model, the new gate also stops a client passing `ModelSort` directly as a sort column — a name that today resolves happily.

**Negative result →** not taken; companions do not appear in the model, so the simplification the negative branch described does not apply.

**Disposition.** Both assertions folded into `A12` in M4.

### One acceptance criterion re-pointed

**A18** ("row rules still run for a caller admitted via `Authenticated`") is verified structurally
rather than by a new integration test. `IAccessControl` answers only the type-level question and is
never consulted by `RowSecurity`; the two are independent services, and the ordering is fixed in
`DatabaseAccess.cs` (`:84` type-level, then `:106` row gate). Admitting a caller through a different
group cannot bypass a layer that does not consult group membership at all. Building a full
authorization-plus-row-rule integration host to assert this would test the pre-existing wiring, not
the change.
