# PRD — Controllers that obey Spark's rules, an honest group vocabulary, and opt-in auth routes

**Status:** Implemented — see the plan's Outcome section for deviations
**Issues:** [#298](https://github.com/MintPlayer/MintPlayer.Spark/issues/298), [#300](https://github.com/MintPlayer/MintPlayer.Spark/issues/300), [#301](https://github.com/MintPlayer/MintPlayer.Spark/issues/301), [#302](https://github.com/MintPlayer/MintPlayer.Spark/issues/302), [#303](https://github.com/MintPlayer/MintPlayer.Spark/issues/303)
**PR:** _(pending)_
**Branch:** `feat/issue-298-300-301-302-303-controllers-groups-routes`
**Plan:** `docs/issue_298_300_301_302_303_plan.md`
**Base:** `master` @ `2bfd542` (`10.0.0-preview.59`)
**Release:** `10.0.0-preview.60`, `@mintplayer/ng-spark-auth@23.0.0` (major — breaking)

---

## Problem

Five issues with one theme: **Spark's rules stop at Spark's own surface, and everything outside it is silently on its own.** An app's controllers authenticate and authorize but are not CSRF-checked. Row rules cannot be reused, so apps rewrite them. The group vocabulary cannot express "signed in" without also saying "the public internet". And the auth pages mount themselves whether or not anyone asked.

1. **#300** — Spark's antiforgery gate fires only on endpoints carrying `IAntiforgeryMetadata`. `AddControllers()` attaches none, and MVC's own `[ValidateAntiForgeryToken]` implements a *different* interface, so the obviously-correct MVC thing still yields nothing.
2. **#301** — row rules live on the actions class and are reachable only through the Spark pipeline, so an app with a mixed `/spark` + `/api` surface writes the same predicate two or three times and keeps it in step by hand.
3. **#298** — `Everyone` means "the public internet" and nothing at the point of writing says so; membership is matched by *display name*, which makes authorization depend on JSON key order.
4. **#302** — `SparkSignInComponent` has never been rendered in a browser.
5. **#303** — the demo hard-codes `loginWithProvider('GitHub')` and never renders the component at all; there is no way to customise a provider button.

Two further defects were found during investigation and are folded in (F13, F14).

## Origin

#300/#301 come from auditing `MintPlayer/CodeCoverage`, which has five cookie-authenticated mutating endpoints with no CSRF — including the one that mints upload tokens — and which hand-rolled `RepositoryVisibility`/`AccountVisibility` because one rule had to be written in three places. #298 came out of the same audit. #302/#303 are carry-overs from PR #291. The owner has since directed two deliberate breaking changes (D1, D2).

## Investigation findings

### F1 — `FleetWeb.cs`: what to borrow, what to reject

`C:\Repos\Fleet\Fleet\Service\FleetWeb.cs` (a Vidyano app, unrelated to Spark's `Demo/Fleet`) is 90 lines and 13 endpoints. Routing is **by method name** — `GetFuelCardPersonInfo` is served at `/api/GetFuelCardPersonInfo`; `[HttpGet]`/`[HttpPost]` are borrowed purely as verb constraints. It is **default-anonymous with opt-in auth**, and every gate is hand-written as the first line of the handler (`if (!args.IsValidSignature(token)) return Results.Unauthorized();`).

**Worth borrowing:** `args.Handle<TReq,TRes>(handler, OnError)` runs a fail-closed seven-step chain — token present, body deserializes, key well-formed, signature verifies, client resolves, caller on the allow-list, identity active — and hands the handler a verified caller plus an open session. **One call the handler cannot run without.** That is the shape #300/#301 need.

**Right to reject** (as the owner directed): routing by method name (a C# rename breaks a public URL; no route parameters, no versioning); `CustomApiControllerBase` re-declaring ~40 `ControllerBase` members plus a parallel Swagger attribute family; a singleton controller; and above all **default-anonymous with per-handler opt-in auth**, which is literally #300 in another framework.

### F2 — nothing in `UseSpark()` is path-scoped

`SparkMiddleware.cs:176-308`. No `UseWhen`, no `MapWhen`, no `PathString` test. Consequence: **an app's controllers already sit behind every one of Spark's global middlewares** — they authenticate, they authorize, they receive an `XSRF-TOKEN` cookie (`:275-294`). The only thing they do not get is the CSRF *check*, because that one is metadata-gated (`:215-237`).

### F3 — the gate inventory a controller must opt into

Tracing `GET /spark/persistentobject/{type}/{id}` through `DatabaseAccess.cs:79`:

| Gate | Anchor |
|---|---|
| Type-level right `EnsureAuthorizedAsync("Read", name)` | `:84` |
| Collection guard `BelongsToAuthorizedCollection` | `:99-100` |
| Row read gate `IsAllowedAsync(type, "Read", entity)` | `:105-106` → **404**, not 403 |
| Per-viewer redaction `RedactAsync` | `:114` |
| Per-row `can` block (type right **AND** row rule) | `:122-131` |

The grid is different in kind: `QueryExecutor.cs:186` `ComposeRowFilterAsync` (pushdown, position load-bearing), `:211` `FilterAsync` (**the actual gate**; pushdown is only an optimization), `:221` `RedactAsync`.

Today an app can reach exactly **one** of these — `IPermissionService`.

### F4 — `IRowSecurity` is internal, and its reusable core is private

| Type | Declared |
|---|---|
| `IRowSecurity` | `internal` — `RowSecurity.cs:34` |
| `ResolveEffectiveRuleAsync` (the reusable core) | `private` — `:439` |
| `ICollectionGuard` | `internal` — `CollectionGuard.cs:20` |
| `IPermissionService`, `IAccessControl`, `IActionsResolver` | public |

`InternalsVisibleTo` covers only the test project. **No consuming app is on any IVT list.**

### F5 — the row hooks are deliberately absent from the public actions interface

`GetRowFilterAsync`, `IsAllowedAsync`, `GetProtectedAttributesAsync` all carry `[NoInterfaceMember]` (`DefaultPersistentObjectActions.cs:55, 152, 224`) and are **not on `IPersistentObjectActions<T>`**. So even the public `IActionsResolver` returns something that cannot be asked for a row rule; `RowSecurity` reaches them by reflection (`:548-554`).

Downcasting to `DefaultPersistentObjectActions<T>` is **not** a safe workaround: `ActionsResolver.cs:47-50` supports an app registering a custom `IPersistentObjectActions<T>` that does not derive from it, and a downcast would silently report "no rule" — a silent open door.

### F6 — `GetRowFilterAsync` returning `null` means allow-all, and the filter is only half the rule

`DefaultPersistentObjectActions.cs:186-188`. So `query.Where(await rule.FilterAsync("Query") ?? (x => false))` **inverts** the rule.

Worse: `ResolveEffectiveRuleAsync` (`:460-471`) ANDs the filter with the per-row `IsAllowedAsync` hook. **A type that overrides only `IsAllowedAsync` returns `null` from `GetRowFilterAsync`** — so a caller consuming only the filter is *completely unfiltered*. This is why the shape suggested in #301 (`IRowRule<T>.FilterAsync(action)`) is the one shape not to ship.

### F7 — the per-request memo exists to protect a hard limit

`RowSecurity.cs:119-120` holds hook invocations to one per `(type, action)` per request because Raven's `MaxNumberOfRequestsPerSession` defaults to 30 (`:365-397`). `DefaultPersistentObjectActions.cs:203-212` documents this to hook authors as a contract. A new public service with its own memo would **double** invocations whenever a controller and the pipeline both ask.

### F8 — MVC's antiforgery attributes implement a different interface

`[ValidateAntiForgeryToken]` / `[AutoValidateAntiforgeryToken]` live in `Mvc.ViewFeatures` and implement `IAntiforgeryPolicy`/`IFilterMetadata`. Spark's gate reads `IAntiforgeryMetadata` from `Http.Abstractions`. They do not meet. Repo-wide grep for `ValidateAntiForgeryToken` returns **zero product hits**.

`Microsoft.AspNetCore.Antiforgery.RequireAntiforgeryTokenAttribute` *is* public framework API and *does* work on a controller action today — **that is an existing one-line workaround worth documenting immediately**, independent of this work.

### F9 — no `[Authorize]` interop exists at all

Zero repo-wide hits for `IAuthorizationPolicyProvider`, `AuthorizationHandler`, `IAuthorizationRequirement`, `AddPolicy(`, `RequireAuthorization(`. `SparkMiddleware.cs:46` calls a bare `AddAuthorization()` registering no policies. So `[Authorize(Policy = "Administrators")]` **throws at request time**.

Two things work by accident: bare `[Authorize]`, and `[Authorize(Roles = "…")]` **iff** the group is stored as an ASP.NET Identity role — because `ClaimTypes.Role` is on the group-claim list. A group stored as a `group` claim (the shape the E2E fixtures, the identity provider, and module certificates all use) is invisible to `RequireRole`. **That inconsistency is itself a trap**: anyone testing against a role-shaped fixture concludes interop already works.

### F10 — well-known groups are matched by display name, and display name is file-order-dependent

`AccessControlService.cs:66-72` resolves `Everyone`/`Authenticated` via `TranslatedString.GetDefaultValue()`, which is:

```csharp
public string GetDefaultValue() => Translations.Values.FirstOrDefault() ?? string.Empty;
```

**First translation in file order, not "the English one".** So `{"en":"Everyone","nl":"Iedereen"}` matches and `{"nl":"Iedereen","en":"Everyone"}` does not. Meanwhile `ResolveGroupIds` (`:144-155`) matches claim-derived names against **any** translation — two different matching rules, sixty lines apart. Reordering JSON keys silently changes authorization; two groups sharing a first translation resolve arbitrarily; renaming a group for the UI silently un-declares a well-known group.

### F11 — the reserved names are not reserved (corrects a claim shipped in #304)

`AccessControlService.cs:51-54` states *"an external identity provider cannot assert this group name for itself."* **That is false as implemented.** `ResolveGroupIds` matches any provider-returned name against any translation, so a principal carrying `group: "Authenticated"` resolves the well-known id at step 1 and never reaches the `IsAuthenticated` gate at `:90`.

Inert with the shipped `ClaimsGroupMembershipProvider` (it returns nothing for an unauthenticated caller), so not exploitable today — but any custom `IGroupMembershipProvider` breaks it silently, and the guarantee is enforced nowhere. **This comment was written and merged in PR #306; it must be corrected in code, not just in prose.**

### F12 — `QueryRead` expands invisibly, and `canQuery` is missing

`CombinedActions` (`AccessControlService.cs:22-34`) maps `QueryRead → Query, Read` and nine other combinations. Expansion is **grant-only** (`:125` filters `!r.IsDenied`), so a *denial* written `EditNewDelete/Person` denies nothing — symmetric syntax, asymmetric semantics, undocumented.

And `GET /spark/permissions/{type}` (`GetPermissions.cs:26-29`) reports `canRead/canCreate/canEdit/canDelete` — **there is no `canQuery`**. The one right `QueryRead` adds beyond a reader's expectation is precisely the one introspection never mentions.

### F13 — auth routes mount by default

`spark-auth-routes.ts:38` — `const mode = config?.localCredentials ?? 'full'`. The pages are mounted unless the developer explicitly opts *out*. The owner's recollection was the opposite, and the opposite is what it should be.

Note the mode literals differ across the wire: Angular uses `'full' | 'sign-in-only' | 'disabled'` (`auth-route-config.ts:13`), the server/capabilities enum uses `Full | SignInOnly | Disabled`.

### F14 — route absence is already tested; #302 as filed is largely redundant

`spark-auth-routes.spec.ts` asserts route absence **per mode, by exact array equality** (not `toContain`) for all three modes. `LocalCredentialModeTests` asserts over `EndpointDataSource` — deliberately, because *"a 404 would pass just as happily against shadowing middleware"* (`:25-31`). `OidcLocalCredentialModeTests` does the same for `/connect/*`.

**Playwright: nothing.** The E2E project drives Fleet only, in `full` mode, and asserts the *positive* direction (`SmokeTests.cs:70-84`).

So the reachability half of #302 is covered twice, at levels stronger than a browser 404. What is genuinely uncovered is **rendering** — and `bs-card`/`bs-spinner`/`bs-alert` are web-component-backed, so jsdom "renders" them without proving anything.

A stronger guarantee than any test can give already exists and is **unasserted**: in `disabled` mode the excluded pages are not in the bundle at all, because the `import()` call sites sit inside the mode branches (`spark-auth-routes.ts:29-32`).

### F15 — content projection is unreachable on a routed component

`SparkSignInComponent` is mounted via `loadComponent` (`spark-auth-routes.ts:55-56`). **The router instantiates a component with no projected content**, so `<ng-content>` and `contentChild` see nothing on the default route. Any projection design is reachable only if the consumer *hosts* the component — which `SparkAuthRouteEntry`'s `{ path, component }` form already allows (`auth-route-config.ts:3`, honoured at `:17-20`).

### F16 — `ng-spark` already has a template-projection idiom

`spark-po-detail.component.ts:57-58` and `spark-query-list.component.ts:57` expose `input<TemplateRef<Ctx>>` consumed via `*ngTemplateOutlet`. No consumer passes either today, so there is no migration debt — but the idiom is established, and the owner uses `*ngTemplateOutlet` routinely.

### F17 — CodeCoverage confirms both #300 and #301, and #301 more subtly than filed

Five cookie-authenticated mutating endpoints with no CSRF: `MeController.cs:82`, `RepoSettingsController.cs:25` (**mints the badge token**), `:47`, `TokensController.cs:54`, `:142`. `UploadsController` is correctly exempt — `[Authorize(AuthenticationSchemes = "ApiToken,GitHubOidc")]`, both non-ambient.

`TokensController.cs:16` documents protection it does not have:

> *"Upload-token management for the signed-in user (cookie auth + XSRF via the Spark middleware)."*

A careful author read the framework, concluded the middleware covered them, and wrote it down. It did not.

For #301, the app **already centralised the predicate** (`RepositoryVisibility.cs`) — so the residual duplication is not the predicate but the *plumbing*: knowing it must be applied, keeping the expression form and the compiled form in agreement (they wrote `RepositoryVisibilityParityTests` for exactly this), remembering there is a second half, and reproducing redaction. **That is the strongest argument for `ApplyAsync` over `FilterAsync`**: the app that did the centralisation *correctly* still needed a parity test, because a bare predicate has two evaluation modes that can drift.

### F18 — `MapControllers()` is undetectable at runtime but trivially detectable at compile time

Two different claims that are easy to conflate.

**At runtime:** by the time `UseSpark()` executes, the app has already called `MapControllers()` on its own `IEndpointRouteBuilder`, and the resulting endpoints are indistinguishable from any other. Nothing Spark can inspect says whether the app opted into Spark's rules. This is the same limitation `SparkBuilderRateLimiterExtensions.cs:42-58` documents for `UseRateLimiter`.

**At compile time:** `endpoints.MapControllers()` is an ordinary `InvocationExpressionSyntax` in the app's own source, resolvable to `ControllerEndpointRouteBuilderExtensions.MapControllers` by symbol. An analyzer sees it directly. SPARK004 (`MiddlewareOrderAnalyzer.cs:52-63`) is the existing precedent for exactly this shape of rule.

Crucially the check needs **no cross-file or compilation-end analysis**: `spark.UseControllers()` calls `MapControllers()` inside *Spark's own assembly*, which the consuming app's compilation never analyses. So "any `MapControllers()` in this compilation" is already the right predicate, evaluated one syntax node at a time.

The analyzer infrastructure exists — `libs/source_generators/MintPlayer.Spark.SourceGenerators/Diagnostics/` holds SPARK001-SPARK009. Note the measured constraint recorded there: **a `CodeFixProvider` must live in its own assembly** or it breaks the entire generator suite via `ReflectionTypeLoadException` (#270). A code fix for this rule is desirable ("replace with `spark.UseControllers()`") but must be budgeted against that.

## Design

### D-A — antiforgery: invert the default, do not stamp metadata

The owner's own statement — that these endpoints "may as well reuse `MapGet`, `MapPost`" — **rules out the stamping approach in #300**. No MVC convention reaches a minimal API the app wrote. Any metadata-based answer covers half the surface and leaves the rest silently open, which is the failure mode the issue is about.

Instead, change the gate's default inside a scope Spark owns (`SparkMiddleware.cs:215-237`):

```csharp
var metadata = endpoint?.Metadata.GetMetadata<IAntiforgeryMetadata>();
var required = metadata switch
{
    { RequiresValidation: true }  => true,   // explicit opt-in wins  (today's stamps)
    { RequiresValidation: false } => false,  // explicit opt-out wins (DisableAntiforgery)
    null => options.RequireAntiforgery
            && MatchesAnyPrefix(context.Request.Path, options.PathPrefixes)
            && HasAmbientCredential(context),
};
```

`PathPrefixes` mirrors `SparkRateLimiterOptions.PathPrefixes` — an idiom the codebase already has. `HasAmbientCredential` keeps genuinely-anonymous POST endpoints working; a CSRF check on a request with no ambient credential protects nothing.

**The gate is idempotent** (unlike `UseRateLimiter`): `ValidateRequestAsync` is a pure header-vs-cookie read, consumes nothing, and `IFormFeature` caches the parsed form.

### D-B — `ISparkRowRule<T>`: one deep call, both halves

```csharp
public interface ISparkRowRule<T> where T : class
{
    /// Pushes down where translatable, materializes, then post-filters with the compiled
    /// predicate AND the per-row hook. One call; the caller cannot forget half the rule.
    Task<IReadOnlyList<T>> ApplyAsync(IQueryable<T> query, string action, CancellationToken ct = default);

    Task<bool> IsAllowedAsync(string action, T entity, CancellationToken ct = default);
    Task<IReadOnlyCollection<string>?> GetProtectedAttributesAsync(string action, T entity, CancellationToken ct = default);

    /// Escape hatch for callers that must compose themselves (paging, aggregation, facets).
    /// null means UNRESTRICTED — never coalesce to `x => false`.
    Task<Expression<Func<T, bool>>?> GetFilterAsync(string action, CancellationToken ct = default);
}
```

`ApplyAsync` is what the docs promote; `GetFilterAsync` is the sharp tool. It delegates into the **same scoped `RowSecurity`** so the memo is shared (F7).

Reaching the hooks reflection-free requires removing `[NoInterfaceMember]` from the three row hooks so they land on `IPersistentObjectActions<T>` — a deliberate breaking change for hand-written implementers.

### D-C — `[SparkAuthorize]` via `IAuthorizationRequirementData`

.NET 10 provides `IAuthorizationRequirementData`, so no policy provider and no policy-name strings are needed:

```csharp
[SparkAuthorize("Read", nameof(Repository))]   // → IAccessControl.IsAllowedAsync("Read/Repository")
[SparkAuthorize(Group = "Administrators")]     // → IGroupMembershipProvider
```

**The right form is primary, not the group form**: `security.json` is the product's authorization model, a right lets an operator change access without a redeploy, and it is *the same string* the pipeline checks — so a controller and a persistent-object endpoint provably agree.

### D-D — group vocabulary: `anonymous` + `authenticated`, declared by id

```json
{
  "wellKnown": {
    "anonymous":     "00000000-0000-0000-0000-000000000000",
    "authenticated": "a1b2c3d4-0000-0000-0000-00000000000f"
  },
  "groups": {
    "00000000-0000-0000-0000-000000000000": { "nl": "Anoniem", "en": "Anonymous" },
    "a1b2c3d4-0000-0000-0000-00000000000f": { "en": "Signed-in users" }
  }
}
```

An explicit id map fixes localization, renaming, duplicates, case, **and** F11 (reserved ids are excluded from `ResolveGroupIds`, so no claim can assert them) in one move. It follows the shape `GroupComments` already establishes, so no existing field changes type.

**`Everyone` is deleted rather than renamed.** Renaming keeps one token meaning "the public internet" and hopes a better word carries the warning; deleting it forces the author to type `anonymous`, which is self-documenting at the point of writing. "All callers" becomes two grants — verbose on purpose.

### D-E — `sparkAuthRoutes` becomes composable feature functions

```ts
sparkAuthRoutes(
  withLocalLogin(),
  withExternalLogin(githubProvider(), facebookProvider()),
)
```

No features passed ⇒ nothing mounted. Opt-in is enforced by construction rather than by a flag, matching `provideHttpClient(withFetch())` and `provideRouter(withComponentInputBinding())`.

`withLocalLogin()` mounts login/two-factor/forgot-password/reset-password; a `withRegistration()` feature mounts register; `withExternalLogin(...)` mounts the sign-in landing page.

**`githubProvider()` decorates, it does not declare.** The server remains authoritative over which providers exist (`GET /spark/auth/capabilities`); a provider feature supplies *presentation* — icon, label, ordering — keyed by scheme. A scheme the server reports with no matching declaration falls back to the default button, so a server-side addition never yields a blank page.

### D-F — provider customisation by `*ngTemplateOutlet`

Per F16 and the owner's stated preference, an `input<TemplateRef<SparkProviderButtonContext>>` consumed via `*ngTemplateOutlet`, matching `po-detail`/`query-list`:

```ts
readonly providerTemplate = input<TemplateRef<SparkProviderButtonContext> | null>(null);
```

The context carries `{ $implicit: provider, signIn: () => void }`. **Passing the closure is the point**: the consumer never touches `provider.scheme`, so #303's failure mode becomes unreachable by construction, and busy-state/`returnUrl`/popup-vs-redirect can move behind it later without a consumer-facing change.

Per F15 this is reachable only when the consumer hosts the component, via `signIn: { path, component }`. **The PRD states this explicitly so the API does not ship unreachable.**

## Decisions

**D1 — auth routes become opt-in; the server default becomes `Disabled`.** Owner directive, breaking changes accepted ("still in preview, nothing is actually released yet"). Both halves move together so the client and server defaults agree; leaving the server at `Full` would default the two to opposite postures, which is exactly the mismatch `SparkSignInComponent`'s dev-mode warning exists to catch.

**D2 — the group vocabulary is a clean break, not a shim.** Owner directive. A compatibility shim that kept treating a display-name `Everyone` as anonymous-inclusive would preserve exactly the invisibility #298 is about. Instead it fails startup with a two-line migration instruction.

**D3 — invert the antiforgery default rather than stamp metadata.** Rejected: `IApplicationModelConvention` (MVC only — misses `MapPost`), endpoint conventions on `MapControllers()` (same limit, plus it must be called), `MatcherPolicy` (selects among endpoints; not a validation seam). See D-A.

**D4 — ship `ApplyAsync`, not `FilterAsync`.** The shape suggested in #301 is the one shape not to ship: `null` means allow-all, and a type overriding only `IsAllowedAsync` returns `null`, leaving such a caller completely unfiltered (F6). CodeCoverage needed a parity test precisely because a bare predicate has two evaluation modes that drift (F17).

**D5 — `spark.UseControllers()` is the supported entry point, and a raw `MapControllers()` is diagnosed.** Owner directive, and it corrects an error in the investigation.

The investigation concluded "a library cannot detect the call, so a prohibition is unenforceable advice." That reasoning is sound **at runtime** — by the time `UseSpark()` executes, `MapControllers()` has already run on the app's own builder and left no trace Spark can inspect, which is the same argument `SparkBuilderRateLimiterExtensions.cs:42-58` documents for `UseRateLimiter`. It is **false at compile time**: `endpoints.MapControllers()` is an ordinary invocation in the app's own source, and an analyzer sees it directly. That is precisely what SPARK004 already does for middleware ordering.

So the rule ships as a **diagnostic**, not as prose:

- `spark.UseControllers()` is the documented way to mount controllers under Spark's rules.
- A bare `MapControllers()` in a project referencing Spark raises a warning saying it bypasses Spark's authorization and antiforgery rules, and naming the replacement.
- The check is **single-file and syntactic**. No cross-file analysis is needed, because `spark.UseControllers()` calls `MapControllers()` inside *Spark's* assembly, which the app's compilation never analyses. An app that deliberately wants the raw call suppresses the diagnostic — a deliberate, reviewable act rather than a silent one.

This is strictly better than wrapping: wrapping leaves an app that never heard of `spark.UseControllers()` silently outside the rules, which is the exact shape of #300 itself.

**D6 — the right form of `[SparkAuthorize]` is primary, the group form secondary.** Groups are an implementation detail of who holds a right; rights are the product's model and are changeable without a redeploy.

**D7 — do not split `Query` and `Read`.** They are *already* independently grantable — write `Query/Person` alone and the grid works while the by-id load refuses. `QueryRead` merely bundles them invisibly. Splitting would churn every `security.json` for no security gain once the expansion is documented and `canQuery` is reported.

**D8 — a startup check, not an analyzer, for the anonymous surface.** `security.json` is not in the compilation, is not the file that ships, and is hot-reloadable. This is the mirror image of SPARK004, which exists because middleware order is undetectable at *runtime*. Here the posture is trivially computable at runtime and barely computable at build time. A `--spark-verify-security` CI gate mirroring `--spark-verify-model` is what makes an anonymous grant reviewable in a diff.

**D9 — rescope #302 from reachability to rendering.** Per F14 the reachability half is already asserted twice, more strongly. Building a Playwright test to prove a 404 would restate existing assertions at the cost of ~300 lines of fixture and a second `dotnet run`. What ships instead: navigation-level absence tests at the vitest tier (~30 lines), and a bundle-exclusion check. **Owner confirmed the Playwright host is not wanted** — #302 closes on those, and the browser render stays a manual check.

**D10 — `githubProvider()` decorates rather than declares.** Letting the client declare providers would reintroduce the string-literal mismatch `/spark/auth/capabilities` exists to prevent.

## Migration

**This release is breaking on four axes.** Release notes lead with them.

1. **`sparkAuthRoutes()` → feature functions.** Every consumer's call site changes. `@mintplayer/ng-spark-auth` goes to **23.0.0**.
2. **`SparkLocalCredentials` defaults to `Disabled`.** An app wanting local credentials must now say so. An app with neither local credentials nor an external provider **fails startup** — which is correct, and loud.
3. **`security.json`: `Everyone` is gone.** Every grant to it must become an explicit `anonymous` and/or `authenticated` grant. ⚠️ **`Everyone` was the floor for every caller, so moving a grant to `anonymous` alone narrows it** — Fleet grants `QueryRead/Company` through `Everyone` and nowhere else, so a signed-in Fleet user would lose Company access. The mechanical, behaviour-preserving migration is **one grant becomes two**.
4. **`IPersistentObjectActions<T>` gains three members.** Breaks hand-written implementers; classes deriving from `DefaultPersistentObjectActions<T>` are unaffected.

Release-note text, ready to use:

> Every right you granted to `Everyone` was granted to the public internet. Decide, per right, whether that was intended. If it was, move it to `anonymous`. If it was not, move it to `authenticated` — **do not delete it**, because type-level rights gate row rules and a deleted grant denies signed-in users too.

`RequireAntiforgery` defaults **off** this preview and on at the next major, with a warning-only mode logging what *would* have been rejected — otherwise every existing app's controller writes start 400ing on upgrade.
