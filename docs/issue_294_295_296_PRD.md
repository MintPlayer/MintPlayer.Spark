# PRD — First-class async custom queries, the sort-column disclosure oracle, and external sign-in provisioning

**Status:** In progress
**Issues:** [#294](https://github.com/MintPlayer/MintPlayer.Spark/issues/294), [#295](https://github.com/MintPlayer/MintPlayer.Spark/issues/295), [#296](https://github.com/MintPlayer/MintPlayer.Spark/issues/296)

**Branch:** `feat/issue-294-295-296-first-class-async-queries`
**Plan:** `docs/issue_294_295_296_plan.md`
**Guides touched:** `docs/guide-queries-and-sorting.md`, `docs/guide-authentication-schemes.md`
**Release:** `10.0.0-preview.59`, `@mintplayer/ng-spark-auth@22.2.1`

## Problem

Three defects, found by three separate investigations, that share one property: **the test suite is green and the product is wrong.** None of them is visible from a passing build, and two of them are only visible from outside the repository.

1. **#294 — an `async` custom query silently loses six capabilities** its identical sync twin keeps: declared `sortColumns`, header-click sorting, row-filter pushdown, search pushdown, index projection, and `.Include()`. A declared `sortColumns` on an async query is accepted, ignored, and never warned about.
2. **#295 — `?sortColumns=` is a disclosure oracle.** Sorting resolves any CLR property by reflection, without consulting the model. An attribute that redaction nulls, or that `showedOn` excludes from the query surface, remains fully usable as a sort key — and ordering by a hidden value is binary-searchable.
3. **#296 — external sign-in cannot provision an account.** `AddGitHub` requests no OAuth scope, but the provisioning gate requires an issuer-attested email, which is obtainable only with `user:email`. The two are mutually unsatisfiable, and the failing HTTP call is swallowed without a log.

## Origin

#294 was filed by the `MintPlayer/CodeCoverage` consumer session. #295 and #296 were found by the investigations commissioned for this PRD — #295 while auditing Coverage's data security against its four stated requirements, #296 while assessing what the stub-based external-login spike from PR #291 structurally could not cover.

#296 is a direct consequence of shipping `SparkLocalCredentials.Disabled` in preview.58: in `Disabled` mode there are no local accounts to fall back on, so a provisioning failure means **nobody can sign in at all**.

## Investigation findings

### F1 — `!isAsync` is the only thing suppressing the capability flags

`libs/spark/MintPlayer.Spark/Services/QueryExecutor.cs:418-432`. `returnType` is unwrapped from `Task<T>` at `:420-424`, so by the time the flags are computed both assignability tests would answer `true` on their own:

```csharp
:423    returnType = returnType.GetGenericArguments()[0];
...
:431    var isRavenQueryable = !isAsync && typeof(IRavenQueryable<>).MakeGenericType(elementType).IsAssignableFrom(returnType);
:432    var isQueryable = !isAsync && typeof(IQueryable).IsAssignableFrom(returnType);
```

The runtime value is unwrapped too (`:281-286`), *before* any gated step runs. So the guard is suppressing capabilities for values that are, by then, perfectly ordinary queryables.

### F2 — the guard was incidental, not load-bearing

`git log -L 425,435` on this file returns exactly two commits.

- **`45bb9e2`** (#41, "Custom query support with Database/Custom source routing") introduced the flags with **no** `isAsync` notion at all.
- **`0132f55`** (#84, "Split webhook handlers, add-to-board logic, and sync columns") added the await block **and** the `!isAsync &&` prefix in a single hunk, inside a large multi-topic webhooks PR.

The only async consumer that commit was written for is `Task<IEnumerable<ProjectColumn>>` — a shape for which both flags evaluate `false` regardless. No issue, test, or commit message justifies the guard, and it has not been touched since.

### F3 — no async-specific lifetime hazard exists

This was the strongest candidate for the guard being deliberate, and it does not hold. `QueryExecutor` is `[Register(..., ServiceLifetime.Scoped)]` (`:19`) with an injected `IAsyncDocumentSession` (`:22`). The file contains **no `CreateScope`, no `OpenAsyncSession`, and no `using var`** — grep returns nothing. An awaited method runs on the same DI scope and the same session as a sync one, and enumeration happens inside `ExecuteCustomQueryAsync` before it returns. A user method that opens and disposes its own session breaks identically in the sync case.

### F4 — `Task<IRavenQueryable<T>>` is broken today, not merely degraded

The six gates read the cached flags, but the materialization fallback at `:338` tests the **runtime object**:

```csharp
:334   if (methodInfo.IsRavenQueryable) entities = await ExecuteQueryableAsync(...);
:338   else if (result is IQueryable)   entities = MaterializeQueryable(...);
```

With the guard, an awaited Raven queryable fails the flag test at `:334`, falls into `:338`, and lands in `MaterializeQueryable` (`:483`) — a blocking `Enumerable.ToList` over an async Raven session, which RavenDB rejects. **The flag/runtime asymmetry is the actual root cause**, and dropping the guard eliminates the failure rather than causing it.

### F5 — a test comment documents the bug as though it were a design constraint

`tests/MintPlayer.Spark.Tests/Services/QueryExecutorAdvancedIntegrationTests.cs:253-255`:

> Async returns `Task<IEnumerable<T>>` (already-materialized) — that's the only async shape the executor supports cleanly; `Task<IRavenQueryable<T>>` would synchronously enumerate the Raven query after awaiting and Raven rejects sync ops on async sessions.

This reads as a documented constraint and will be cited against the change. It is not one — it is a description of F4's consequence. It must be corrected in the same PR or it becomes a landmine.

### F6 — the reporter's own suggested fix half-fixes the reporter's own case

Dropping `!isAsync &&` gives `Task<IQueryable<T>>` — CodeCoverage's `Repository_Commits` — `IsQueryable = true` but `IsRavenQueryable = false`. It therefore gains sorting and row-filter pushdown, but **not** index projection, `.Include()`, or search pushdown, and still materializes through the blocking path at `:338`. The declared type is routinely weaker than the runtime object, because `session.Query<T>()` assigned to `IQueryable<T>` is the common idiom.

The same gap already exists for **sync** methods declared as `IQueryable<T>`. It is pre-existing, not introduced.

### F7 — zero in-repo behaviour change

Every custom query in the repository is unaffected by #294:

| Method | Shape | Effect |
|---|---|---|
| `DemoApp` / `HR` `Company_People`, `Fleet` `Stolen_Cars`, `Recent_Cars` | sync `IRavenQueryable<T>` | no-op |
| `WebhooksDemo` `GetProjectColumns` | `async Task<IEnumerable<ProjectColumn>>` | no-op — `IEnumerable<T>` is not `IQueryable` |
| Four test fixtures in `QueryExecutorAdvancedIntegrationTests` | sync, plus one `Task<IEnumerable<T>>` | no-op |

`Custom.StreamItems` routes to `StreamingQueryExecutor`, a separate resolution path that never touches `CustomQueryMethodInfo`.

**This cuts both ways.** Regression risk is nil, but the existing 1907-test suite passing proves nothing about this change. The new fixtures are the entire evidence base.

### F8 — `ValueTask` is misdiagnosed as a missing method

`:420` tests `GetGenericTypeDefinition() == typeof(Task<>)` only. For `ValueTask<IQueryable<T>>`: `isAsync` stays `false`, `returnType` stays `ValueTask<...>`, `ExtractQueryableElementType` (`:446`) finds neither `IQueryable<>` nor `IEnumerable<>` among its interfaces, returns `null`, and `:255` throws *"Custom query method 'X' not found on actions class … Expected a public method returning `IQueryable<T>`"* — for a method that plainly exists. Same for non-generic `Task`.

### F9 — sorting never consults the model

`QueryExecutor.cs:650-664`:

```csharp
var propertyInfo = entityType.GetCachedProperty(ResolveSortProperty(entityType, col.Property));
if (propertyInfo == null) { /* warn, skip */ continue; }
```

Neither `ApplySorting` nor `ResolveSortProperty` consults `EntityAttributeDefinition.ShowedOn` or `GetProtectedAttributesAsync`. Any CLR property on the entity type is a valid sort key.

Redaction (`RowSecurity.RedactAsync`) nulls a **value**; ordering by that value still works. `?sortColumns=Secret:asc` observed against row order is a comparison oracle, and comparison oracles are binary-searchable.

`Coverage` demonstrates the shape: it redacts `Repository.BadgeToken`, `Repository.Gate` and `Account.InstallationId`, and had already narrowed `InstallationId`'s `showedOn` to `PersistentObject` only — correctly removing it as a *column*. It remains a *sort key*, because the framework never reads `showedOn` when sorting.

### F10 — `EShowedOn` already carries exactly the information needed

`libs/spark/MintPlayer.Spark.Abstractions/EShowedOn.cs` is a flags enum; `EntityTypeDefinition.ShowedOn` defaults to `Query | PersistentObject`. `ModelSynchronizer.cs:622-699` already narrows it structurally and preserves hand-edits by intersection (#274). So the model already knows which attributes belong to the query surface — sorting simply does not ask.

### F11 — `AddGitHub` requests no scope, and the provisioning gate requires one

`GitHubAuthenticationExtensions.cs:31` sets `AuthorizationEndpoint`, `TokenEndpoint`, `UserInformationEndpoint`, `CallbackPath = "/signin-github"` and `SignInScheme = IdentityConstants.ExternalScheme` — and never touches `options.Scope`. Nothing in `libs/` or `Demo/` adds one.

The email attestation comes only from `:60-78`, which calls `https://api.github.com/user/emails`, commented at `:56` as "(requires the `user:email` scope)". `SparkAuthenticationExtensions.cs:159-168` refuses to provision without it.

Chain, for an **OAuth App**: no `scope` → token has no scopes → `/user/emails` 403 → no `urn:github:email_verified` claim; `GET /user` also returns `email: null` unless the profile email is public → every first-time sign-in ends at `ExternalLoginErrors.EmailNotVerified`. For a **GitHub App**, scopes are ignored (`libs/webhooks/.../README.md:537`) but `/user/emails` needs the "Email addresses: Read-only" account permission, ungranted by default — same dead end.

The 403 is swallowed at `:66` (`IsSuccessStatusCode` checked, nothing logged), so there is no diagnostic.

### F12 — the challenge URL is asserted nowhere

Spark never composes a `redirect_uri`; ASP.NET derives it from `CurrentUri` + `CallbackPath`. `CallbackPath = "/signin-github"` is a bare string literal that **no test reads**. `ExternalLoginReturnUrlTests.cs:71-88` hits the challenge endpoint but against Fleet, which registers no provider — its own comment notes it "will fail before OAuth runs" — and asserts only that an attacker host is absent.

The PR #291 stub (`LocalCredentialModeTests.cs:103-119`) writes Identity's `ExternalScheme` cookie directly with a ready-made `email_verified` claim. It never invokes `/spark/auth/external-login`, never forms an authorize URL, and never calls `OnCreatingTicket`.

### F13 — `SparkSignInComponent` has no tests, and its page is unreachable in the demo

`git show --stat fa0f6c3` confirms the component and template shipped with **zero** accompanying spec; `core/src/spark-auth.service.spec.ts` contains no reference to `capabilities`.

Reading the component clears it on correctness: all four template branches (loading spinner, failure alert, empty-provider alert, provider list) exist and are guarded, both translation keys resolve, all imports and the secondary entry point resolve, `/sign-in` is routed in `disabled` mode, and all 11 `routerLink`s were chased — no dangling link survives.

Separately, `WebhooksDemo`'s shell (`shell.component.ts:54-57`) calls `loginWithProvider('GitHub')` with a hard-coded string instead of linking to `/sign-in`, so the page is never rendered in normal use. Filed as #303, out of scope here.

## Design

### D-A — capability inference moves from the signature to the result

`CustomQueryMethodInfo` keeps `IsAsync` (still needed to decide whether to await at `:282`) and `ResultElementType`. The two capability flags **leave the cached record entirely** and become per-invocation locals computed immediately after the await:

```csharp
var isRavenQueryable = typeof(IRavenQueryable<>).MakeGenericType(methodInfo.ResultElementType).IsInstanceOfType(result);
var isQueryable = result is IQueryable;
```

All six gates read those locals. This is a simplification, not a patch: it deletes state rather than adding a branch, and it collapses the `:334`/`:338` asymmetry that causes F4 — both sites now agree because both are asking the same object the same question.

### D-B — sorting is gated on the model, not on reflection

Before resolving a property, `ApplySorting` looks the declared column name up in the entity's `EntityTypeDefinition` and requires `ShowedOn.HasFlag(EShowedOn.Query)`. Only then does `ResolveSortProperty` run and redirect to a sort companion.

This is deterministic and needs no per-row knowledge — which matters, because `GetProtectedAttributesAsync` takes an entity and can differ per row, so it cannot gate a query-level operation. Gating on the query surface is the tractable, sound approximation: an attribute the caller can never see as a column must not be usable as an ordering key.

### D-C — the GitHub scope is requested, and its absence is diagnosable

`AddGitHub` adds `user:email` to `options.Scope` by default. Harmless for GitHub Apps (which ignore scopes) and required for OAuth Apps. The `/user/emails` failure path logs at Warning naming the missing scope/permission.

Verification is split by what is knowable in-process:

- **Automated:** the challenge-URL shape test (R12) and the 403 → `email_not_verified` test (R13).
- **Irreducibly manual:** that a deployed GitHub App's callback URL is registered and its email permission granted. Those live on github.com and no test can read them.

## Decisions

**D1 — infer from the runtime result, not from the declared signature.** The reporter suggested simply deleting `!isAsync &&`. Rejected: per F6 it half-fixes their own motivating query, leaves the F4 asymmetry intact, and perpetuates reasoning about assignability of unwrapped generic types — exactly the reasoning that produced the bug. Runtime inference cannot over-claim (an object either is a Raven queryable or it is not) and fixes the same gap for sync methods in one stroke.

**D2 — no post-materialization sort fallback.** Considered as a "safer" way to honour `sortColumns` on shapes that cannot push down. Rejected: it would make the grid look right while silently defeating pushdown, which is precisely the failure mode `ContextPropertyRerootTests` was written to prevent. A capability that cannot be pushed down should be visibly absent, not quietly emulated.

**D3 — gate sorting on `ShowedOn`, not on `GetProtectedAttributesAsync`.** The redaction hook is per-row and async; a query-level gate cannot call it meaningfully, and calling it per row after materialization would not prevent the ordering that already happened. `ShowedOn` is static, already synchronized, already hand-editable, and already the mechanism an app uses to hide an attribute from the grid. Coverage's existing `showedOn` narrowing becomes effective the moment this ships, with no change on their side.

**D4 — reject bad sort columns loudly rather than erroring the request.** A hard failure would break any client that persisted a sort state referencing an attribute later hidden. #279 already established that silently dropping reads as broken ordering; the middle path is to drop but report clearly.

**D5 — `ValueTask` gets a diagnostic, not support.** Adding `ValueTask` unwrapping is a feature with its own test surface, and no consumer has asked for it. Misdiagnosing an existing method as "not found" is a defect regardless, and fixing the message is cheap. If `ValueTask` support is wanted later it is a clean follow-up.

**D6 — the real GitHub round trip stays manual, with automated substitutes.** A full github.com integration test needs a human consenting in a browser and cannot run in CI. The challenge-shape test converts every "did the challenge even form" divergence into a red test for ~60 lines. A wire-protocol stub provider (~250 lines, a second Kestrel speaking real OAuth) would additionally close correlation, state, token exchange and `SignInScheme` — deferred, not rejected; the manual procedure covers it for now.

**D7 — Playwright render test deferred to #302.** The vitest spec substitutes for nearly all of it, and a second E2E host would compound the known post-#277 teardown flake.

## Migration

**#294 and #295 are behaviour changes for consuming apps, not for this repository** (F7).

- An app with an async custom query **gains** sorting, pushdown, projection and `.Include()`. If it was ordering in memory as a workaround, that ordering still applies — but a declared `sortColumns` will now also take effect, and the two can disagree. Apps should remove the workaround or the declaration.
- An app sorting by an attribute hidden from the query surface will find that column **stops working**. That is the point of #295, and the console warning names the column.
- `AddGitHub` now requests `user:email`. For an OAuth App this changes the consent screen. For a GitHub App it is inert.

Version bumps: 21 `.csproj` to `10.0.0-preview.59`; `@mintplayer/ng-spark-auth` to `22.2.1` (spec-only change, patch).

**Coverage adoption**, ready once this ships: bump seven package references `preview.57` → `preview.59`, set `LocalCredentials = Disabled` on `Program.cs:57`, bump `@mintplayer/ng-spark-auth` and pass `{ localCredentials: 'disabled' }` to `sparkAuthRoutes()`. ⚠️ Coverage registers GitHub **conditionally** (skipped when no client id is configured); with `Disabled`, `GuardAgainstUnreachableSignIn` turns that boot-without-credentials path into a hard startup failure. Correct behaviour, but it will bite any dev machine or CI job without GitHub secrets.
