## Spikes

### S1 — can the endpoints `MapIdentityApi<TUser>()` produces be selectively suppressed?

**Why it is load-bearing:** the entire premise of R3/R4 and of M1. `MapIdentityApi` is Microsoft's, lives
in `Microsoft.AspNetCore.Identity.dll`, is all-or-nothing, and exposes no removal API —
`IEndpointConventionBuilder` can *decorate* endpoints but cannot *unmap* them. If none of the routes below
works, M1 becomes "hand-write the retained endpoints", which is a materially larger and longer-lived
piece of work (it must track upstream Identity changes), so this must be answered first.

**Method:** build a throwaway minimal host and try each candidate in order, asserting against
`EndpointDataSource.Endpoints` (**not** against HTTP status codes — a 404 proves reachability, and the
requirement in R3 is *absence*, which only the data source can demonstrate):

- **(a) Nested route builder + filtered re-publication.** Call `MapIdentityApi<TUser>()` into a throwaway
  `IEndpointRouteBuilder`, read its `DataSources`, and publish only the wanted endpoints into the real
  builder via a custom `EndpointDataSource`. Expected to work and is the preferred outcome — it keeps
  Microsoft's handlers, so no upstream behaviour is re-implemented.
- **(b) A custom `MatcherPolicy` / `EndpointDataSource` decorator** that filters the composite source.
  Fallback if (a)'s route-group conventions (the antiforgery metadata stamped at
  `SparkAuthenticationExtensions.cs:84-101`) do not survive re-publication.
- **(c) Reflection over the internal `IdentityEndpointsExtensions` route table.** Explicitly to be
  *rejected* if it works — recorded here so the next reader knows it was considered and why it was not
  taken: it binds Spark to a private shape that a servicing release can change without notice.

**Trap to avoid:** running the spike inside the existing test host, where Spark's own conventions and the
generated `MapSparkAuthEndpoints` are already present, would leave it ambiguous which registration
produced a surviving endpoint. Run it as a standalone `WebApplication` with *only* `AddIdentityApiEndpoints`
+ the candidate mapper.

**Pass criterion:** for `Disabled`, `EndpointDataSource.Endpoints` contains no route pattern in the R3
set, while `/manage/2fa` and `GET /manage/info` remain, and the antiforgery metadata on the retained
endpoints is intact.

**RESULT — PASSED on candidate (a), first try.** Three probes in
`tests/MintPlayer.Spark.Tests/Authorization/Extensions/LocalCredentialFilterSpike.cs`, all green.
Candidates (b) and (c) were never needed and are not implemented.

The unfiltered route table, read from `EndpointDataSource` (probe 1) — ten endpoints, exactly what F1
claimed, with `/manage/info` appearing twice because GET and POST are separate endpoints:

```
/spark/auth/confirmEmail
/spark/auth/forgotPassword
/spark/auth/login
/spark/auth/manage/2fa
/spark/auth/manage/info
/spark/auth/manage/info
/spark/auth/refresh
/spark/auth/register
/spark/auth/resendConfirmationEmail
/spark/auth/resetPassword
```

After mapping into a throwaway `IEndpointRouteBuilder` and re-publishing the wanted subset through a
fixed `EndpointDataSource` (probe 2):

```
/spark/auth/manage/2fa
/spark/auth/manage/info
/spark/auth/manage/info
```

Probe 3 settles the question that mattered most for safety: **conventions added before materialization
survive re-publication.** The antiforgery stamping at `SparkAuthenticationExtensions.cs:84-101` is still
present as `IAntiforgeryMetadata` on the retained endpoints after the round trip, so candidate (a) does
not silently drop a CSRF control.

Two facts worth carrying into M1: `/manage/info` must be filtered **per HTTP method**, not per route
pattern (R5 keeps GET and drops POST, and they share a pattern); and `MapIdentityApi` generates
confirmation links by route name, so a mode must never keep a link-*generating* endpoint while dropping
its link *target* — `Full`, `SignInOnly` and `Disabled` all satisfy this, but a future fourth mode
might not.

**Negative result →** M1 changes shape: do not call `MapIdentityApi` at all in non-`Full` modes; hand-write
`login`, `refresh`, `manage/2fa`, `GET /manage/info` against `SignInManager`/`UserManager`, and record in
the PRD that `Full` mode keeps Microsoft's implementation while the other two use Spark's. Add a test that
pins response-shape parity between the two implementations so they cannot drift.

**Disposition (revised in M1):** the spike probes were **deleted** rather than kept. Keeping them would
have meant maintaining a second copy of the filtering mechanism in test code, which drifts from the real
one and then pins the copy instead of the product. Everything they proved is now asserted against the
shipped implementation in `LocalCredentialModeTests`: probes 1 and 2 by
`Full_mode_matches_the_pre_change_endpoint_set` + `Disabled_mode_does_not_map_any_local_credential_endpoint`,
and probe 3 — the convention-survival question — by `Antiforgery_metadata_survives_the_filtered_republication`.

### S2 — does GitHub sign-in still work end to end with the local-credential family removed?

**Why it is load-bearing:** F3 establishes by inspection that the external callback provisions inline via
`UserManager`/`SignInManager` and never calls `/register` or `/confirmEmail`. That is an argument, not an
observation, and it is the one regression that would matter most — a framework flag that silently breaks
the only remaining way to sign in would be worse than the problem it fixes.

**Method:** in `Disabled` mode, drive the full flow against a stub OAuth provider (an in-process scheme
standing in for GitHub, emitting an attested `email_verified` claim): `GET /spark/auth/external-login`
→ challenge → stub callback → `/spark/auth/external-login-callback` → assert a new `SparkUser` exists
with `EmailConfirmed = true`, no password hash, an `AddLoginAsync` row, and a valid `ApplicationScheme`
cookie. Then `GET /spark/auth/me` must report `isAuthenticated: true`, and `POST /spark/auth/csrf-refresh`
must rotate the XSRF cookie.

**Pass criterion:** the whole chain succeeds with zero endpoints from the R3 set present.

**Negative result →** the coupling F3 ruled out is real after all; identify it and either retain the
specific endpoint (amending R3, with the reason recorded) or replicate the step inline in the callback.

**Disposition:** landed as a permanent test in `tests/MintPlayer.Spark.Tests/Authorization/Extensions/`
(`External_login_provisions_a_user_when_local_credentials_are_disabled`) — AC 3.

**Sequencing note (deviation from the original plan):** S2 was written to run before M1, but it needs the
`LocalCredentials` mode to exist in order to configure `Disabled`, and its disposition was always "lands
as a test" rather than "throwaway probe". It is therefore executed **inside M1** rather than ahead of it.
This does not weaken the gate: S1 alone determines M1's *shape*, and S1 passed. S2 determines whether the
result is *correct*, and M1 does not ship until it is green.

### Not spiked: the client-side route omission

`sparkAuthRoutes` builds a plain array locally with five unconditional `import()` calls in one function
(`routes/src/spark-auth-routes.ts:27-62`), the package declares `"sideEffects": false`, and each page is
its own secondary entry point. Skipping a branch of `import()` calls is ordinary esbuild dead-code
elimination — there is no unknown here. The only subtlety (the call site must be removed, not merely the
route object, or the lazy chunks are still emitted) is a *build-output assertion in M3*, not a question
whose answer changes the design.

## M2 — `GET /spark/auth/capabilities` (#288) — R9; AC 7

**Files:**
- `libs/authorization/MintPlayer.Spark.Authorization/Endpoints/GetCapabilities.cs` (new — follows `Endpoints/GetCurrentUser.cs:8`, picked up by the endpoint source generator via `SparkAuthGroup.Prefix`)
- `libs/authorization/MintPlayer.Spark.Authorization/Extensions/SparkAuthenticationExtensions.cs` (make the mode available to the handler)

- Anonymous, like `/me`. Shape: `{ localCredentials: "Full"|"SignInOnly"|"Disabled", externalProviders: [{ scheme, displayName }] }`.
- Providers come from `IAuthenticationSchemeProvider.GetAllSchemesAsync()`, filtered to schemes with a `DisplayName` (which is what distinguishes an interactive external provider from `ApplicationScheme`/`BearerScheme`/module-certificate schemes). Shared with M1's startup guard as `ExternalAuthenticationSchemes`, so "can a human sign in with this?" has one answer.
- **Design change made during M1/M2:** the reported mode is **derived from the route table**, not read back from `SparkAuthenticationOptions`. Reporting the configured value would let the endpoint claim a surface that was never mapped, or deny one that was — exactly the drift this endpoint exists to prevent. Deriving it from the endpoints that exist makes the answer true by construction.
- No caching header initially; it is one small allocation per app boot on the client.
