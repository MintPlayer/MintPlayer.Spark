# Findings — `MintPlayer.Spark.IdentityProvider` security audit (M12.3)

**Date:** 2026-08-08
**Scope:** the OIDC provider ported from `feat/identity-provider` in `d51f9fd`. Never security-reviewed before this pass.
**Method:** two rounds of four parallel adversarial reviewers plus direct verification of every claim. Round 1 (authorize/consent/login, token endpoint, data model, endpoints/keys) produced F1–F11 and O1–O25; **its endpoints/keys reviewer never reported**, leaving that surface unexamined. Round 2 (2026-08-08), run while building [the e2e test matrix](./idp-e2e-test-matrix.md), covered it and produced N1–N4 — including the only Critical in the audit, sitting in the one file nobody had read.
**Condition this satisfies:** shipping `client_credentials` was made conditional on the package being proven sound (plan D1).

Severity uses the reviewers' ratings. "Fixed in" refers to commits on `feat/spark-hardening-m0`.

## 1. Fixed

| # | Severity | Finding | Fixed in |
|---|---|---|---|
| F1 | High | `VerifyClientSecret` used **unsalted single-round SHA-256** and `string.Equals` (not constant-time). Hashing existed only in consumer seed code, so every consumer reimplemented it and a mismatch failed silently as `invalid_client`. | `19f4bf2` |
| F2 | High | Application claims emitted as `client_{Type}`, so `{Type:"group"}` became `client_group`, matched nothing in `ClaimsGroupMembershipProvider`, and **every machine token authorized as a member of no group**. | `19f4bf2` |
| F3 | Critical | **Authorization-code replay via stale index.** Codes and refresh tokens were found by index query filtered on `Status == "valid"`; RavenDB indexes are eventually consistent, so a redeemed code still read back as valid until the index caught up. | `dfab40a` |
| F4 | High | **Bearer values stored in plaintext.** `OidcToken.ReferenceId` held the raw code/refresh token. A database dump was a live-credential dump. | `dfab40a` |
| F5 | High | **No refresh-token reuse detection.** Replaying a rotated token merely failed; a thief who redeemed first took over the chain permanently and silently. | `dfab40a` (partial — see O1) |
| F6 | Critical | **`/connect/consent` re-validated nothing** — not `redirect_uri`, `AllowedScopes`, `RequirePkce`, nor `Enabled`. One victim click on a consent screen naming a genuinely trusted client, carrying the attacker's `redirect_uri` and `code_challenge`, yielded full account takeover. Granted scopes were persisted, making escalation durable. | `09dc3cb`, `697097e` |
| F7 | Critical | **Authorization codes not bound to the redeeming client.** `codeToken.ApplicationId` was never compared to the presenter. The `redirect_uri` check compares against the code's *own* stored value — the issuing client's registered URI, which is public — so it provided no binding. A public client could redeem a confidential client's code **presenting no secret at all**. RFC 6749 §4.1.3. | `09dc3cb` |
| F8 | Critical | **Refresh tokens not client-bound, scopes never re-validated.** Any client could present another's refresh token and receive one carrying the original's subject and scopes. | `09dc3cb` |
| F9 | High | **Client authentication skipped on `ClientType == "confidential"`** — a case-sensitive ordinal compare against an unvalidated free-form string. `"Confidential"` or a trailing space silently disabled it. | `09dc3cb` |
| F10 | High | **Application claims merged into delegated tokens.** A service client configured `{Type:"group", Value:"Administrators"}` made **every user who signed in through it an administrator** — by consenting, which they do themselves. F2's prefix removal widened this without closing it. | `09dc3cb` |
| F11 | High | **Open redirect on `returnUrl`** at `/connect/login` and `/connect/two-factor` — sending a freshly authenticated user off-origin. The repo already shipped `SanitizeReturnUrl` for this exact bug class; it was `private` and uncalled. | `697097e` |

## 2. Open

### From the never-audited surface (found 2026-08-08, while building the e2e matrix)

**~~N1~~ — CRITICAL, now FIXED. `/connect/introspect` never checked token ownership.** After authenticating the caller as *some* enabled client, neither branch compared the resolved record to that client. Any client holding valid credentials could present a token it had come across and read back `sub` and `scope` — whose token it was never entered into it. Because each resource server is its own `OidcApplication`, one resource server's introspection credentials read another's users. `Revocation.cs` has always gated on `tokenDoc.ApplicationId == app.Id`; introspection simply never did, and **I carried the omission into the access-token branch myself** when rewriting it for O5 in `9b2958a`. Both branches now gate, and a mismatch returns `{active:false}` — indistinguishable from never-issued, so the gate is not itself an oracle.

> **This contradicted a claim in this document.** O5's entry said the three consumers "resolve through one `AccessTokens` so they cannot drift on what *still valid* means." True and beside the point: the shared resolver answers *whether* a token is live, and nothing downstream asked *whose* it was. Sharing a validity check is not sharing an authorization check — worth remembering the next time consolidation is offered as evidence of soundness.

**~~N3~~ — FIXED. `token_type_hint` gated the search instead of merely hinting it.** RFC 7662 §2.1 and RFC 7009 §2.1 both require extending the search when the hinted type does not resolve. Introspection returned `active:false` for a live access token presented with `token_type_hint=refresh_token` — a false negative. Worse, **revocation silently did nothing**: an access token revoked with the wrong hint matched no branch, was never revoked, and still returned the RFC-mandated 200. A caller responding to a breach was told the credential was dead while it stayed live for its full lifetime. Neither endpoint gates on the hint now.

**~~N5~~ — HIGH, now FIXED. Grant-type restrictions were unenforceable: the default was re-added on every load.** `OidcApplication.AllowedGrantTypes` carried a property initializer of `["authorization_code"]`, and RavenDB's serializer *populates* the collection the initializer already created rather than replacing it. So an application stored as `client_credentials`-only came back from the database as `["authorization_code", "client_credentials"]`. Every grant-gating check — O11's on `/connect/authorize`, O8's on the refresh grant and on refresh issuance — was therefore comparing against a list that always contained `authorization_code` and could never reject it. The interactive flow accepted a machine client no matter how it was configured. Initializer removed; empty now means empty, so a client declaring no grants can use none.

> **Only a running test could have found this.** Every fix in this branch was reviewed by reading code, and the code reads correctly at every point: the seed sets one value, the check is present and right. The defect lives in the round-trip between them. It was caught within minutes of the first test that actually seeded an application and called an endpoint — after four reviewers and a full audit had read these files and passed them.
>
> **Check the other models before trusting them.** Any Raven-persisted collection property with a non-empty initializer has the same behaviour. `AllowedGrantTypes` was the only one in this package, but the pattern is not IdP-specific — a repo-wide sweep is warranted, and the durable fix would be `ObjectCreationHandling.Replace` on Spark's serialization conventions rather than a rule everyone has to remember.

**~~N6~~ — MEDIUM, now FIXED. Two sources of truth for scopes, silently disagreeing.** `/connect/authorize` validated a requested scope against `OidcApplication.AllowedScopes` — a string list on the client — while token issuance resolved it against `OidcScope` documents filtered on `Enabled`. Nothing reconciled them. A scope listed on the client but undefined, or defined and disabled, was accepted at authorize, shown on the consent screen, consented to, and written onto the code — and then **vanished from the issued token's `scope` claim**, with a success at every screen and no error anywhere. The user granted more than the token carried. Authorize now also requires an enabled `OidcScope` and answers `invalid_scope` otherwise, so the disagreement surfaces at the point of request.

> Found by a test guard, not by looking for it: an assertion that a tampering test was actually changing something reported `"scope":""` on a token issued for `openid`. Filtering issuance on `Enabled` is right and stays — the defect was accepting at one end what the other end would not honour.

**Observation for M12.7 (not a finding).** Client lookup rides `OidcApplications_ByClientId`, which is eventually consistent, so a **newly registered application is not usable the instant registration returns**. Harmless in production, where clients are provisioned long before use, but whatever registration surface M12.7 adds should not promise otherwise — and its own tests will need to wait for indexing.

**~~N7~~ — HIGH, now FIXED. The second factor overrode the user's "Remember me" choice.** `TwoFactor.cs` invoked `TwoFactorAuthenticatorSignInAsync(code, isPersistent: true, ...)` with the flag hardcoded — the same defect O4 fixed on the login page, never carried across. Worse, the choice was not merely ignored but *dropped*: the two-factor form rendered no such field and the handler read none, so the value made on the login page did not survive the hop. A user with 2FA who declined a persistent cookie received one anyway. `rememberMe` now travels login → redirect → hidden field → POST, and the toggle links between authenticator and recovery preserve it.

**~~N8~~ — MEDIUM/HIGH, now FIXED. A recovery code could be spent twice concurrently.** `UserStore.RedeemCodeAsync` removes the code from an in-memory list and persistence happens later in `UpdateAsync`; the store's session had no optimistic concurrency. `UserStore` is scoped, so two concurrent requests each opened a session, each loaded the user, each removed the same code from their own copy, and both saved — last write wins and **both sign-ins succeed**. A single-use two-factor bypass, spendable more than once. The session now sets `UseOptimisticConcurrency`, and `UpdateAsync` maps a `ConcurrencyException` to Identity's own `ConcurrencyFailure` result rather than throwing. This is O2's fix applied to the user document, which is where it had never been applied.

> Note the shape repeating: O2 (token redemption), O9 (grant records) and now N8 are one defect — read-modify-write on a document that gates a single-use decision. The remaining unguarded writers of `SparkUser` are worth a sweep.

**N9 — MEDIUM, OPEN. Recovery codes are stored in cleartext.** `SparkUser.TwoFactorRecoveryCodes` is a `List<string>` of the codes as issued. F4 rated exactly this situation **High** for `OidcToken.ReferenceId` — "a database dump was a live-credential dump" — and fixed it by storing a hash. The same threat model applies: a dump discloses a working two-factor bypass for every user. It is stock ASP.NET Core Identity behaviour, but F4 already establishes that "that is how Identity does it" is not a reason here. **Not fixed because it is not a one-line change**: `RedeemCodeAsync` removes by exact match, so hashing means iterating and comparing every stored hash, and the codes must stay verifiable without being reversible. Pinned by test **L-T13** so a change in either direction is visible. Decide before release.

**N10 — LOW, OPEN. Recovery-code comparison is not constant-time.** `List<string>.Remove` uses ordinal equality, which short-circuits. Codes are high-entropy and not pipelineable over HTTP, so the practical risk is slight — but O18 applied constant-time comparison to the PKCE challenge for a leak that was slighter still, so the inconsistency is worth closing.

**Correction to O27's decision, forced by a structural finding.** I accepted O27 (login timing enumeration) on the reasoning that rate limiting would bound enumeration at scale. **That mitigation does not exist and cannot be enabled by configuration.** `SparkBuilderRateLimiterExtensions` partitions its global limiter on `Path.StartsWithSegments("/spark")` and returns *no limiter* for everything else; `/connect/*` is a different prefix entirely, so an app that opts into Spark's rate limiter still gets **zero** throttling on every interactive OIDC endpoint — login, two-factor, consent. Lockout is the only throttle, and lockout is per-account: it does nothing against enumeration, which spreads one attempt across many accounts. **O27 therefore stands unmitigated, not accepted-with-mitigation.** Either extend the limiter's partition to cover `/connect`, or re-decide O27 on its own merits. Recorded here rather than quietly amended, because the original decision was reasoned from a premise that turned out to be false.

**N2 — MEDIUM, OPEN. Audience is neither validated nor exposed.** `AccessTokens.ResolveAsync` sets `ValidateAudience = false`, so no path in the package asks "was this token minted for me?". Introspection now reports `aud` so a resource server can decide for itself — the disclosure half is fixed — but nothing *enforces* audience anywhere. A token minted for resource A is still accepted at resource B if B only checks `active`. Decide whether enforcement belongs here or is the resource server's job, and document whichever.

**N4 — LOW/MEDIUM, OPEN. Signing-key `kid` is the hardcoded literal `"spark-oidc-key-1"`** (`OidcSigningKeyService.cs:65`) regardless of the key material loaded, and the server holds exactly one key. So JWKS advertises the same `kid` after a key file is replaced — a relying party caching by `kid` keeps the stale key — and rotation is a hard cutover: every unexpired token signed by the old key fails validation the instant the file changes, with no overlap window. Fails closed, so not a bypass, but it makes key rotation an outage. Fix shape: derive `kid` from the key (e.g. a thumbprint), hold and publish a set, validate against any of them, sign with the newest.
>
> Also noted, not elevated: the Development auto-generated private key is written with a plain `File.WriteAllText` and no permission hardening. Fine for a local run; a problem the moment that path is reused for anything shared.

### Highest value

**~~O1~~ — CLOSED by M12.5.** `AuthorizationId` was always `""`, so every revocation cascade was dead code: `Authorize.cs` hardcoded it with the comment *"Will be linked when consent is created"* and nothing ever filled it, while `Token.cs` propagated the empty string onto every issued token. `Revocation.cs`'s access-token cascade had **never executed once**, and the reuse-detection chain revocation added in `dfab40a` revoked only the presented token. Now every code-issuing path goes through `Authorize.EnsureAuthorizationAsync`, and the id travels on the stored request record (D7) rather than as a parameter someone must remember to pass.

**~~O2~~ — CLOSED (`66ea577`).** The point-load fixed replay-by-staleness, **not** replay-by-concurrency: two simultaneous redemptions both loaded, both validated, and both saved. Both redemption sessions now set `UseOptimisticConcurrency`, and since RavenDB applies a session's changes as one batch the loser writes nothing and is answered as a replay. Best-effort bookkeeping saves ignore the outcome.

**~~O3~~ — CLOSED (`66ea577`), pending one confirmation.** `MapIdentityProviderEndpoints` stamped no `IAntiforgeryMetadata`, and the handlers read the body via `ReadFormAsync` rather than `[FromForm]`, so minimal APIs never inferred it and nothing covered them. Only the cookie's default `SameSite=Lax` stood in the way — a browser default, not a control, lost the moment a host sets `SameSite=None` (routine for SPA/OIDC; HR and Fleet already call `ConfigureApplicationCookie`). The three interactive POSTs now carry `RequireAntiforgeryTokenAttribute(true)` (`SparkIdentityProviderExtensions.cs:97,99,101`) and the rendered forms emit a token via `ConnectPage.AppendAntiforgery`.

> **Confirmed by code trace (2026-08-08) — the wiring works.** The middleware (`SparkMiddleware.cs:181-201`) runs *before* endpoint execution, reads `IAntiforgeryMetadata` off the endpoint, and calls `IAntiforgery.ValidateRequestAsync`, which parses the form itself rather than relying on minimal-API binding. `IFormFeature` caches the parsed form, so the handler's later `ReadFormAsync()` sees the same instance — no double-read hazard. On failure the middleware returns 400 and never calls `next()`, so the handler body never executes (meaning a rejected POST also cannot increment the lockout counter).
>
> One boundary worth knowing: `AddAntiforgery(opt => opt.HeaderName = "X-XSRF-TOKEN")` makes `ValidateRequestAsync` check that **header first**, falling back to the form field. A plain server-rendered `<form>` sets no custom header, so for these three pages the hidden field is what is actually validated — the header path is for the Angular JSON API. Also: tokens are bound to the **session cookie, not the route**, so a token minted on `/connect/login` validates on `/connect/two-factor`. That is by design and is not a finding; test **L-A8** pins it so nobody later reports it as one.

**~~O4~~ — CLOSED (`66ea577`).** `Login.cs` passed `lockoutOnFailure: false`, so failed passwords never called `AccessFailedAsync`: `/connect/login` was an unauthenticated, unthrottled, **unlimited password oracle** and the `IsLockedOut` branch was unreachable — strictly weaker than `MapIdentityApi`'s own login beside it, which passes `true`. Now `true`. `isPersistent` was hardcoded `true` and now follows a "Remember me" checkbox. **Rate limiting is still not applied** to this endpoint; lockout bounds attempts per account, not per attacker.

**~~O5~~ — CLOSED.** Access tokens were self-contained JWTs with **no `jti`**, and `Introspection`/`UserInfo` validated signature and expiry only, never consulting `OidcToken` — so `Status = "revoked"` had no effect, introspection reported `active: true` for a revoked token (the one question RFC 7662 exists to answer), and `client_credentials` tokens were unrevocable outright. Direct revocation could not work either: the record's id was a random Guid, so nothing tied the presented JWT to it, while RFC 7009 mandates a 200 — the caller was told it had succeeded. Access tokens now carry a `jti` and their record is keyed by it; `Introspection`, `Revocation` and `UserInfo` all resolve through one `Services/AccessTokens.cs` so they cannot drift on what "still valid" means. A missing record fails closed.

**~~O6~~ — CLOSED.** `Payload` stored the full signed JWT in cleartext, written three times and read never. Property deleted; the `jti` key is what makes a record findable, so storing the token bought nothing but a liability.

### Medium

- **~~O7~~ — CLOSED.** `iss` was derived from the attacker-controllable `Host` header on every issuance and validation path, so a forged `Host` minted tokens claiming a different issuer, signed with the real key. Now resolved in one place (`Services/OidcIssuer.cs`) from `SparkIdentityProviderOptions.Issuer`, which is **required outside Development** — it throws rather than falling back, because an unset issuer in production is the vulnerable configuration and silently working is how it would stay unset. Discovery resolves through the same helper, so what it advertises and what tokens carry cannot diverge.
- **~~O8~~ — CLOSED.** `HandleRefreshTokenGrant` never checked `AllowedGrantTypes`, so a client never registered for refresh could rotate one indefinitely; and code redemption **always** minted a refresh token regardless of `AllowedGrantTypes` or `offline_access`, so every browser client silently received a 14-day credential it never requested and could not decline. Both gated now: the grant checks registration, and issuance additionally requires `offline_access` in the granted scopes. An unissued refresh token is **absent** from the response rather than present-and-null.
- **~~O9~~ — CLOSED by M12.5.** The existing-grant lookup rode an index, so concurrent consents created duplicate `OidcAuthorization` documents (revocation then revoked one while the other kept auto-approving), and a revoked grant could still satisfy the skip-consent check until the index caught up. `OidcAuthorization` now has a natural id derived from `(subject, applicationId)`, so the pair maps to exactly one document and both reads are point-loads. The index is deleted. **Residual:** the grant is still mutated without optimistic concurrency — that half is O2's remit, and now merges rather than races, since both writers address the same document.
- **O10** — `AllowRememberConsent` and `ConsentLifetimeSeconds` are declared and **never read**. Remembered consent never expires and ignores the client's own setting.
- **~~O11~~ — CLOSED by M12.5.** `/connect/authorize` now rejects a client not registered for `authorization_code` up front, instead of letting a `client_credentials`-only client — typically holding broader application claims than any user — drive the whole interactive flow and fail only at the token endpoint.
- **~~O12~~ — CLOSED.** `post_logout_redirect_uri` was validated against **every** enabled application, so one client's registered URI was a legal logout destination for all of them — anyone able to register an application gained a redirect through this provider's origin. Logout now requires `client_id` (how OIDC RP-Initiated Logout §2 identifies the caller) and validates against that application alone. Also stops loading the whole collection per logout.
- **Logout CSRF — reviewed and ACCEPTED, not a gap.** `/connect/logout` is a bare GET with no antiforgery protection. That is deliberate and matches every OIDC implementation: front-channel logout has to be reachable by plain navigation. Forcing a victim's session to end is a nuisance, not an escalation — nothing is read, granted, or disclosed. Recorded explicitly so the absence reads as a decision rather than an oversight; test **L-G6** pins it.
- **O13** — Cleanup service deletes only `valid|redeemed`; **`revoked` and `expired` documents accumulate forever**. `Take(1000)` once per hour also caps throughput. *M12.5 settled the shape of the fix: `OidcAuthorizationRequest` carries RavenDB `@expires` metadata and the IdP now enables `ConfigureExpirationOperation` at startup, so the server reaps it. Give `OidcToken` the same treatment and `OidcTokenCleanupService` — index, query, `Take(1000)`, status filter and all — deletes outright. Status then governs validity only, never lifetime, which is the distinction the current filter conflates.*
- **~~O14~~ — CLOSED.** `client_credentials` granted **every** allowed scope when none was requested, handing a caller that asked for nothing the client's full authority. `scope` is now required on that grant.
- **O15** — Error responses distinguish unknown-client from bad-secret, and expired-code from invalid-code — client-id and code enumeration oracles. Plus a timing oracle: unknown clients return instantly while known ones run 100k PBKDF2 iterations.
- **~~O16~~ — CLOSED.** `/connect/authorize` and both consent handlers read ambient `context.User`, which under `AddIdentityApiEndpoints` resolves the **bearer** scheme before the cookie — so a Spark API access token satisfied "is a user signed in?", and a non-interactive credential could drive the whole interactive grant headlessly, minting codes with no human at any screen. All three now resolve through `HttpContext.GetInteractiveUserIdAsync()`, which authenticates explicitly against `IdentityConstants.ApplicationScheme`. The authorization-code grant delegates *a person's* authority, and only the login cookie evidences a person.
- **O17** — No uniqueness constraint on `OidcApplication.ClientId` or `OidcScope.Name`. Two documents sharing a `ClientId` means effective config is whichever the index returns first. `UserStore` already has the compare-exchange reservation pattern to copy.

### Low

- **~~O18~~ — CLOSED.** PKCE comparison now uses `CryptographicOperations.FixedTimeEquals`. The impact was slight — the stored side is the public challenge, not the verifier — but "slight" is a judgement someone has to re-make every time they read the line, and constant-time costs nothing.
- **~~O19~~ — CLOSED.** Multi-audience access tokens silently dropped all but the first: `new ClaimsIdentity(claims)` copies the list, so the later `claims.Add` never reached the token. Audiences are now appended before the identity is constructed. It failed closed, but the comment described behaviour the code did not have.
- **O20** — `OidcToken.State` actually stores the **nonce**. Rename before someone stores the real `state` there and silently breaks ID-token replay binding.
- **~~O21~~ — CLOSED.** Redirect URLs were built with an unconditional `?`, so a registered URI already carrying a query string yielded `…?x=1?code=…` on the hop that delivers the authorization code. All four sites now go through `Endpoints/RedirectUrl.cs`, which also omits empty values so "include `state` only if sent" stops needing a guard per call site.
- **O22** — *partially closed.* `id_token` was issued regardless of scope, so a client that only asked for API access still received a signed identity assertion it never sought; both grants now require `openid`, and the key is **absent** from the response rather than null when it is not issued. **Still open:** no `auth_time`/`azp`, so relying parties cannot implement `max_age`.
- **O23** — Only `client_secret_post` is supported. Discovery advertises this honestly, but RFC 6749 §2.3.1 makes Basic mandatory-to-implement and SDKs defaulting to it will fail.
- **~~O24~~ — CLOSED.** Login and two-factor reflected error *text* from the query string. It was HTML-encoded so there was no XSS, but it let anyone put their own words in the provider's own styled error box, on its real origin, above a real password field — "your session expired, confirm your password" reads convincingly there. Both pages now carry error **codes** mapped to fixed strings via `ConnectPage.ErrorMessage`, with an unrecognised code falling back to a generic message.
- **~~O25~~ — CLOSED, after a wrong first attempt.** RavenDB compares strings case-insensitively by default and the `ClientId` lookup did not opt out, so `acmeapp` would resolve the application registered as `AcmeApp` — impersonation by casing, on the lookup that decides which client every other check is then applied to. The first fix — `exact: true` on the query alone — **made it worse**, and A-C4 caught it: RavenDB's default string indexing lowercases the stored term, so a verbatim query stopped matching the correctly-cased id while the lowercased one still matched. The index side had to change too (`FieldIndexing.Exact`). Both halves of A-C4 now pass, which is what makes this an observation rather than an argument.
- **O27** *(new)* — **Timing-based user enumeration on `/connect/login`.** An unknown email short-circuits at `Login.cs:100-104` before any password hashing; a known email always reaches PBKDF2. The *messages* are identical (verified — both emit the same literal), so this is purely a timing channel. Same class as O15's timing half but a different endpoint, and O15's text does not cover it.
  > **Decision (mine, reversible) — SEE THE CORRECTION ABOVE; its premise was false.** **accept and mitigate by rate limiting** rather than equalising the hash. Reasons: this is stock ASP.NET Core Identity behaviour that every Identity-based app in this repo already shares; the registration endpoint discloses address existence far more cheaply than a timing measurement does; and the dummy-hash fix has to run through the reflection-based dynamic user-type resolution on a security-critical path, which buys complexity in exchange for closing the *slowest* of several enumeration routes. Rate limiting — already outstanding from O4 — bounds enumeration at scale, which is what actually matters. Revisit if the IdP is ever deployed somewhere registration is closed, since the calculus flips there.
- **O26** *(new — found while building the e2e matrix)* — **`OidcScope.Required` is enforced only in the UI.** The consent page renders required scopes as a `disabled` checkbox plus a hidden duplicate input (`Consent.cs:103-115`), but `HandlePost` only *intersects* the posted scopes with the request's (`Consent.cs:192-197`) — it never re-adds a scope marked `Required`. A forged POST that omits `openid` is accepted and mints a code without it. **Not an escalation** (nothing can be gained that was not requested and allowed), so this is Low. **CLOSED:** `HandlePost` now re-adds any `Required` scope present on the stored request, so `Required` means something on the server and not only in the markup. It matters because a relying party may assume `openid` is always present — an `id_token` is issued regardless (O22 notes the missing check), so the mismatch surfaces as a confusing downstream failure rather than a security boundary. Decide whether to enforce server-side or document the assumption away.

## 3. The structural fix — bind the authorization request server-side

F6, F7's amplification, the scope escalation, and `nonce`/`code_challenge` tampering are all one defect: **`/connect/consent` is routed separately and re-derives the authorization request from browser input instead of referring to the validated one.** Every security parameter round-trips through the user agent and returns as untrusted input, so every hop must independently remember to re-validate.

The same defect appeared in **five** places (authorize, consent GET, consent POST, login `returnUrl`, two-factor `returnUrl`). All five are now correct; the sixth page someone adds will be wrong again, and nothing will fail loudly.

**Fix:** persist the validated request at the end of `Authorize.Handle` as a short-lived, single-use server-side document, and redirect to `/connect/consent?request_id=<opaque>`. The page renders from that record; the POST carries only `request_id` and the decision. `redirect_uri`, `scope`, `code_challenge` and `nonce` are then **never request parameters after the first hop** — there is nothing to re-validate and no way to forget.

**Shipped as M12.5.** The per-hop checks added in `09dc3cb`/`697097e` were deliberately kept as belt-and-braces: they cost nothing and fail closed if a future path ever reintroduces a parameter-carrying hop.

Implementing it surfaced that the same "eventually-consistent index behind a security decision" mistake was one document further down — `OidcAuthorization` itself. That is now natural-id'd too (see O9). The lesson generalises: **in this package, if a document backs an authorization decision, address it by a derived id, never by index.** Three types now follow that rule (`OidcTokenReference`, `OidcRequestReference`, `OidcAuthorizationReference`); the remaining index-backed lookup is `OidcApplications_ByClientId`, which O17 and O25 both concern.

## 4. Previously not audited — now covered

The first attempt at this surface never reported, leaving `OidcSigningKeyService`, `Jwks.cs`, `Discovery.cs`, `UserInfo.cs` and the `Introspection`/`Revocation` caller model unreviewed. **A second pass covered it on 2026-08-08** and produced N1–N4 above — including the only Critical in the whole audit, which had been sitting in the one file nobody had read. Worth noting as a process point: the gap was recorded honestly in this document for weeks and still nearly shipped, because "known unreviewed" reads like "known" once it has been written down.

**Verified sound on that surface** (do not regress):
- **`alg=none` unreachable** — RS256 hardcoded at both signing sites, no negotiation.
- **Algorithm confusion (RS256→HS256 with the public key as the HMAC secret) closed** — every verification path sets `IssuerSigningKey` directly rather than resolving a key from the token's own header, so there is no attacker-steerable key lookup. `ValidAlgorithms` is therefore not load-bearing, but setting it would make the property explicit rather than emergent.
- **JWKS exposes only `n`/`e`** — never `d/p/q/dp/dq/qi`. No private-key leak.
- **Issuer validated on every path** from the single `OidcIssuer.Resolve` source, failing closed outside Development.
- **Discovery matches enforcement** on response types (`code` only) and PKCE methods (`S256` only). It advertises `client_secret_post` only, which is honest — Basic genuinely isn't implemented (O23).
- **A missing key file in Production throws at construction** — the app refuses to start rather than inventing a key.

## 5. Also missing: no way to register an application

There is **no admin surface for `OidcApplication`**. It lived in `Demo/SparkId` on the branch (`OidcApplicationActions.cs` + `App_Data/Model/OidcApplication.json`), which was deliberately not ported. Today the documents — `RedirectUris`, `AllowedScopes`, `AllowedGrantTypes`, hashed secrets — must be seeded by hand.

Coverage cannot use `client_credentials` until a client can be registered and a secret minted. This is where `RedirectUris` and `AllowedScopes` get set correctly or not, so it is also a security surface. Either port the SparkId management screens or add a minimal registration API.

## 6. What is sound (verified — do not regress)

- **`redirect_uri` matching is exact ordinal**, no prefix/wildcard/subdomain, and is validated *before* any error redirect, so the classic error-leak-to-unvalidated-URI is absent.
- **Implicit and hybrid flows are unreachable** — strict `response_type != "code"` rejection, no `response_mode`, nothing ever lands in a fragment. Discovery agrees.
- **PKCE `plain` is rejected outright**; `RequirePkce` defaults `true`; S256 is recomputed correctly and re-verified at the token endpoint.
- **All empty-collection defaults fail closed** — the classic "empty means unrestricted" is genuinely absent throughout.
- **Expiry is enforced at use time for all three token types**, not merely by the cleanup service.
- **2FA cannot be skipped** by jumping ahead; partial-auth state lives in the framework's separate scheme, not a hand-rolled flag, so it is immune to the staleness class.
- **No user enumeration by message**; no XSS in the generated HTML (all interpolation is `HtmlEncode`d).
- **Email uniqueness is cluster-safe** via compare-exchange in `UserStore` — the right primitive to copy for O2 and O17.
- **`client_credentials` is the most correct of the three grants**: a genuinely public client cannot use it, `AllowedGrantTypes` and `AllowedScopes` are both enforced, and no `id_token` or refresh token is issued.
- Codes and refresh tokens are 256-bit CSPRNG values; code TTL is 5 minutes; token responses set `no-store`.
