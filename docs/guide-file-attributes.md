# File and image attributes

Spark stores files and images on your entities through two data types, `BinaryFile` and `Image` (#700). The bytes live in a
file store, the entity keeps a small value with the file's id, name, type and length, and every download runs the entity's
read path. The design and its evidence are in [`file_attributes_PRD.md`](file_attributes_PRD.md).

## 1. Enable it

```csharp
builder.Services.AddSpark(builder.Configuration, spark =>
{
    spark.AddFiles(files => files
        .UseSkiaSharpImages()                                   // re-encode images, make variants (section 6)
        .UseClamAV(builder.Configuration.GetSection("ClamAV")));  // scan every upload (section 5)
});
```

On the client, add `withFileAttributes()` from `@mintplayer/ng-spark/files` to `provideSpark(...)`. It provides the upload
control, the detail renderer and the grid cell for both data types.

If a model declares a `BinaryFile` or `Image` attribute and `AddFiles()` is missing, startup fails and names the attribute.
The analyzer SPARK063 reports the same at build time.

## 2. Declare an attribute

The CLR property type decides the data type, and the synchronizer writes it:

| Property | Data type | Value |
|---|---|---|
| `SparkFile?` | `BinaryFile` | a stored file |
| `SparkImage?` | `Image` | a stored, re-encoded image with its variants |
| `List<SparkFile>` / `List<SparkImage>` | the same, `isArray: true` | an ordered list; the client adds, removes and reorders |
| `string` with `"dataType": "Image"` in the model JSON | `Image` | an `https:` URL or a `data:` URI, displayed only; nothing is uploaded and no plugin is needed |

```csharp
public class Car
{
    public List<SparkImage> Photos { get; set; } = [];
    public SparkFile? RegistrationDocument { get; set; }
}
```

Every member of `SparkFile` is written by the server. A save never copies a client-sent value. The client either echoes a
stored file back (kept, matched by its id), claims a fresh upload with its upload token, or sends `null` to clear the file. A
file id that the entity does not already hold is refused, so a client cannot point an attribute at someone else's bytes.

Files work inside AsDetail rows too, one level deep. The upload is bound to the document and the path `Parent.Field`
([guide-asdetail-attributes.md](guide-asdetail-attributes.md)).

## 3. `fileOptions`

A hand-written block on the attribute in `App_Data/Model/<Type>.json`. It is structural (part of the model hash), so re-run
`--spark-synchronize-model` after editing it.

```json
{ "name": "RegistrationDocument", "dataType": "BinaryFile",
  "fileOptions": { "accept": [".pdf"], "maxBytes": 5000000 } }
```

| Key | Default | Meaning |
|---|---|---|
| `accept` | images: the raster formats; **files: nothing** | Extensions or content types. Matched against the type sniffed from the bytes, never the client's name or MIME type. `*` and markup (HTML, SVG, XML) are refused. |
| `maxBytes` | `Spark:Files:MaxFileBytes` (10 MiB) | Per file. Can only lower the global cap. |
| `maxCount` | `Spark:Files:DefaultMaxCount` (10) | For a list. |
| `variants` | `thumb` 160, `medium` 800 | Image sizes (longest edge, 16–4096 px), stored as WebP. `{}` turns them off. |
| `maxPixels` | `Spark:Files:MaxImagePixels` (40 million) | Checked from the header, before decoding. |
| `delivery` | inline for raster images, otherwise attachment | How downloads are served. |

**A `BinaryFile` without `accept` refuses every upload.** That is deliberate: what a document attribute accepts is a decision
you write down. A format Spark does not recognise needs `files.AddSignature(…)`.

## 4. Choose a store

| Store | Package | Use |
|---|---|---|
| RavenDB attachments | built in (the default) | small files, one database to back up; files join the save's transaction |
| File system | `MintPlayer.Spark.Files.FileSystem` (`UseFileSystem(path)`) | a single server with a disk that is backed up |
| Azure Blob | `MintPlayer.Spark.Files.AzureBlob` (`UseAzureBlob(…)`) | Azure; direct uploads and reads through SAS URLs |
| S3-compatible | `MintPlayer.Spark.Files.S3` (`UseS3(section)`) | AWS, Garage, SeaweedFS; direct uploads through a presigned POST policy capped at the slot's size |

Object keys are always generated by the server. An external store can let browsers upload and read directly
(`DirectUploads`, `DirectDownloads`). Without that, the app proxies the bytes and serves them itself. Changing the store later
strands the files kept in the old one, so choose before users upload.

## 5. Scanning

Register an `IFileScanner`: `files.UseClamAV(…)` ([its README](../libs/files/MintPlayer.Spark.Files.ClamAV/README.md)), or your
own through `files.UseScanner<T>()`.

- **Fail closed.** Only a file the scanner calls clean can be claimed by a save and served. An infected file is deleted. A
  failed scan (timeout, reset, unreadable reply) is never a pass.
- **Inline or deferred.** By default the scan runs during the commit (`SparkFileScanMode.Inline`). With `Deferred`, the commit
  answers `Pending` and a background worker scans the file. The client then shows "Scanning for malware…" until the verdict.
- **Outside Development the app refuses to start without a scanner**, unless `Spark:Files:AllowUnscannedFiles` is set, which
  logs a warning on every start.
- **What a pass means.** clamd's signatures know nothing bad about the bytes. That does not make a file safe to open. Spark
  therefore serves every download with `X-Content-Type-Options: nosniff`, a sandbox CSP and `Content-Disposition: attachment`
  (inline only for raster images).

## 6. Images and variants

With an `IImageProcessor` (`UseSkiaSharpImages()`, or `UseNetVipsImages()`, which is LGPL; see its README), every uploaded image is
decoded and re-encoded:

- the pixel count is checked from the header first;
- the EXIF orientation is applied;
- all metadata (GPS included) is dropped;
- only the first frame is kept, and a GIF becomes a PNG;
- the variants are made beside the original.

The renderers draw the nearest larger variant. After changing the variants, run the app once with
`--spark-regenerate-variants` (add `--force` to remake all of them). Without a processor, images are stored as uploaded and
startup logs a warning.

## 7. Hooks

`IFileUploadHandler`, registered in DI:

- `ValidateAsync` runs at commit, after the size check and the sniff and before the scan. Return
  `FileUploadDecision.Refuse("…")` to reject the file with a message for the uploader.
- `OnFileAcceptedAsync` runs after a save has claimed a clean file onto an entity.

## 8. Downloads, URLs and revoking access

- A read response embeds a short-lived signed URL per file the caller may read (`Spark:Files:EmbeddedUrlLifetime`, 5 minutes).
  `/spark/files/download` issues 60-second URLs (`DownloadUrlLifetime`). The client renews an expired one.
- **Revoking a right takes effect after that lifetime**: a URL already handed out keeps working until it expires.
- A custom endpoint that hands out a picture can use the **checked** URL instead:
  `SparkFileDownloadUrl.For(new SparkFileLocation(typeId, id, attribute, file, variant))`. It never expires and runs the read
  path on every request. CodeCoverage's avatars use it.
- A caller who may not read the entity gets the same 404 as for a missing file, or the uniform 401 when anonymous. A download
  therefore never confirms that an entity exists.

## 9. Erasure and history

Replacing or clearing a file detaches it, but **on the RavenDB store a revision still holds the old bytes** while revisions are
kept (`Spark:History:Revisions`, 30 days by default). For a GDPR erasure, clear the attribute (or delete the entity) first, then
call `IFileStore.EraseAsync(entityId, fileId)`. It erases the file, its variants and the revisions that still hold it. External
stores keep no copy per revision, so deleting the object is enough there; a history entry that points at it then answers
404. Files never calls `EraseAsync` itself. CodeCoverage's `ClearAvatarAction` is a worked example.
