## S1 — measure the disclosure delta before widening it

**Question.** The PRD argues that embedding a pruned row-type definition discloses *strictly less*
than `attr.Objects` already carries. That is an argument from reading `ScaffoldFrom` and
`FromDefinition`. Before shipping an authorization-adjacent change on the strength of an argument,
measure it.

**Method.** Take a real response — `GET /spark/po/oidcapplication/{id}` in apps/HR as an admin, who
holds nothing on `ClientClaim`/`ClientSecret`. Dump the JSON. Enumerate every field of the row type
that already appears anywhere in it. Then diff that set against the pruned `EntityTypeDefinition`
the design would embed.

**Output.** A field-by-field table in the PRD's Design section, replacing the prose argument. If the
delta is anything other than "empty-collection schema + presentation metadata", **stop and re-decide**
— that is the premise the whole option rests on.

**Why it is a spike and not a test.** The answer changes the design, not just its verification. If
the delta is bigger than claimed, option C (per-app grants) becomes the right answer and M2 changes
shape entirely.

## S2 — does #387 change anything a user can currently see?

**Question.** `canEditDetailRow` fails closed. For which shipped screens does
`asDetailPermissions()[attr.name].canEdit` come back **false** today?

**Why it matters.** Two failure modes, opposite directions. If it is false everywhere (because the
record is missing — the #385 condition), M3 turns every inline AsDetail table read-only and the PR
reads as a regression. If it is true everywhere, M3 is untestable against real config and needs a
fixture.

**Method.** For each of the six array-AsDetail attributes, resolve the row type's rights from the
owning app's `security.json` and record what `canEdit` would be for a signed-in user and for an
admin. Cross-check against S1's live response.

**Done. Measured across all four apps' `security.json`, expanding combined actions and applying
`Read ⇒ Query`:**

| Parent.attribute | Row type | Rights on the row type | Effect of a fail-closed `canEdit` |
|---|---|---|---|
| `Build.Sessions` (CodeCoverage) | `BuildSession` | **none at all** | already broken (#385) |
| `OidcApplication.Claims` (HR) | `ClientClaim` | **none at all** | already broken (#385) |
| `OidcApplication.Secrets` (HR) | `ClientSecret` | **none at all** | already broken (#385) |
| `GitHubProject.Columns` | `ProjectColumn` | Signed-in: Query, Read | none — the attribute is already `isReadOnly` |
| `GitHubProject.EventMappings` | `EventColumnMapping` | Signed-in: Query, Read, Edit, New, Delete | none — `canEdit` is true |
| `Person.Jobs` (HR) | `CarreerJob` | Admins: full · HR managers: Query/Read/Edit/New · **Viewers: Query, Read only** | **one screen changes** |

**Answers.** M3 changes exactly one shipped screen: HR `Person.Jobs` becomes read-only for
**Viewers**, who hold `Query`+`Read` and no `Edit`. That is the correct behaviour and the intended
effect of the issue, not a regression — and it is the fixture M3 should be written against.

**And it surfaces something the PRD did not say.** For the three row types with *no rights at all*,
M2 restores **readability only**. The `ClrType` fallback then returns honest all-false, so the Add
button stays absent and the inputs stay read-only — correct per the decision register's rule that
*"a type used only as an `asDetailType` still needs a type-level grant"*, but it means **an HR
administrator still cannot manage `OidcApplication.Claims`/`.Secrets` after the framework fix.**
Restoring that needs the per-app grants (the PRD's option C), which are therefore **promoted from
"interim" into this plan as M2b** rather than left implied.

Note also that the form template has **no renderer branch** for AsDetail arrays (only
`editMode === 'inline'` at `spark-po-form.component.html:104` and the modal branch), so
`Build.Sessions`' `build-sessions` renderer does not spare it on the form — only on the detail page.

## S3 — is the delete arm reachable by the existing test payload?

**Question.** Before writing six facts about `DeleteHeadBranchIfEnabled`, prove a test can reach it
at all.

**Why it matters.** The shared PR payload in `GitHubEventsRecipientTests.cs:214-218` hardcodes
`"merged": false`, `"state": "open"` and has **no `installation` node**. The method returns early at
`:407` when `evt.Installation?.Id` is null — the unlisted seventh arm. A test suite written without
noticing would pass, assert on an empty `Deleted` list, and prove nothing. **This is the exact
"green over a dead path" failure this repo has now hit three times.**

**Method.** One throwaway test: seed a `Repository` with `DeleteBranchOnPrClose = true`, drive a
`closed`+`merged` payload, and assert `installer.Deleted` has **one** entry. Get it passing before
writing anything else.

**Output.** The minimal payload edits needed, recorded here. Then delete the throwaway or promote it
to M4's first fact.

## M1 — RED: a row type without `Query` renders no columns

The regression test, at the layer where it is visible. Two levels:

- **Server** (`tests/MintPlayer.Spark.Tests`): `GET /spark/types/{parentId}` for a parent with an
  array-AsDetail attribute whose row type the caller lacks `Query` on. Assert `detailTypes` carries
  the row type with its attributes. Fails today: the property does not exist.
- **Client** (`libs/node_packages/ng-spark/pipes`): `as-detail-columns.pipe` given an
  `asDetailTypes` record missing the attribute returns `[]`. That is *current* behaviour and the
  pipe is correct — so the client-side RED belongs in the component, asserting that
  `loadAsDetailTypes` populates `asDetailTypes[attr.name]` from `entityType().detailTypes` when the
  catalogue misses.

**Verify RED for the right reason.** The server test must fail with "no `detailTypes` property",
not with a 403/404 — a fixture whose caller accidentally holds `Query` would pass without the fix
and prove nothing. Record the observed failure here, as `issue_384_plan.md` M1 did.

## M2 — GREEN: embed pruned row definitions, and the `ClrType` fallback

Per the PRD's Design. In order:

1. `EntityTypeDefinition.DetailTypes` — `[JsonIgnore(WhenWritingNull)]`, modelled on `CanRead`.
   ⚠️ Add a round-trip test that a synchronize does **not** write it to a model file. `ModelSynchronizer`
   persists definitions, and `#253` established that synchronize never deletes — a property that
   leaked in would be permanent in every model file.
2. `SubQueryPruner` — `EmbedDetailTypesAsync`, with a visited-id set and a depth bound.
3. `EntityTypes/Get.cs` + `List.cs` — chain it after `PruneAsync`.
4. `ModelLoader` — a `ByClrType` dictionary beside `ById`/`ByAlias`. `GetEntityTypeByClrType` is a
   `FirstOrDefault` today, and embedding calls it per AsDetail attribute per type.
5. `GetPermissions.cs` — the two-line `ClrType` fallback (FR2).
6. `entity-type.ts` — `detailTypes?: EntityType[]`, documented as per-caller.
7. `spark-po-form.component.ts:283-293` and `spark-po-detail.component.ts:320-327` — fall back to
   `entityType().detailTypes` when the catalogue misses.

**Verify:** M1 goes green; the four pruned fields are absent from the embedded copy; and a caller with
**no** rights on the parent still gets nothing.

## Deliberately not doing

- **Widening `List.cs`** to admit `Read` or `New`. Its `Query`-scoping is deliberate and
  `spark-po-detail` depends on it for sub-query pruning.
- **A `ClrType` fallback in `ResolveEntityType`.** Twelve call sites, and it would make
  `POST /spark/po/{ClrType}/…` route while creating a CLR-name-versus-alias collision class. The
  fallback goes in `GetPermissions` alone.
- **Changing `Get.cs:27` to test `Read || Query`.** `SparkRightImplications` already does this at
  index-composition time; a second implementation in the endpoint layer is exactly what that type's
  doc comment warns against. The only edit worth making is replacing `Get.cs:26`'s parenthetical with
  a `<see cref="SparkRightImplications"/>` pointer, so the next reader finds the implementation
  rather than concluding — as this plan's own first draft did — that it does not exist.
- **Making `DeleteBranchOnPrClose` settable.** Belongs to the Account-PO work; the naive grant is
  actively dangerous (PRD, Out of scope).
- **#386 and #388.** Separate units, not a split of this one.
