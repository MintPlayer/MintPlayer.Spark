## Spikes

### S1 — `MapControllers()` idempotency, and analyzer detectability

**Question, two parts.**

(a) During migration an app may call both `spark.UseControllers()` and its old `MapControllers()`. Does the second call reuse the single `ControllerActionEndpointDataSource`, producing no duplicate endpoints and no `AmbiguousMatchException`? This decides whether the analyzer diagnostic is a *warning* (harmless-but-wrong) or must be an *error* (actively broken).

(b) Does an analyzer reliably resolve `endpoints.MapControllers()` to `ControllerEndpointRouteBuilderExtensions.MapControllers` by symbol, across the call shapes apps actually write — `app.MapControllers()` (minimal hosting), `endpoints.MapControllers()` inside `UseEndpoints`, and a `MapControllers().RequireAuthorization()` chain?

**Method.** (a) A `TestServer` host with a trivial controller; call `MapControllers()` twice; assert over `EndpointDataSource` that each action appears once. (b) An analyzer unit test over all three call shapes, following the SPARK004 test pattern.

**Negative result →** (a) if duplicates appear, `spark.UseControllers()` must detect and refuse rather than compound, and the severity rises to error. (b) if symbol resolution is unreliable for a shape, fall back to a name match with the containing type checked, and document the gap.

### S2 — deny-by-default antiforgery in a real browser

**Question.** Does the Angular SPA actually send `X-XSRF-TOKEN` on the five CodeCoverage writes? And does the non-ambient exemption hold under a real `covt_` API token **and** a GitHub OIDC JWT?

**Method.** Run CodeCoverage against the new middleware with `RequireAntiforgery = true`, drive the five endpoints from the SPA, and drive `UploadsController` with both non-ambient schemes. `Coverage\ClientApp\src\spark-auth.setup.ts:34` suggests the interceptor is wired — **that must be tested, not assumed.**

**Negative result →** if the SPA does not send the token, the warning-only mode becomes the shipped default and the flip moves to the next major. If the exemption misses a scheme, `IsNonAmbientCredential` needs widening before this ships.

### S3 — memo sharing

**Question.** F7: the per-request memo holds hook invocations to one per `(type, action)` because Raven caps a session at 30 requests. Does `ISparkRowRule<T>` delegating into the scoped `RowSecurity` actually share it?

**Method.** Instrument the invocation counter. Issue one request that hits both a controller (via `ApplyAsync`) and a `/spark` query for the same type, and assert **one** invocation per `(type, action)`.

**Negative result →** the interface must take the memo explicitly, or `RowSecurity` must expose a scoped accessor. Shipping a second memo is not an option — it silently doubles I/O against the cap #239 exists to protect.

### S4 — `ApplyAsync` over a projection

**Question.** `ComposeRowFilterAsync` declines to compose when `elementType != entityType` (`RowSecurity.cs:232-245`) and falls back to `FilterAsync`'s base-document reload — which is session-bound and internal. Can `ApplyAsync` reproduce that path from a public API, or must it refuse projections?

**Method.** Call `ApplyAsync` with `session.Query<VRepository, Repositories_Overview>()`. CodeCoverage queries exactly this shape, so it is the **first** thing a real consumer hits.

**Negative result →** `ApplyAsync` must throw a clear "projection queries are not supported; query the entity type" rather than silently returning unfiltered rows. State the limit in the XML docs either way.

### S5 — `[SparkAuthorize]` end to end

**Question.** Does `IAuthorizationRequirementData` work in this host shape, with `AuthorizationMiddleware` where `UseSpark()` puts it (`SparkMiddleware.cs:200`) and a handler resolving a scoped `IAccessControl`?

**Method.** An MVC action with `[SparkAuthorize("Read", "Person")]`. Assert granted and denied paths, plus `[AllowAnonymous]` override. Confirm no pipeline reordering is needed.

**Negative result →** fall back to `SparkAuthorizationPolicyProvider : DefaultAuthorizationPolicyProvider` resolving `"Read/Person"` as a policy name, with base fallback for unknown names.

### S6 — reserved ids are unreachable by claim

**Question.** F11 says a claim naming `Authenticated` resolves the well-known id through `ResolveGroupIds`, bypassing the `IsAuthenticated` gate — falsifying a comment shipped in #306. Confirm before designing the exclusion.

**Method.** A stub `IGroupMembershipProvider` returning `["Authenticated"]` for an unauthenticated caller. Assert the group is granted **today** (RED), and not granted after M6.

**Negative result →** if it is already unreachable, this is a doc fix rather than a code fix and M6 shrinks.

### S7 — `*ngTemplateOutlet` under OnPush + zoneless

**Question.** Does writing `providers.set([...])` after first render re-stamp a projected template with the new context — with no `markForCheck`, no `ApplicationRef.tick()`, no zone?

**Method.** A host component passing `providerTemplate`, with `capabilities()` resolving late. Build on the timing shape already demonstrated at `spark-sign-in.component.spec.ts:114-126`.

**Negative result →** the whole projection design needs `ChangeDetectorRef` plumbing inside the component, which should be decided now rather than discovered in a consumer's app.

### Not spiked: the bundle-exclusion guarantee

`spark-auth-routes.ts:29-32` documents that an excluded page ships no chunk because the `import()` call site is unreachable. Not spiked because it is not testable at the vitest tier and not observable from Playwright — it is a **CI grep over the built bundle**, added in M12, not a spike.

### Not spiked: `In()` at scale

#301's unbounded-`In()` concern is real but is a *measurement*, not a design gate. Nothing in this PR's design depends on the answer, and a cap chosen without data would be arbitrary. Recorded as a follow-up in the PRD.

## M2b — SPARK010: a bare `MapControllers()` bypasses Spark's rules

Per F18 the check is single-file and syntactic: any invocation resolving to `ControllerEndpointRouteBuilderExtensions.MapControllers` in a compilation referencing Spark. `spark.UseControllers()` calls it inside Spark's own assembly, which the app's compilation never analyses, so no cross-file tracking is required.

**Files:** `libs/source_generators/MintPlayer.Spark.SourceGenerators/Diagnostics/MapControllersAnalyzer.cs` + `.Rules.cs`, matching the SPARK001-SPARK009 layout.

The message must say what is lost, not merely what to type: *bypasses Spark's authorization and antiforgery rules; use `spark.UseControllers()`.* Warning severity (pending S1a), suppressible — an app that deliberately wants the raw call should be able to say so once, visibly.

A code fix ("replace with `spark.UseControllers()`") is desirable but requires the CodeFixes assembly (#270) — **not in this PR**; recorded as a follow-up.

## Outcome

**Every milestone shipped.** Deviations from the plan, and why:

### The analyzer lives in `MintPlayer.Spark.SourceGenerators`, not in the Controllers package

The plan put SPARK010 "next to the feature it polices". It ships in the existing generator assembly
instead, for three reasons that only became visible on contact:

- Every Spark app already references that assembly as an analyzer. Shipping the rule from the
  Controllers package would mean an app only gets warned *after* adopting the package — precisely
  backwards, since the warning's audience is an app that has not adopted it.
- The predicate is "this compilation references Spark", which is exactly what the generator assembly
  already scopes itself to.
- The analyzer test harness resolves analyzers out of that one assembly by name.

The **runtime** is its own package, as directed. Only the diagnostic moved.

### `spark.UseControllers()` is on `ISparkBuilder`, not on `IEndpointRouteBuilder`

It registers through `SparkModuleRegistry.AddEndpoints`, so `MapSpark()` mounts the controllers along
with everything else Spark maps. That is how every other module already works, it matches the owner's
literal `spark.UseControllers()`, and it makes the Add/Use split expressible without a second
extension surface. Idempotent, guarded by a marker registration.

### No `SparkControllersOptions`; antiforgery scope lives in core

`AddControllers` takes an `Action<IMvcBuilder>` instead of a bespoke options class — that keeps every
MVC feature reachable without this package growing a property per feature, and there turned out to be
nothing controller-specific left to configure.

The antiforgery scope is `SparkAntiforgeryOptions` in `MintPlayer.Spark`, reached by
`spark.AddAntiforgeryProtection(...)`. It has to be there: R6 requires the inverted default to cover
minimal-API `MapPost` and Razor Pages, which have nothing to do with the Controllers package. Putting
the knob in the module would have made the one design decision the PRD argues hardest for — cover the
whole surface, not just MVC — impossible to express.

### M7's resource-target validation is not implemented

Rejecting a combined action in a denial, a malformed resource and a duplicate right id all ship.
Validating the *target* half against known entity names, `LookupReferences` and plural collection
names does not: the Authorization package has no access to the model, and the three namespaces the
plan lists are exactly the conditions under which a naive check cries wolf. Filed as a follow-up
rather than shipped half-right.

### S2 was not run

It requires driving CodeCoverage's five endpoints in a browser, in another repository. What ships
instead is a demonstration in this repo: WebhooksDemo turns `RequireAntiforgery` on for `/api`, and
its one cookie-authenticated `POST` is the same shape as CodeCoverage's five. The browser run stays
on the carry-over list with the GitHub OAuth round trip.

### An analyzer discouraging `[Authorize]` was considered and declined

Raised by the owner mid-implementation. Declined, and the reasoning is worth keeping: all three
shapes of `[Authorize]` have a legitimate use — bare `[Authorize]` always works, `Policy =` works if
the app registered one, `Roles =` works if the app stores groups as Identity roles. SPARK004 and
SPARK010 earn a warning because *no* correct program trips them; a rule that fires on correct code
teaches people to suppress it.

The genuinely dangerous shape is `[Authorize(Roles = …)]`, which fails closed and inconsistently when
groups arrive as `group` claims — but that is a symptom of Spark having no canonical group-claim
shape, which is already an out-of-scope follow-up. Fix the cause and the diagnostic is unnecessary;
ship the diagnostic and the inconsistency is blessed. Documented in the controllers guide instead.
