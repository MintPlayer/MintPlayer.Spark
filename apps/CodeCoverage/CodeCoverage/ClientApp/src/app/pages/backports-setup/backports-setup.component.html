Backports

CodeCoverage carries a merged change onto your older release lines. Ask for it with a label or a comment; the app cherry-picks the change onto every line you named and opens one pull request per line.

Each line is handled on its own: a line that conflicts never holds the others back. Platform values such as the target framework are rewritten to the line's own first, so a change that only moved the platform does not conflict.

Branches matching releaseBranches in coverage.yml are release lines, such as release/dotnet-10.x or release/8.x. They are versioned like the default branch, within the major their own content computes, so master on net11.0 and a line on net10.0 release 11.2.3 and 10.1.2 side by side.

A line is cut for you when a merge into the default branch moves a platform major, for example from net10.0 to net11.0: the app creates the old major's line at the merge's first parent and comments on the pull request.

A line is supported while its platform major has not reached end of life (the Platform lifecycle page under Guides lists the dates), and the newest line of each ecosystem always is. Supported lines get the backport labels a pull request is given when it opens. lines: in the backport section keeps or retires a line.

Push a backport/<pr>-<line> branch yourself, with write access, and the app opens its pull request into the line. Or comment /backport <line> --draft for a draft pull request with the conflict markers committed: resolve them on that branch, then mark it ready.

A backport made entirely by hand is recognised too, when its description says Backport of #N, its branch is backport/<N>-<line>, or its commits were picked with git cherry-pick -x. The original then gets its backported: label and a comment linking it.
