Setting up the dependency updater

CodeCoverage keeps a repository's dependencies current with one rolling pull request, mintplayer/dependencies, rebuilt on a schedule. It updates every ecosystem the lookup reports (npm, pnpm, yarn, NuGet, Maven, Gradle, Cargo, Go, Python, Composer, Bundler, Docker, GitHub Actions, …) and the platform SDKs (.NET, Node.js, Python, Java, Go).

Nothing of your repository ever runs on the CodeCoverage server. Every restore, relock and migration runs in your own GitHub Actions, in workflows the bot dispatches and whose results it checks before anything is pushed. Each run:

  1. Lookup. The bot dispatches dependency-lookup.yml on the default branch, which lists every dependency and the versions available.
  2. Plan. It applies your policy (thresholds, holds, cooldown, account rules, approvals) and commits the plan to the bot-only ref mintplayer/dependencies-work.
  3. Apply. It dispatches dependency-apply.yml, which edits the manifests and relocks with scripts off, and never builds.
  4. Validate and push. The bot checks the patch against the plan line by line, then builds the rolling branch from the default branch, with commits people pushed on it replayed on top.
  5. Pull request and CI. The pull request says what was applied, what waits for an approval and what is held. Green and within the thresholds, it goes to the merge queue; red, the bot bisects to find the culprit.

Right after you switch it on, the bot opens mintplayer/dependencies-onboarding (a repository GitHub has only just added shows as "syncing" on the onboarding page and is onboarded once it is in; a daily pass retries anything that did not go through). It:

  • adds .github/workflows/dependency-lookup.yml and dependency-apply.yml, thin callers of the GitHub Action MintPlayer/MintPlayer.Spark/apps/CodeCoverage/dependency-action, pinned to a commit with the dependency-update-v1 tag kept as a comment. The lookup lists what is available; the apply edits and relocks with scripts off;
  • adds angular-migrate.yml and nx-migrate.yml when the repository has angular.json or nx.json: they run the migrations of a group you approved;
  • appends a commented dependencies: section to coverage.yml: the defaults apply until you uncomment it;
  • removes the version-update entries of .github/dependabot.yml and lists its ignore: entries translated into dependencies: rules, for you to keep the ones you want.

The workflows are all you add: no other action, and no secret unless a private feed needs one. Keep their file names, or name them in dependencies.lookupAction / applyAction. To add them by hand, copy them from the action's templates. The rolling pull request keeps the action's pin current without the cooldown, because the action is the bot's own runtime.

The first rolling pull request is a draft. After you merge the onboarding pull request, the first mintplayer/dependencies pull request is opened as a draft and never auto-merges: review it once. The ones after it follow your thresholds.

Dependabot alerts stay on: they are what starts a security run. A vulnerable package skips the schedule and the cooldown, and the fix goes into the rolling pull request, with only the groups that may auto-merge anyway; a fix that is a major still waits for approve.

Approvals
An update over its threshold stays out of the pull request until a writer comments approve <group>. The approval is bound to the exact dependency set, the target major and the coverage.yml it was given under: a newer major, a changed group or another coverage.yml expires it. It is checked again at apply time, so an approver who lost write access loses the approval.
Holds
A group is held by a hold comment or a rule's hold:, until removed; by a manifest value you pushed on the rolling branch, so the next slot does not undo it; and by the bot itself, when CI went red on it or the resolver refused it. The pull request lists every hold and why.
Blockers
A group the resolver refuses (an Angular major before the Nx plugin supports it, say) is reset and held, naming its blockers, and the other groups still ship. The hold lifts when a newer version of a blocker appears, and after four slots in any case.
Red CI
The failing checks are re-run once. Then suspects are left out one by one, majors first, one CI run each within the bisect budget, until the culprit is found; it is held, recorded as red for the whole account, and the rest is rebuilt without it.
Your own commits
A code fix you push on the rolling branch keeps the versions it was written against pinned until the pull request is merged or closed, and such a pull request is merged by a person. A conflict the bot cannot regenerate, or a branch rewritten by hand, freezes the branch: resolve it there, or close the pull request to let it start over.
} @case ('platforms') {

Platform SDKs. When net10.0 becomes net11.0 or Node 22 becomes 24, every location moves together: the target framework, global.json, a Dockerfile's FROM and the setup-* versions in your workflows. Locations are detected; a computed target framework is reported, never guessed. Override the detection under platforms.<sdk> with locations and exclude; strategy: add with keepPrevious multi-targets instead of replacing, and lockPackageMajor: true moves your packages' own major version with the platform. Previews are followed only when the repository is already on one, and a platform major never auto-merges.

Code migrations. migrate: maps a dependency to a workflow, such as the angular-migrate.yml and nx-migrate.yml templates the onboarding adds. It runs only after an approve of a major, with no secrets (ng update --migrate-only, nx migrate --run-migrations). A migration that does not complete drops its group, and a pull request with migrations never auto-merges and says so.

} @case ('security') {
  • No repository code runs on the server. The server runs git only, without hooks, filters or merge drivers.
  • The workflows are read-only. The templates have contents: read, no id-token and persist-credentials: false. The bot refuses to dispatch a workflow, yours included, with write permissions, id-token, no top-level permissions: or a pull_request_target trigger, or a migrate workflow that reads secrets. The dispatched file must equal the default branch's.
  • Feed secrets reach only the lookup, and the apply of ecosystems whose relock runs no package code (npm, pnpm, yarn, NuGet restore, Composer with --no-plugins, Cargo, Go, Maven); never Gradle, and uv only with --no-build.
  • The bot judges every patch, not the runner: only planned package files, each changed line a planned version swap, no added or deleted files, no build or registry configuration, no install scripts, nothing under .github/ but uses: refs and setup-* versions, lockfile URLs on known registries with integrity on every entry, and a person for more than 25 new packages.
  • Pushes use a token minted per job for the one repository, revoked afterwards.
The residual risk, stated plainly. The validators stop the runner from changing anything beyond the plan; they cannot make a planned package safe. Once a malicious version is planned, your pull request's CI installs it with your CI's secrets (npm scripts in CI's own install, NuGet build/*.targets on build).
