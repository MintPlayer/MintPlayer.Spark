Optimal GitHub setup for the merge queue

The merge queue rebases each pull request onto the latest base, resolves conflicts in generated files, waits for your checks on the result and squash-merges it. Set the repository up as below, and every merge goes through the queue while the queue is held to exactly the reviews and checks everyone else is.

Every merge should go through the queue, and the queue should be held to the same reviews and checks as everyone else. One ruleset cannot do both: the App would need a bypass that also skips the reviews and checks. So there are two rulesets, and this first one only restricts who may update the branch.

Settings → Rules → Rulesets → New ruleset → New branch ruleset:

  • Ruleset name: Only the merge queue updates the default branch, or any name you like.
  • Enforcement status: Active.
  • Target branches: the default branch and every other branch in mergeQueue.branches. Never all branches and never mq/**: the queue creates, force-updates and deletes its own mq/<base>/pr-<n> branches and force-pushes pull-request branches, and a rule on those ends its pull requests with push-rejected.
  • Branch rules: only Restrict updates.
  • Bypass list: the CodeCoverage App with Exempt, and the Repository admin role with For pull requests only.

With the App exempt, Squash and merge is blocked for everyone else, maintainers included; their write role still lets them queue. Repository admins can still merge by hand, through the pull request only and never by a direct push, for what the queue refuses by design: a pull request from an organization-owned fork, a fork push GitHub refused (fork-push-rejected), and a change under .github/ that also needs regenerating, from a fork whoever queued it, or from the repository itself queued without the merge queue bypass role (step 8). Why both approval settings are off. GitHub dismisses an approval when a push changes the pull request's diff. A plain rebase by the queue keeps the diff, but the regenerate step (step 6) changes it. With the first setting, a pull request whose generated files the queue rewrote would lose its approval just before the merge; with the second, it would wait for someone to approve again, because the queue pushed last. The queue never pauses for that. It covers the gap itself: it pins the commit you queued and takes the pull request out on any push it did not make, it limits its own change to the generated files you list, and your checks run on the final commit. If you keep either setting on, the queue warns when it takes a pull request, and GitHub refuses the merge of every pull request whose files it regenerated.

The queue checks the App's bypass itself every time it takes a pull request, with its own token, and refuses (bypass) when it could bypass a ruleset that holds reviews or checks.

Only for a repository with generated files, such as Spark's modelHashes.json and securityPosture.txt. After a rebase that resolved a conflict in one of them, the queue dispatches this workflow on its mq/<base>/pr-<n> branch. The run regenerates the files and uploads them as a patch; the queue checks the patch against regeneratedPaths and pushes it itself. The workflow never commits or pushes.

Copy it to .github/workflows/regenerate.yml on the default branch (GitHub dispatches only a workflow the default branch has), list your apps under projects:, pin the action and set postRebaseActionName: regenerate.yml.

This workflow builds and runs the pull request's code, in your repository's context.
  • permissions: contents: read and nothing more; never id-token: write.
  • No secrets: no secrets.* and no environment. Restore packages from public feeds only.
  • GitHub-hosted runners only: on a self-hosted runner, the pull request's build code would run on your machine.
  • Keep persist-credentials: false, so the job token is not left in .git/config while the build runs.
  • Pin the action by a full commit SHA, never @master: that branch moves many times a day, and the action has no moving tag.

Lockfiles. Your other workflows

The queue pushes to its mq/ branch only to dispatch this workflow; a pull request that needs no regeneration never creates one. Pushes to mq/ start push workflows, never pull_request ones, and their check runs land on the commit the queue may merge, so a push-only workflow there would hold up the merge. Add branches-ignore: ['mq/**'] to every push: trigger that is not limited to named branches already; a push: with branches: [master] needs nothing.

For a pull request from a fork, this is enforced. The mq/ commit holds the fork's code, and a workflow started by that push runs it with your repository's secrets. So before it pushes there, the queue reads your workflows and removes the pull request (fork-unsafe-workflows, naming the file, the line and the fix) while a push: or create: trigger would start on that branch (paths: filters do not count), this workflow grants more than contents: read, reads a secret or may run on a self-hosted runner, a workflow_run: trigger follows this workflow there, or any workflow runs on check_run, check_suite, status, deployment or deployment_status: a check, a status or a deployment of the mq/ commit starts it with your secrets, and it may check that commit out. For a pull request from a fork, the queue pushes the rebased commit to the contributor's own branch, through GitHub's Allow edits by maintainers checkbox (on some pull requests "Allow edits and access to secrets by maintainers"); it never makes a fork of its own. A fork's pull request without the box ticked is refused when it is queued, with an explanation. The box is in the pull request's sidebar, and on the form that opens the pull request.

GitHub offers the box only on forks owned by a user, not on forks owned by an organization. Those pull requests, and any whose fork refuses the queue's push (fork-push-rejected), are merged by a repository admin through ruleset 1's bypass (step 3).

GitHub never lets an App add or change a workflow file in a fork, whatever its permissions. When the base branch changed its workflow files after the fork branched, the queue cannot publish to the fork, and the run ends with fork-workflow-update-needed. Click Update branch on the pull request (or merge the base into the branch), then queue it again.

Merge queue approval floor
Approval for external authors (the default): a pull request by an author without write needs an approval first; an author with write needs none. Repository rules only: nothing beyond the repository's own rules, which suits an organization with a single maintainer. Always require an approval: every pull request needs one. An approval counts when it is an approving review of the queued commit, by someone with write other than the author, and still that reviewer's latest word.
Checks the merge queue ignores
Check-run or commit-status names the queue does not wait for, matched exactly; the typical entry is a secret scanner that flags the hash lines of modelHashes.json. A check a ruleset requires is always waited for. A repository takes the account's list or its own (Ignored checks from), which may be empty. Everything else on the commit about to be merged is waited for, including every check that had reported on the pull request when it was queued: queue a pull request once its CI has started.
Merge queue bypass role
The lowest GitHub role on the repository whose holders skip the queue's own rules: Nobody (the default), Maintain or admin role or Admin role only. A repository's page also offers Use account setting, its default, and can turn the account's bypass off with Nobody. When whoever queued a pull request holds the role, the approval floor is skipped, and so is the .github/ rule of step 6 for a pull request from the repository itself, never from a fork. The checks, the workflow and patch checks, and the write role it takes to queue are never skipped.

Then queue a pull request

Click Add to merge queue on the pull request's "Merge queue" check, add the merge-queue label, comment /queue (/dequeue takes it out again), or use the button in the merge queue panel of the repository's CodeCoverage page. Queueing takes the write role on the repository. The queue answers on the pull request and in its "Merge queue" check run.

The "Merge queue" check is on every open pull request into a queue branch that is not a draft. While the pull request is not queued, the check reads "Not queued", and its button is at the top of the check's page: open it from the pull request's checks, or from the link at the end of CodeCoverage's coverage comment. While the pull request waits in line, the check carries Remove from queue instead, which takes it out like /dequeue. A pull request that leaves the queue without merging gets Add to merge queue back, and the check's title says why it left.

Every reason a pull request can leave the queue is in the merge queue guide.
